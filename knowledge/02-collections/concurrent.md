## ConcurrentHashMap: что защищает карта (CCN-01–03)

Обычный HashMap не предназначен для конкурентных структурных изменений без внешней синхронизации. Hashtable синхронизирует свои методы; это не превращает последовательность вызовов в одну атомарную операцию. ConcurrentHashMap (CHM) реализует ConcurrentMap, допускает конкурентные чтения и обновления, не допускает null ни в ключах, ни в значениях. Поэтому null из get означает отсутствие отображения в момент соответствующего чтения, а не сохранённое null-значение.

Два клиента могут прочитать один и тот же счётчик и потерять обновление:

~~~java
var m = new ConcurrentHashMap<String,Integer>();
m.put("x",0);
int a = m.get("x"); // клиент A
int b = m.get("x"); // клиент B
m.put("x",a+1);
m.put("x",b+1); // 1, а не 2
~~~

Это последовательная модель допустимого чередования, не случайно воспроизведённая гонка. Каждая операция корректна по отдельности. Ошибка — логика check-then-act между операциями. Аналогично containsKey и последующий put не резервируют отсутствие ключа.

| Операция CHM | Атомарный переход | Результат |
|---|---|---|
| putIfAbsent(k,v) | установить при отсутствии | прежнее значение либо null |
| remove(k,v) | удалить при равенстве текущего значения v | boolean |
| replace(k,old,new) | заменить при совпадении old | boolean |
| replace(k,v) | заменить только существующее | прежнее значение либо null |

Условные операции сравнивают значения по равенству, а не по идентичности. Успешный переход не гарантирует, что другой поток не изменит отображение сразу после него.

## Вычисления на одном ключе (CCN-04–07)

Для CHM следующие методы выполняют соответствующий вызов атомарно. В таблице описана именно эта реализация, а не универсальное поведение любого Map.

| Метод | Когда вызывается функция | Результат null | Исключение из функции |
|---|---|---|---|
| computeIfAbsent(k,f) | ровно один раз за вызов, если ключ отсутствует; иначе не вызывается | не устанавливает запись | запись не устанавливается |
| computeIfPresent(k,f) | ровно один раз за вызов при наличии отображения; иначе не вызывается | удаляет запись | отображение не меняется |
| compute(k,f) | ровно один раз за вызов; старое значение может быть null | удаляет существующую запись либо оставляет отсутствие | отображение не меняется |
| merge(k,v,f) | при отсутствии устанавливает v без вызова f; иначе вычисляет f(old,v) | удаляет запись | отображение не меняется |

Передаваемое в merge значение v и функции должны быть ненулевыми. Для CHM null из функции — специальный результат, не способ сохранить null. Гарантии вызова не означают «один раз за всю жизнь ключа»: после удаления или неуспешного вычисления следующий вызов может вычислять снова.

~~~java
m.merge("x",1,Integer::sum);
m.compute("x",(k,v)->v==null?67:v+1);
var value = m.computeIfAbsent("new",k->67);
~~~

У default-реализаций ConcurrentMap другой уровень обязательств: computeIfAbsent может вычисляться несколькими конкурирующими вызовами, а compute/computeIfPresent/merge используют условные операции и повторные попытки; remapping function может быть вызвана повторно. Реализации вправе переопределять их с более сильными гарантиями. Общий Map не обещает атомарность default-методов. Проверяйте Javadoc фактического класса.

Для CHM вычисления должны быть короткими: во время них некоторые обновления других потоков могут блокироваться. Не изменяйте эту же карту из mapping/remapping function; в частности, computeIfAbsent запрещает попытки обновлять другие отображения этой карты, а computeIfPresent/compute/merge запрещают модификацию карты во время вычисления. IllegalStateException при обнаруживаемом рекурсивном обновлении, которое иначе не завершилось бы, не означает диагностику любого цикла. Не демонстрируем рекурсию потенциально зависающим кодом.

**Исключение не является транзакционным откатом.** Если функция изменила поле существующего mutable value, затем бросила исключение, отображение может остаться той же ссылкой, но объект уже изменён. Внешняя запись в журнал, отправленное сообщение или побочный эффект в другой структуре также автоматически не отменяются.

## Атомарность и публикация (CCN-08–09, CCN-24)

Пусть баланс A=67, B=0. Две операции compute/merge списывают 1 и зачисляют 1. Между ними сумма 66, хотя начальное и конечное состояние имеют сумму 67. Атомарность отдельного отображения не даёт атомарной транзакции по двум ключам. Общая блокировка помогает лишь тогда, когда все участники, включая читателей инварианта, используют тот же протокол. Альтернатива — хранить связанное неизменяемое состояние одним отображением либо использовать подходящую транзакционную систему.

Happens-before (HB) — отношение, задающее видимость и порядок действий по JMM. ConcurrentMap гарантирует, что действия потока до помещения объекта в карту как ключа или значения предшествуют действиям другого потока после доступа к этому объекту или его удаления. CHM отдельно гарантирует HB между обновлением ключа и ненулевым результатом чтения, сообщающим именно это обновление.

~~~java
record Payload(int number) {}
var map = new ConcurrentHashMap<String,Payload>();
map.put("x",new Payload(67)); // публикация
// Другой поток читает опубликованное отображение:
var p = map.get("x");
~~~

Если чтение вернуло опубликованный объект, предшествующая инициализация доступна по указанному контракту. Но обычное поле изменяемого объекта, записанное после публикации, не становится автоматически потокобезопасным. Аналогично передача элемента через concurrent queue публикует действия до помещения элемента для потока, который затем получает или удаляет его. Для последующих изменений нужен отдельный протокол. Два независимых get не образуют общий снимок.

## Обход, представления, агрегаты (CCN-10–11)

Итераторы CHM слабо согласованные (weakly consistent): могут отражать изменения после создания, не бросают ConcurrentModificationException из-за конкурентного изменения карты и не являются атомарным снимком. Один итератор предназначен для использования одним потоком. Не проверяйте конкретный набор или порядок элементов при конкурентном обновлении.

~~~java
var m = new ConcurrentHashMap<String,Integer>();
m.put("a",1);
var keys = m.keySet();
// keys.add("b"); // UnsupportedOperationException
m.keySet(67).add("b"); // отображение b -> 67
~~~

Обычное представление keySet связано с картой, допускает удаление, но не добавление; вариант с mapped value позволяет добавить ключ с данным ненулевым значением при отсутствии. Он не заменяет имеющееся значение при добавлении уже существующего ключа.

size/isEmpty/containsValue при конкурентных обновлениях годятся для приблизительного мониторинга, не для резервирования состояния. Проверка isEmpty и последующее действие не атомарны. При putAll/clear конкурентные чтения могут видеть лишь часть изменений. Даже создание копии из изменяемой карты не гарантирует согласованный глобальный снимок.

## Синхронизированная обёртка (CCN-12)

~~~java
Map<String,Integer> m = Collections.synchronizedMap(new HashMap<>());
synchronized (m) {
    m.put("x",m.getOrDefault("x",0)+1);
    for (var key : m.keySet()) {
        System.out.println(key);
    }
}
~~~

Все участники обращаются через возвращённую обёртку. Для составной операции и обхода её представлений через Iterator, Spliterator или Stream вручную удерживают монитор именно возвращённой карты, а не исходной карты или keySet. Если кто-то изменяет backing map напрямую или использует несовместимую блокировку, протокол нарушен. Удержание монитора при медленном обходе увеличивает задержку других участников; не считать это универсально лучшим решением.

## CopyOnWriteArrayList (CCN-13, CCN-22)

~~~java
var a = new StringBuilder("a");
var list = new CopyOnWriteArrayList<>(List.of(a,new StringBuilder("b")));
var it = list.iterator();
list.add(new StringBuilder("c"));
list.set(1,new StringBuilder("d"));
a.append(67); // один поток, не пример гонки
~~~

Старый итератор сохраняет ссылки a и b и видит содержимое [a67,b]; текущий список содержит [a67,d,c]. Снимок массива ссылок не глубокая копия элементов. Итератор не отражает последующие изменения структуры, а его remove/set/add (для соответствующих видов итератора) не поддерживаются. В OpenJDK 21 изменяющая операция обычно публикует новый массив ссылок; цена копирования O(n), но не каждый вызов без фактического изменения обязан копировать массив. Старые итераторы могут удерживать прежние массивы и объекты. Выбирать при частых обходах и относительно редких изменениях, проверяя объём данных и фактическую нагрузку.

## Неблокирующие очереди (CCN-14)

ConcurrentLinkedQueue — потокобезопасная логически неограниченная FIFO-очередь, ConcurrentLinkedDeque — двусторонняя очередь. Оба класса запрещают null, предоставляют слабо согласованные итераторы; poll пустой очереди возвращает null. У CLQ/CLD size требует обхода и при конкурентных изменениях может быть неточным. size и poll не образуют атомарную пару. Логическая неограниченность не означает бесконечную память. Не использовать очередь как ограничитель нагрузки без отдельного протокола.

## BlockingQueue: четыре формы операций (CCN-15–17)

| Действие | Исключение | Особый результат | Ожидание | Ограниченное ожидание |
|---|---|---|---|---|
| Добавить | add(e) | offer(e) | put(e) | offer(e,time,unit) |
| Извлечь | remove() | poll() | take() | poll(time,unit) |
| Посмотреть | element() | peek() | — | — |

На полной ограниченной очереди add бросает IllegalStateException, offer возвращает false. На пустой remove/element бросают NoSuchElementException, poll/peek возвращают null. Null-элементы запрещены. put ждёт свободного места, take — доступного элемента; timed offer возвращает false при истечении ожидания, timed poll — null. Это бюджет ожидания в API, а не строгая гарантия времени возврата по настенным часам.

~~~java
var q = new ArrayBlockingQueue<Integer>(1);
q.offer(67); // true
q.offer(1);  // false
q.poll();    // 67
q.poll();    // null
~~~

ArrayBlockingQueue имеет фиксированную вместимость; LinkedBlockingQueue допускает заданную границу, по умолчанию Integer.MAX_VALUE. Ограничение очереди предотвращает бесконечное накопление именно в ней, но не гарантирует обратное давление всей системы: производитель обязан обработать отказ, ожидание, отбрасывание или ограничение допуска. При постоянном превышении скорости поступления над обработкой очередь заполняется.

put/take и timed offer/poll допускают InterruptedException. Если контракт позволяет, передайте исключение вызывающему. Если обработчик завершает работу и не может передать checked exception, обычно восстановите флаг Thread.currentThread().interrupt() и выйдите. Не игнорируйте прерывание и не продолжайте бесконечный цикл. Прерывание до входа в ожидание также возможно. N01: Queue не объявляет put; N02: BlockingQueue.take требует обработки checked exception.

## Специализированные очереди (CCN-18–19, CCN-23, CCN-27)

ArrayBlockingQueue с fairness=true предоставляет ожидающим производителям и потребителям FIFO-доступ согласно документации класса; порядок доступа потоков отличен от FIFO элементов и не обещает одинакового процессорного времени. В закреплённой реализации ABQ использует ReentrantLock и условия notEmpty/notFull; LBQ — отдельные putLock и takeLock и общий счётчик; CLQ — CAS при работе со связями/элементами. Это механизмы OpenJDK, не рейтинг производительности.

SynchronousQueue не имеет внутренней ёмкости: передача требует встречной операции получателя. offer без готового получателя возвращает false. PriorityBlockingQueue логически неограниченна, извлекает по приоритету, запрещает null; put не ждёт свободного места в нормальной работе, но память конечна. При равном приоритете FIFO не обещан; см. [приоритетную очередь](priority-queue.md).

BlockingQueue не объявляет встроенные close/shutdown. Протокол завершения (прерывание, специальный элемент, внешнее состояние) зависит от приложения. Для специального элемента нужны согласованные число потребителей, обработка полной очереди и политика остановки производителей. Полная жизнь executor и отмена задач — будущие CON-POOL/CON-THREAD.

## Bulk-операции CHM (CCN-20)

forEach, search и reduce могут работать при конкурентных обновлениях, но результат не обязательно соответствует единственному моменту времени. Не полагайтесь на порядок. Search возвращает найденный ненулевой результат, а не «первый» в фиксированном порядке. Редукция требует ассоциативной и коммутативной операции. Для примитивных reduce-вариантов basis — нейтральный элемент (0 для суммы, MAX_VALUE для минимума int); для объектной редукции null означает отсутствие результата, а не произвольный basis. Long.MAX_VALUE как parallelismThreshold подавляет параллелизм, 1 максимизирует разбиение, но не задаёт число потоков. Функции должны выдерживать порядок и условия конкретной bulk-операции; не превращайте результат в транзакционный снимок.

## Внутренности OpenJDK 21 (CCN-21)

В закреплённом исходнике CHM использует таблицу корзин, CAS для вставки в пустую корзину (casTabAt), синхронизацию на первом узле непустой корзины в соответствующих путях обновления (synchronized(f)), деревья для некоторых корзин и совместный перенос при расширении (helpTransfer/transfer). Чтения обычно не блокируются, но из CAS одной операции не следует lock-free всех обновлений. Разные ключи могут разделять корзину, вычисление может задерживать другие updates. Segment сохраняется ради совместимости сериализации, а не как схема сегментированных блокировок горячего пути современной CHM. Не обещать универсальных размеров корзин, задержек или выигрышей.

## Дополнительные структуры и счётчики (CCN-25–26)

ConcurrentSkipListMap/ConcurrentSkipListSet дают конкурентный сортированный порядок и навигацию, ожидаемую логарифмическую стоимость базовых операций по документации классов. CHM не является индексом диапазонов; skip list не дерево TreeMap. Для множества отдельно см. [ConcurrentSkipListSet API21](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ConcurrentSkipListSet.html).

~~~java
var counts = new ConcurrentHashMap<String,LongAdder>();
counts.computeIfAbsent("x", k -> new LongAdder()).increment();
~~~

LongAdder распределяет конкурентные обновления по внутренним ячейкам в реализации, sum не является атомарным снимком при обновлениях. Итог проверяется после завершения всех updates (например, join/Future.get всех работников) при отсутствии reset, удаления/замены счётчика и переполнения. Атомарность установки ссылки computeIfAbsent не охватывает весь жизненный цикл счётчика. Для согласованного многоключевого состояния этот паттерн недостаточен.
