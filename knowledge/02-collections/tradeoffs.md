Эта статья объединяет [контракты](contracts.md), [хеш-структуры](hash-collections.md), [списки и двусторонние очереди](sequential.md), [итераторы](iteration.md), [сортированные структуры](sorted.md), [кучу](priority-queue.md) и [конкурентные коллекции](concurrent.md). ## Сначала семантика, потом скорость (CTR-01)

Представим сервис тарифов. Нужно узнать значение для точного идентификатора, получить тариф, действовавший на заданную дату, и извлечь следующую запланированную задачу. Это три разных операции: поиск по равенству, поиск предшествующего ключа и извлечение минимального элемента. Одинаковое слово «поиск» не делает структуры взаимозаменяемыми.

Перед выбором уточните, что определяет уникальность, разрешены ли дубликаты и `null`, нужен ли порядок вставки, порядок сравнения или позиция, допустимы ли изменения через представление, какой инвариант требуется при конкурентном доступе. Например, BigDecimal("1.0") и BigDecimal("1.00") различны по `equals`, но сравниваются как равные по `compareTo`. Замена `HashSet` на `TreeSet` может изменить число сохранённых элементов. `PriorityQueue` может быстро извлечь голову, но обход её итератором не обещает сортировку.

Сравнивать скорость допустимо лишь после проверки того, что кандидаты реализуют одну и ту же требуемую семантику. Если контракт не выполняется, экономия времени не исправляет решение.

## Списки, позиции и концы (CTR-02)

`ArrayList` хранит элементы в массиве ссылок; `get`(i) использует индекс. `LinkedList` в OpenJDK 21 хранит двусвязные узлы и для доступа по индексу проходит от ближайшего конца. Для n элементов многократный вызов `get`(i) при полном последовательном обходе может привести к O(n²) суммарной работе у `LinkedList`.

~~~java
// Список уже заполнен. Для LinkedList это плохой способ полного обхода.
long sum = 0;
for (int i = 0; i < list.size(); i++) {
    sum += list.get(i);
}

// Если нужна только последовательность значений, используйте итератор.
long other = 0;
for (int value : list) {
    other += value;
}
~~~

Вставка в связный список при уже известной позиции итератора не требует поиска узла заново: изменение соседних ссылок — постоянное число действий. Но вызов add(index,value) сначала ищет позицию; в худшем случае это линейный проход. У массива вставка в середину перемещает суффикс. Нужно отдельно учитывать поиск позиции и собственно изменение.

Для работы с концами при единоличном владении обычно рассматривают `ArrayDeque`: операции добавления и удаления на концах имеют амортизированную постоянную стоимость, но произвольного доступа по индексу нет. У `ArrayDeque` запрещён `null`; замена `LinkedList` на неё может потребовать изменения контракта.

## Хеширование или порядок сравнения (CTR-03)

`HashMap` предназначена для поиска точного соответствия. Документация обещает постоянную стоимость базовых `get`/`put` при хорошем распределении хешей по корзинам. Это не безусловная гарантия O(1) для каждого набора ключей. Коллизии приводят к дополнительным сравнениям; преобразование некоторых корзин в деревья в OpenJDK не делает все операции гарантированно логарифмическими для произвольных ключей.

`TreeMap` гарантирует логарифмическую стоимость `containsKey`/`get`/`put`/`remove` в модели операций над деревом. Она предоставляет `floorEntry`, `ceilingEntry` и диапазонные представления, которых нет в контракте `HashMap`.

~~~java
var tariffs = new TreeMap<Integer,String>();
tariffs.put(10,"basic");
tariffs.put(67,"premium");
var entry = tariffs.floorEntry(70); // 67=premium
~~~

Полный поиск предшественника в неиндексированной `HashMap` потребовал бы просмотра ключей. Но если нужны только точные идентификаторы и порядок не важен, дерево выполняет дополнительные сравнения.

В модель стоимости входят `hashCode`, `equals` и `Comparator`: вычисление хеша длинного составного ключа, сравнение длинных строк с общим префиксом, дорогая пользовательская функция могут изменить картину. Не переносите оценку числа сравнений на абсолютную задержку в наносекундах.

## FIFO, deque и приоритет (CTR-04)

Если задача — обрабатывать сообщения в порядке поступления, нужна FIFO-очередь; если нужно обслуживать оба конца, `Deque`; если сначала нужно извлекать задачу с наименьшим сроком, `PriorityQueue` с соответствующим компаратором.

~~~java
var fifo = new ArrayDeque<Integer>();
fifo.offer(67); fifo.offer(1);
System.out.println(fifo.poll()); // 67
var priority = new PriorityQueue<Integer>();
priority.offer(67); priority.offer(1);
System.out.println(priority.poll()); // 1
~~~

Обе очереди допускают дубликаты, но выбирают голову по разным правилам. Для равных приоритетов `PriorityQueue` не обещает стабильного порядка. Если он нужен, добавьте явный критерий сравнения по уникальному номеру поступления. Уточните поведение на пустой очереди: `poll` возвращает `null`, `remove` бросает `NoSuchElementException`. Если производителей и потребителей несколько, обычные `ArrayDeque`/`PriorityQueue` без общего протокола синхронизации не подходят; нужно отдельно выбрать конкурентный контракт и политику ожидания.

## Что означает O(1) (CTR-05)

Различайте три разных утверждения.

| Вид оценки | Смысл | Пример |
|---|---|---|
| В худшем случае | Верхняя граница стоимости отдельной операции для допустимых входов размера n | перемещение суффикса при вставке в начало массива |
| Амортизированная | Верхняя граница суммарной стоимости последовательности, делённая на число операций | добавления в конец динамического массива |
| Ожидаемая | Оценка при явно заданных предположениях о случайности или распределении | хеширование при хорошем распределении |

При геометрическом росте массива суммарное число копируемых ссылок за n добавлений ограничено геометрической суммой O(n), хотя конкретное расширение может стоить O(n). Поэтому амортизированная O(1) вставка не означает постоянную стоимость каждой вставки. Это анализ модели роста, а не обещание конкретного коэффициента увеличения массива в API Java.

У `PriorityQueue` подъём элемента требует O(log n) сравнений в обычном случае, но отдельное расширение массива требует копирования ссылок. Для `HashMap` редкое расширение также может заметно увеличить стоимость конкретного `put`. Нельзя вывести p99 задержки из амортизированной оценки, особенно если измерение включает работу сборщика мусора (GC, garbage collector), ожидание блокировки и планирование потоков.

## Размер, вместимость и удержание памяти (CTR-06–07)

`size` — число элементов или отображений. Внутренняя вместимость массива — число доступных позиций, не обязательно равное `size`. `ensureCapacity` у `ArrayList` может заранее подготовить вместимость, но не добавляет элементы. У `HashMap` начальная вместимость и коэффициент заполнения влияют на расширение таблицы; число корзин не равно числу отображений. Javadoc отдельно предупреждает: стоимость обхода представлений `HashMap` пропорциональна `capacity` + `size`. Слишком большая таблица может ухудшить обход и расход памяти, даже если расширений меньше.

Ограничение `BlockingQueue` — другое понятие: это договорённость о количестве допускаемых элементов. `remainingCapacity` является наблюдением, а не бронью места для последующего `offer`. Даже очень большая ограниченная очередь не заменяет контроль поступления запросов.

Механизм хранения влияет на память и скорость независимо от асимптотики. В OpenJDK `ArrayList` хранит массив ссылок; `LinkedList` создаёт отдельные узлы со ссылками на элементы и соседей. Последовательный обход массива ссылок обычно благоприятнее для локальности, чем переходы по отдельно выделенным узлам, но сами объекты элементов могут быть разбросаны по памяти. `ArrayList`<Integer> не является плотным массивом примитивов int: упаковка примитивов (boxing) создаёт или переиспользует объекты-обёртки, а массив хранит ссылки. Сравните с [int[]](../01-java-core/arrays.md).

Выделение памяти для узлов и копий массивов увеличивает нагрузку на подсистему памяти и сборщик мусора. Фактическая стоимость зависит от JVM, размеров ссылок, выравнивания, анализа выхода объектов за пределы области использования (escape analysis), состояния кэшей, GC и нагрузки. Java не гарантирует конкретную раскладку объектов в памяти. Не указывайте универсальное число байтов на элемент без измерения в заданной среде.

## Владение состоянием и конкурентный доступ (CTR-08)

Если коллекция принадлежит одному потоку, добавление синхронизации может не решать никакой задачи. Если данные строятся один раз и затем читаются, рассмотрите неизменяемое состояние и безопасную публикацию. Если нужен атомарный переход нескольких элементов, рассмотрите общую синхронизацию или изменение модели данных. Если большинство операций независимо меняет отдельные отображения, `ConcurrentHashMap` даёт специальные операции одного ключа, но не транзакцию по нескольким ключам.

Соотношение чтений и изменений — не единственный критерий. Важны длительность обхода, размер контейнера, необходимость снимка, распределение обращений по ключам и цена вычисления. `CopyOnWriteArrayList` позволяет обходить старый массив без блокировки его структуры, но записи часто копируют массив; долгие обходы удерживают старые ссылки. Синхронизированная обёртка помогает защитить составную операцию, только если все участники соблюдают один протокол. Потокобезопасная коллекция не делает изменяемые значения потокобезопасными.

Подробные контракты и контрпримеры приведены в [COL-CONCURRENT](concurrent.md). Модель памяти Java (JMM), блокировки, атомарные классы и жизненный цикл исполнителя задач подробно рассматриваются отдельно.

## Ограничение ресурсов и обратное давление (backpressure, CTR-09)

Пусть поступает в среднем 120 задач в секунду, а потребители могут обработать 100. В простейшей модели без отказов и изменения скорости накапливается 20 задач в секунду. Это аналитическая иллюстрация, не результат измерения. При устойчивом превышении входной нагрузки над обслуживанием логически неограниченная очередь растёт до вмешательства другого ограничения. Ограниченная очередь достигает полной вместимости.

Производитель должен выбрать политику:

- ожидать освобождения места (с учётом прерывания и предельного срока);
- отклонять запрос, когда места нет;
- отбрасывать или заменять задачи, только если допускает семантика;
- ограничивать допуск до очереди, например общим протоколом управления ресурсами.

Блокировка производителя может переносить накопление в другой компонент — например, в пул ожидающих запросов. Отказ может вызвать повторные попытки и усилить перегрузку. Увеличение буфера способно поглотить краткий всплеск, но не повышает устойчивую производительность потребителя само по себе. Для `SynchronousQueue` отсутствие буфера означает непосредственную передачу между участниками. `PriorityBlockingQueue` логически неограниченна; приоритет не является ограничением ресурса.

## Таблица принятия решений (CTR-16)

| Требование | Кандидат | Условия и риск |
|---|---|---|
| Чтение по индексу, частое добавление в конец | `ArrayList` | стоимость сдвига при вставке в середину, расширения |
| Изменение в известной позиции двустороннего списка | `LinkedList` с `ListIterator` | позиция уже найдена; узлы и локальность |
| Работа с концами в одном потоке | `ArrayDeque` | `null` запрещён, не потокобезопасна |
| Точный поиск, порядок не требуется | `HashMap` | стабильные `equals`/`hashCode`, распределение хешей |
| Диапазоны и соседи | `TreeMap` | корректный стабильный компаратор |
| Извлечение по приоритету | `PriorityQueue` | обход не отсортирован, дополнительный критерий сравнения при равном приоритете |
| Независимые конкурентные изменения отображений | `ConcurrentHashMap` | один ключ, не общий снимок или транзакция |
| Редкие изменения, частые обходы снимка | `CopyOnWriteArrayList` | копирование и удержание массива |
| Ограниченный буфер между производителями и потребителями | `ArrayBlockingQueue` / `LinkedBlockingQueue` с заданной вместимостью | определить политику заполнения и завершения |

Таблица — исходные гипотезы. Чтобы выбрать между кандидатами с одинаковым контрактом, нужна информация о реальной нагрузке и, когда существенна производительность, воспроизводимый эксперимент.

## Представление, копия и снимок (CTR-17)

Представление связано с исходной коллекцией: например, диапазон `TreeMap` или `List.subList`. Для `subList` важно отдельное ограничение: если исходный список структурно изменён иначе, чем через это представление, семантика возвращённого списка становится неопределённой по контракту API. Защитная копия отделяет структуру от исходной, но обычно сохраняет ссылки на те же объекты. `List.copyOf` возвращает немодифицируемый список (может переиспользовать подходящий исходный список), но не делает его содержимое глубоко неизменяемым и не копирует сами объекты элементов и не является универсальным способом атомарно получить согласованный снимок меняющегося состояния.

Итератор `CopyOnWriteArrayList` сохраняет массив ссылок, существовавший при создании итератора. Это структурный снимок, не снимок состояния всех объектов. Если клиенту нужно согласованное состояние нескольких изменяемых полей, требуется подходящая модель неизменяемости, копирование объектов или общий протокол синхронизации. Снимки имеют цену: ссылки продлевают время жизни объектов. См. [CORE-IMMUTABLE](../01-java-core/immutability.md).

## Что именно измерять (CTR-10)

Пропускная способность (throughput) измеряет число завершённых операций за единицу времени. Задержка (latency) — время одной операции или одного запроса. Высокая пропускная способность может сочетаться с большой задержкой, если запросы ждут в очереди или обрабатываются пакетно. В конкурентном эксперименте отдельно фиксируйте предложенную нагрузку, успешные операции, отказы, ожидания и при необходимости время обработки.

Среднее время не описывает хвост распределения. p99 — квантиль измеренных задержек: примерно 99% наблюдений не превышают это значение (точная оценка зависит от метода вычисления квантиля). Его нельзя вычислить только из среднего. Нужно измерять распределение, указывать число наблюдений, единицы, метод сбора и статистическую неопределённость. Средняя задержка измеряемого метода не включает сетевое ожидание и другие этапы запроса, если они находятся вне измерения.

## JMH: построение корректного микроэксперимента (CTR-11–12)

JMH (Java Microbenchmark Harness) помогает организовать измерение небольших участков JVM-кода. Он не автоматически делает произвольный эксперимент репрезентативным.

| Механизм | Зачем он нужен |
|---|---|
| Warmup | прогреть код, дать компилятору времени исполнения (JIT, just-in-time) возможность оптимизации; не считать первый холодный запуск установившимся режимом |
| Measurement | выделить интервалы сбора результатов после прогрева |
| Forks | запускать отдельные JVM, уменьшая перенос профилей и состояния между экспериментами |
| State | определить владение данными: `Scope.Thread` для отдельных экземпляров, `Scope.Benchmark` для общего, `Scope.Group` для группы |
| Setup/teardown | явно определить, когда готовятся и очищаются входы; не смешивать подготовку с операцией без цели |
| Params | варьировать размер, режим нагрузки, распределение входов |
| Benchmark modes | `Throughput`, `AverageTime`, `SampleTime` и `SingleShotTime` отвечают на разные вопросы |

Если результат вычисления не используется, JIT может удалить ненужную работу (устранение неиспользуемого кода, DCE (dead code elimination)). Возвращайте вычисленный результат или передавайте его в `Blackhole`. Это не устраняет все оптимизации: если входы известны заранее, результат может быть вычислен как константа (свёртка констант (constant folding)). Используйте подготовленные данные и изменяющееся состояние, соответствующее сценарию, не создавайте бессмысленную работу для обхода оптимизатора. Не переносите дорогое случайное генерирование во внутренний цикл измерения, если его стоимость не относится к исследуемой операции.

Иллюстративная заготовка, **не запускалась**, не является добавленным JMH-модулем:

~~~java
@State(Scope.Thread)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
public class IndexedRead {
    @Param({"67", "10000"})
    int n;
    @Param({"array", "linked"})
    String kind;
    List<Integer> list;
    int index;

    @Setup(Level.Trial)
    public void setup() {
        list = kind.equals("array") ? new ArrayList<>() : new LinkedList<>();
        for (int i = 0; i < n; i++) list.add(i);
        index = 0;
    }

    @Benchmark
    public int read() {
        index = (index + 1) % n;
        return list.get(index);
    }
}
~~~

Единица измерения этой заготовки — один вызов метода read: индексное обращение вместе с вычислением следующего индекса и распаковкой Integer. Индексы последовательно проходят по списку, поэтому это не нагрузка со случайным выбором индекса (random access workload). Она не измеряет обход итератором, конкурентную работу или время создания списка. Для измерения обхода нужен отдельный микроэксперимент, например суммирование всех элементов с возвратом результата; единица операции тогда — весь обход, а не один `get`. Указать точные импорты, зависимости и режим запуска нужно при отдельном утверждённом эксперименте. Не сравнивать показатели разных единиц без пересчёта и объяснения.

## Репрезентативность, конкуренция за общие ресурсы (contention) и профилирование (CTR-13–15)

Для хеш-карты и дерева используйте одинаковый набор ключей, согласованные правила равенства и сравнения, несколько размеров, отдельно успешные и неуспешные поиски. Изменяйте распределение обращений (например, равномерные и популярные ключи), долю чтений и записей. Если карта растёт во время измерения, размер и число расширений меняются; фиксируйте этот сценарий явно либо ограничивайте рост, восстанавливайте состояние или подготавливайте отдельные наборы между итерациями.

Для сравнения `ConcurrentHashMap` и synchronizedMap при конкурентных изменениях нужен общий контейнер, а не `Scope.Thread` для каждого работника. Иначе потоки не конкурируют за один и тот же контейнер. Подберите количество потоков, независимые и горячие ключи, группы чтений/записей, одинаковые операции и семантику результата. Проверка итоговых инвариантов должна находиться вне измеряемой операции, если она не является частью полезной работы. Для `CopyOnWriteArrayList` полезно варьировать размер и частоту записей. Для ограниченных очередей учитывайте баланс производителей и потребителей, успешные/отклонённые операции и заполнение буфера; число вызовов `offer` не равно числу принятых задач.

Профилирование JMH с -prof gc может оценить аллокации и активность GC; bytes/op показывает объём выделенной памяти на операцию, а не размер удерживаемой кучи. Для оценки удерживаемой памяти (retained heap) нужна отдельная методика. Не сравнивайте bytes/op, если одна операция означает одно обращение, а другая — целый обход. Фиксируйте погрешность, разброс между отдельными запусками JVM и условия среды; не выбирайте единственный самый удачный запуск.

Минимальный воспроизводимый отчёт: SHA исходника, версии JDK/JMH, ОС/CPU, JVM flags, heap и GC, число потоков, параметры и распределение входов, настройки warmup/measurement/forks, state/setup, режим, единицы, статистика ошибок/квантилей, конфигурация профилировщика. Результаты не переносить на другую JVM или нагрузку как универсальные коэффициенты.

## Границы микроэксперимента (CTR-18–19)

Микроэксперимент отвечает на узкий вопрос об операции в заданных условиях. Он не воспроизводит автоматически сетевой ввод-вывод, БД, очередь запросов, обработку отказов, задержки GC всей системы и перегрузку сервиса. Если задача — оценить p99 запроса при заданной входной нагрузке, потребуется системный эксперимент с моделью поступления и наблюдением результатов на уровне запроса. Отдельно учитывать ожидание и отклонённые запросы.

Ложное совместное использование строк кэша (false sharing), размещение потоков на процессорах, неоднородный доступ к памяти (NUMA, non-uniform memory access) и настройки JVM могут влиять на результаты, но без конкретных данных нельзя объяснять ими любое ухудшение масштабируемости. Профилировать следует для проверки гипотезы, не ради списка инструментов. Полный системный нагрузочный тест и доказательство конкурентной корректности находятся вне объёма этой темы.
