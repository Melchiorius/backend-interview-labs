# Приоритетная очередь Java 21: PriorityQueue и двоичная куча

**Тема:** COL-HEAP. [План C3](../../docs/plans/COL-SORTED-HEAP.md). Связанные статьи: [сортированные коллекции](sorted.md), [последовательные коллекции](sequential.md), [итераторы](iteration.md). Практика: [SortedHeapProbe](../../examples/collections/sorted-heap/README.md).

## Что гарантирует очередь приоритетов (CP-01, CP-02, CP-06)

`PriorityQueue` выбирает голову по естественному порядку или переданному `Comparator`. Голова — наименьший элемент по этому порядку. Это не обязательно первый добавленный объект и не обязательно наименьшее число: при обратном компараторе первым становится максимум.

~~~java
var q = new PriorityQueue<Integer>();
q.offer(67); q.offer(2); q.offer(5);
System.out.println(q.peek()); // 2
System.out.println(q.size()); // 3
var max = new PriorityQueue<Integer>(Comparator.reverseOrder());
max.addAll(List.of(2,67,5));
System.out.println(max.poll()); // 67
~~~

Дубликаты разрешены. Если две задачи имеют одинаковый приоритет по `Comparator`, очередь не обязана выбирать их в порядке добавления. В отличие от `TreeSet`, нулевой результат сравнения не объединяет два элемента. Если порядок при равенстве важен, его необходимо явно определить дополнительным ключом, например неизменяемым номером поступления.

~~~java
record Task(String name, int priority, long sequence) {}
var q = new PriorityQueue<Task>(
    Comparator.comparingInt(Task::priority)
              .thenComparingLong(Task::sequence));
q.offer(new Task("first",1,1));
q.offer(new Task("second",1,2));
System.out.println(q.poll().name()); // first
~~~

Порядковые номера поступления (`sequence`) должны различать поступления, если требуется строгий порядок. Не используйте вычитание приоритетов для сравнения: переполнение нарушает контракт (см. [CT-02](sorted.md)).

## Операции Queue и ошибки (CP-03, CP-04)

| Назначение | Метод с особым результатом | Метод с исключением |
|---|---|---|
| Добавить | offer(e) | add(e) |
| Извлечь голову | poll(): `null` на пустой | remove(): `NoSuchElementException` |
| Прочитать голову | peek(): `null` на пустой | element(): `NoSuchElementException` |

`PriorityQueue` не имеет фиксированного верхнего предела вместимости по контракту, но ресурсы конечны. Для обычной ограниченной очереди `offer` может вернуть `false` при заполнении; это не поведение `PriorityQueue` при достижении внутренней вместимости (`capacity`). Она расширяет хранилище по необходимости. `null` запрещён даже с `Comparator.nullsFirst`: попытка `offer(null)` приводит к `NullPointerException`. Естественный порядок требует взаимно сравнимых элементов; неподходящий тип может вызвать `ClassCastException`. Обобщённые типы сами по себе не гарантируют наличие `Comparable` у каждого допустимого E.

Две перегрузки remove отличаются:

~~~java
var q = new PriorityQueue<>(List.of(67,2,5,2));
System.out.println(q.remove(Integer.valueOf(67))); // true: поиск равного объекта
System.out.println(q.remove()); // 2: удаление головы
System.out.println(q.poll()); // 2
~~~

remove(Object) использует равенство объектов, а не только эквивалентность приоритетов; он удаляет один подходящий экземпляр, если найден.

## Порядок извлечения и порядок обхода (CP-05, CP-14)

Последовательные вызовы `poll()` при неизменных сравниваемых полях и без промежуточных вставок извлекают элементы в порядке приоритетов, но обход через iterator(), spliterator() или new ArrayList<>(q) не обещает такой последовательности. Куча поддерживает лишь частичный порядок.

Для отсортированного снимка, не изменяющего саму очередь:

~~~java
var q = new PriorityQueue<Integer>(Comparator.reverseOrder());
q.addAll(List.of(2,67,5));
var copy = new ArrayList<>(q);
copy.sort(q.comparator());
System.out.println(copy); // [67, 5, 2]
System.out.println(q.size()); // 3
~~~

Для естественного порядка comparator() возвращает `null`, а List.sort(`null`) применяет естественный порядок. `toArray` также не гарантирует порядок приоритетов: массив можно сортировать отдельно с нужным компаратором. Копия содержит ссылки на прежние объекты, а не глубокие копии; при конкурентных изменениях исходной очереди она не является гарантированным атомарным снимком. Итератор `PriorityQueue` поддерживает remove и обнаруживает несовместимые изменения по возможности (fail-fast); это не способ синхронизации.

## Двоичная куча: механизм OpenJDK 21 (CP-08, CP-16)

Публичное API гарантирует голову по приоритету. В конкретном OpenJDK 21 реализация использует массив `queue[]` как двоичную минимальную кучу (min-heap). При индексировании от нуля родитель узла `i` (`i > 0`) расположен в `(i-1)/2` с целочисленным делением (дробная часть отбрасывается), дети — `2*i+1` и `2*i+2`, если такие индексы существуют. Каждый родитель не больше детей по компаратору. Следовательно, по транзитивности корень не больше любого потомка. Остальные элементы могут быть расположены без глобальной сортировки.

Пример допустимого состояния для элементов 2,5,67,8:

~~~text
       2
     /   \
    5     67
   /
  8
~~~

Корень имеет индекс 0, его дети — 1 и 2, а левый ребёнок узла 1 — индекс 3. Массив `[2,5,67,8]` удовлетворяет инварианту, хотя 67 стоит перед 8. Это иллюстрация алгоритма, не требование к точному массиву Java.

При offer новый элемент помещается в свободную позицию в конце и поднимается к родителю, пока сравнение требует обмена (`siftUp`). При poll корень извлекается, последний элемент переносится на его место и опускается, выбирая меньшего ребёнка (`siftDown`), пока инвариант не восстановлен. Высота полного двоичного дерева O(log n). При remove(Object) сначала требуется найти элемент линейным поиском, после чего замещающий элемент может потребовать движения вверх или вниз. Точное размещение равных элементов, детали обхода и число обменов не являются API-гарантиями.

## Стоимость и построение (CP-07, CP-11, CP-15)

| Метод `PriorityQueue` | Оценка Javadoc |
|---|---|
| offer, add, poll, remove() | O(log n) |
| peek, element, size | O(1) |
| contains, remove(Object) | O(n) |

Это оценки в модели обычной стоимости сравнения; дорогое сравнение добавляет свою цену. При расширении массива отдельная вставка может потребовать копирования O(n) ссылок, поэтому логарифмическая оценка операции не означает строго логарифмическую стоимость каждого вызова при увеличении вместимости массива. Формула роста и точное число байтов зависят от реализации/JVM, не фиксируются API.

В OpenJDK 21 метод `heapify` (построение кучи из имеющихся элементов) строит кучу снизу вверх: вызывает `siftDown` для внутренних узлов, начиная с последних. Большинство узлов близко к листьям и требует мало шагов. Обозначим через `h` высоту узла (максимальное число рёбер до листа). Узлов высоты `h` не более порядка `n/2^(h+1)`, каждый требует не более `h` шагов спуска. Суммируя по всем высотам, получаем оценку `O(n * sum(h/2^(h+1))) = O(n)`, поскольку бесконечный ряд по `h >= 0` сходится. Это лучше оценки O(n log n) для n последовательных вставок. Не всякий публичный конструктор проходит одинаковый путь: например, копирование подходящей уже упорядоченной структуры может обойти `heapify`. Не переносите оценку на все реализации Queue.

## Top-k: очередь ограничивает алгоритм, а не API (CP-12)

Задача: найти k наибольших чисел потока, не сохраняя весь поток. Поддерживаем min-heap размером не больше k. В голове находится худший из уже сохранённых кандидатов.

~~~java
static List<Integer> topK(int[] values, int k) {
    if (k <= 0) return List.of();
    var heap = new PriorityQueue<Integer>();
    for (int x : values) {
        if (heap.size() < k) heap.offer(x);
        else if (x > heap.peek()) {
            heap.poll();
            heap.offer(x);
        }
    }
    var result = new ArrayList<>(heap);
    result.sort(Comparator.reverseOrder());
    return result;
}
~~~

Для [1,67,5,2] при k=2 результат [67,5]. После каждой итерации в куче находятся min(k,число обработанных) лучших элементов с учётом повторов: если новый элемент больше головы, он заменяет худшего кандидата; иначе ничего не меняется. Для положительного `k` и входа из `n` элементов обозначим `m = min(n,k)` — число сохранённых элементов. Дополнительная память `O(m)`, обработка `O(n log(k+1))` (точнее `O(n log(m+1))` при `n > 0`) при постоянной цене сравнения, сортировка результата `O(m log(m+1))`. Это аналитические оценки, не измерения. При k>n возвращаются все элементы, при k<=0 — пустой список. Это отдельный алгоритм пользователя, а не свойство ограниченной вместимости `PriorityQueue`.

## Изменяемый приоритет и ошибки Comparator (CP-13, CP-17)

Если объект задачи был добавлен с priority=67 и затем его поле изменилось на 1, очередь не получает уведомления. Элемент не обязательно немедленно окажется в голове. Нельзя обещать конкретный результат poll после нарушения инварианта. Используйте неизменяемую задачу либо удаляйте её до изменения и добавляйте вновь. При уже нарушенном порядке может потребоваться перестроение по достоверным данным.

Компаратор должен быть транзитивным, антисимметричным по знаку и согласованным по нулевой эквивалентности. Циклическая политика (a<b, b<c, c<a) не определяет корректную голову. Исключение из сравнения не превращает операцию в транзакцию: не предполагается автоматический откат всех побочных эффектов. Не тестируйте произвольный результат некорректного компаратора как контракт.

## Потоки и выбор реализации (CP-09, CP-10)

`PriorityQueue` не потокобезопасна. При конкурентном изменении нужна внешняя синхронизация или подходящая конкурентная структура. `PriorityBlockingQueue` имеет отдельный контракт, логически неограниченную вместимость и блокирующее извлечение; это не очередь с гарантированным ограничением числа задач и не обещание атомарности многошагового алгоритма. Подробности конкурентных коллекций — будущая тема COL-CONCURRENT.

| Потребность | Подходящая структура |
|---|---|
| Повторное извлечение лучшей задачи, дубликаты | `PriorityQueue` |
| Упорядоченная уникальность и поиск соседей/диапазонов | `TreeSet` / `TreeMap` |
| Точный поиск по ключу | `HashMap` |
| FIFO/LIFO | `ArrayDeque` |

У `PriorityQueue` линейный contains/remove(Object), поэтому она не заменяет индекс поиска по ключу. Для планировщика с частыми отменами по идентификатору может понадобиться дополнительная структура и согласованный алгоритм обновления; сама куча не решает эту задачу автоматически.
