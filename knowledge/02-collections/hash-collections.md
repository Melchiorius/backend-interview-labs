# Хеш-коллекции Java 21: HashMap и HashSet

**Тема:** `COL-HASH`. **Версия:** Java SE 21; внутренние детали — конкретный OpenJDK 21. **Исследовательский план:** [COL-CONTRACTS-HASH](../../docs/plans/COL-CONTRACTS-HASH.md). Предварительно: [контракты коллекций](contracts.md), [equals и hashCode](../01-java-core/equality.md), [обобщённые типы](../01-java-core/generics.md).

`HashMap<K,V>` хранит отображения уникальных ключей в значения и использует хеширование для быстрого нахождения кандидатов на совпадение. `HashSet<E>` — множество уникальных элементов; в OpenJDK 21 оно использует `HashMap` внутри. Хеш-коллекции **не гарантируют порядок обхода** и требуют согласованного поведения `equals/hashCode`.

## Поиск, вставка и замена (CH-01)

При `put(key, value)` Java `HashMap` в OpenJDK 21 вычисляет хеш ключа, преобразует его для распределения по текущей таблице, выбирает позицию (bucket), затем ищет совпадающий ключ среди кандидатов. Совпадение может быть установлено по идентичности ссылки либо через `equals` при совпадении хеша. Если ключ уже есть, значение заменяется и `put` возвращает предыдущее; иначе создаётся новое отображение.

Для понимания различайте **хеш** и **равенство**: разные ключи вполне могут иметь один `hashCode`.

```java
record Key(int id) {
    @Override public int hashCode() { return 67; }
}
Map<Key, String> map = new HashMap<>();
map.put(new Key(1), "one");
map.put(new Key(2), "two");
System.out.println(map.size());          // 2
System.out.println(map.get(new Key(1))); // one
System.out.println(map.put(new Key(1), "updated")); // one
```

`record` сравнивает компонент `id` в автоматически созданном `equals`; явное переопределение `hashCode` создаёт коллизии. Две записи сосуществуют, потому что их ключи **не равны**. При повторном равном ключе значение заменяется. Для этого примера порядок `entrySet()` намеренно нигде не проверяется.

Разделение на `hash → bucket → equals` — объяснение работы **OpenJDK 21**, а не требование общего интерфейса `Map` иметь таблицу и бакеты. Гарантия `HashMap` для читателя выражается через поведение `Map`, а не вид внутренней таблицы.

## Изменяемый ключ разрушает предпосылку поиска (CH-02)

Поля, от которых зависят `equals` и `hashCode`, не следует менять, пока экземпляр выступает ключом. После изменения поиск может применить другой хеш/индекс и не обнаружить оставшуюся в карте запись.

```java
final class MutableKey {
    int id;
    MutableKey(int id) { this.id = id; }
    @Override public int hashCode() { return id; }
    @Override public boolean equals(Object other) {
        return other instanceof MutableKey k && id == k.id;
    }
}
var key = new MutableKey(1);
var map = new HashMap<MutableKey, String>();
map.put(key, "saved");
key.id = 67;
System.out.println(map.get(key)); // типично null для этой модели OpenJDK 21
```

Это **условное наблюдение**, а не обещание, что любая мутация любого ключа всегда приводит к `null`. Для текущей таблицы OpenJDK 21 размером 16 исходный хеш `1` даёт индекс `1`, а новый хеш `67` — индекс `3`. Ключ остался в исходном бакете. Даже изменение обратно не является универсальной процедурой восстановления некорректной структуры. Надёжный подход — неизменяемый ключ: см. [иммутабельность](../01-java-core/immutability.md).

## Порядок, null, HashSet (CH-03, CH-04, CH-12)

`HashMap` не обещает ни порядок вставки, ни сортировку, ни постоянный порядок после расширения таблицы; `HashSet` тоже. Поэтому тест вида «ожидаем именно такой текст `map.toString()`» неверен как переносимый контракт. Для encounter order используют, например, `LinkedHashMap`; сортировка — другой контракт (`COL-SORTED`).

`HashMap` допускает один `null`-ключ и отображения на `null`-значения:

```java
Map<String, Integer> map = new HashMap<>();
map.put(null, null);
map.put("x", null);
System.out.println(map.size());             // 2
System.out.println(map.get("missing"));     // null
System.out.println(map.containsKey(null));  // true
System.out.println(map.containsKey("x"));   // true
```

Если `get(k)` вернул `null`, без `containsKey(k)` неясно, отсутствует ли отображение. Фабрика `Map.of("x", (Integer) null)` бросает `NullPointerException`: её ограничения не наследуются всеми картами.

`HashSet.add(e)` возвращает `true`, когда добавился новый элемент, и `false`, когда равный элемент уже есть. Независимый `HashSet` не связан с `keySet()` другой карты: первый хранит собственные элементы, второй — backed view карты, изменения которого влияют на карту.

## Capacity, load factor, threshold, resize (CH-05)

**Capacity** — число позиций внутренней таблицы, не число отображений `size`. **Load factor** задаёт порог заполнения: при росте карты компромисс между расходом памяти и частотой расширений. В OpenJDK 21 у `new HashMap<>()` стандартный load factor `0.75`, а таблица при первом выделении имеет capacity `16`. Конкретное время выделения таблицы и перераспределение — детали реализации.

Условно при `capacity=16` и `loadFactor=0.75` threshold равен 12. После превышения порога размер таблицы может увеличиться, с перераспределением записей. Замена значения уже существующего ключа не увеличивает `size` и сама по себе не является новой вставкой. Конструктор с начальной вместимостью не создаёт столько записей: `new HashMap<>(1024).size() == 0`.

Отдельный `resize` требует работы с множеством узлов; поэтому «каждый `put` выполняется строго за O(1)» неверно. А **итерация `HashMap` согласно Javadoc пропорциональна capacity + size**, не одному `size`: чрезмерно большая таблица может замедлить даже обход нескольких отображений.

## Коллизии, списки и деревья: только OpenJDK 21 (CH-06, CH-10, CH-15)

В закреплённой версии исходника [OpenJDK 21 HashMap.java](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java) функция `hash(key)` распределяет биты через `h ^ (h >>> 16)`, а для `null` возвращает ноль. Индекс в таблице с длиной — степенью двойки определяется младшими битами распределённого хеша.

Большое число коллизий в одном бакете может привести к использованию дерева вместо связанной цепочки. В этой конкретной реализации:

| Константа | Значение | Смысл |
|---|---:|---|
| `TREEIFY_THRESHOLD` | 8 | Порог для попытки перевести переполненный бакет в дерево |
| `UNTREEIFY_THRESHOLD` | 6 | Порог перехода обратно к обычным узлам при соответствующей перестройке |
| `MIN_TREEIFY_CAPACITY` | 64 | При меньшей таблице `treeifyBin` предпочитает расширение таблицы |

**Это не означает, что ровно на восьмой вставке всегда появляется дерево.** На результат влияют длина таблицы, структура текущего бакета и конкретная ветка алгоритма. После построения дерева поиск и сравнение также зависят от `equals`, `Comparable`, правил tie-break и распределения ключей. Точная внутренняя структура не является публичным контрактом `Map`; её не следует проверять через private reflection или делать на её основе обязательный stdout.

Деревья помогают при тяжёлых коллизиях, но не гарантируют универсальное ограничение времени на любом наборе искусственно дорогих `hashCode/equals` и всех JVM. Размер отдельных `Node/TreeNode` в байтах зависит от устройства VM, выравнивания и архитектуры; без конкретного измерения числа выдумывать нельзя.

## Асимптотика с условиями (CH-07)

| Операция | Разумная оценка | Почему не абсолютная гарантия |
|---|---|---|
| `get`, `put`, `remove` | Ожидаемая близкая к O(1) стоимость при хорошем распределении и дешёвых `hashCode/equals` | Коллизии, дорогие методы ключей и resize; не строгий худший случай |
| Одна вставка с resize | Может потребовать работы с множеством отображений | Амортизация серии вставок не равна гарантии каждому вызову |
| Обход `HashMap` | O(capacity + size) по Javadoc | Capacity может быть заметно больше size |
| Операции `HashSet` | Ожидаемое постоянное время при хорошем hash distribution | Зависит от качества ключей и backing map |
| Дерево бакета OpenJDK 21 | Снижает некоторые затраты тяжёлых коллизий | Не переносить внутренний bound на любой `Map` и дорогие пользовательские сравнения |

Здесь O(1) не означает «одинаковое число наносекунд». Универсальный benchmark без оговорок о распределении ключей, нагрузке, warmup, VM и железе недостоверен. Экспериментальная производительность — предмет `COL-TRADEOFFS`, а не вывод из единичного запуска.

## Замена, null и callback-операции (CH-08, CH-14)

`put(k,v)` возвращает прежнее значение либо `null`, причём `null` не различает отсутствие ключа и прежнее null mapping. `putIfAbsent(k,v)` присваивает при отсутствии или текущем null. `computeIfAbsent(k,f)` вызывает функцию при отсутствии или null mapping; если функция вернула `null`, новое отображение не возникает. `merge(k,value,remapper)` требует **ненулевой аргумент `value`**: при отсутствии или null mapping записывает его напрямую, иначе вызывает remapper с прежним и новым значением. Если remapper возвращает `null`, отображение удаляется.

```java
Map<String, Integer> m = new HashMap<>();
m.put("a", null);
System.out.println(m.computeIfAbsent("a", k -> 67)); // 67
System.out.println(m.computeIfAbsent("b", k -> null)); // null
System.out.println(m.containsKey("b"));                // false
System.out.println(m.merge("a", 1, Integer::sum));      // 68
System.out.println(m.merge("a", 1, (oldV, newV) -> null)); // null
System.out.println(m.containsKey("a"));                // false
```

Эти функции не являются произвольной транзакцией. Если callback бросает исключение, оно распространяется вызывающему коду; не обещайте откат любых побочных эффектов внутри функции. Изменять ту же `HashMap` структурно изнутри callback нельзя считать безопасным: обнаружение нарушения может привести к `ConcurrentModificationException`; конкретные гарантии выясняйте по Javadoc операции, а не по примеру одного выполнения.

## Thread safety и fail-fast (CH-09, CH-11)

`HashMap` **не синхронизирована**. Если несколько потоков обращаются к ней и хотя бы один изменяет структуру, требуется внешняя синхронизация или подходящая конкурентная структура. `map.containsKey(k)` с последующим `put(k,v)` не становится атомарным действием от того, что каждый метод вызывается последовательно в одном потоке. `Map` default `compute/merge` в общем случае **не гарантирует атомарной конкурентной реализации**; нельзя переносить свойства `ConcurrentHashMap.compute` на `HashMap`. Многоключевая атомарность также не следует автоматически из атомарности операций по одному ключу. Это граница `COL-CONCURRENT` и `CON-JMM`.

Итераторы `HashMap` являются fail-fast по возможности: при обнаружении неподдерживаемых структурных изменений после создания итератора они могут бросить `ConcurrentModificationException`. **Это best effort, а не гарантированная реакция на каждую гонку и не механизм обеспечения thread safety.** Замена значения для уже существующего ключа в обычной OpenJDK `HashMap` не считается добавлением/удалением mapping; однако нельзя обобщать детали `modCount` на все реализации `Map`.

## Сопоставление альтернатив (CH-13)

| Реализация | Отличительная особенность |
|---|---|
| `HashMap` | нет гарантий порядка, разрешает `null` |
| `LinkedHashMap` | определён encounter order, доступен `SequencedMap` |
| `TreeMap` | сортированный по ключам порядок; равенство ключей определяется сравнением, что требует аккуратности |
| `Hashtable` | исторический synchronized-класс; запрещает `null`-ключи и значения |
| `IdentityHashMap` | сравнивает ключи по `==`, а не `equals`; специальная семантика |
| `ConcurrentHashMap` | конкурентные операции, без `null`-ключей/значений; подробности в будущем `COL-CONCURRENT` |

Сравнение не означает, что все операции и граничные случаи этих реализаций эквивалентны. Изучать `TreeMap` и конкурентные варианты следует по отдельному нормативному контракту.

## Специальные границы (CH-16)

`HashMap` поддерживает сериализацию и клонирование в рамках своей документации, но эти механизмы не дают переносимой гарантии порядка обхода после восстановления, `resize` или обновления версии JDK. Ни текущее содержимое бакетов, ни детали расположения узлов не должны становиться частью бизнес-логики.

## Проверка понимания

1. Почему два ключа с одинаковым `hashCode` могут жить в одной карте и как выбирается значение при `get`?
2. Почему изменение ключа после `put` способно сделать запись недоступной, хотя `size` не уменьшился?
3. Когда `get` возвращает `null`, что проверяет `containsKey`?
4. Почему нельзя считать обход `HashMap` гарантированным O(size), а каждый `put` — строгим O(1)?
5. Почему 8/6/64 относятся к OpenJDK 21, а не к интерфейсу `Map`?
6. Чем `computeIfAbsent` и `merge` отличаются при null, и почему это не доказательство атомарности между потоками?
