# Хеш-коллекции Java 21: HashMap и HashSet

**Тема:** `COL-HASH`. **Версия:** Java SE 21; внутренние детали — конкретный OpenJDK 21. **Исследовательский план:** [COL-CONTRACTS-HASH](../../docs/plans/COL-CONTRACTS-HASH.md). Предварительно: [контракты коллекций](contracts.md), [equals и hashCode](../01-java-core/equality.md), [обобщённые типы](../01-java-core/generics.md). **Проверяемая практика:** [ContractsHashProbe — коллизии, изменяемый ключ, compute/merge и N01/N02](../../examples/collections/contracts-hash/README.md).

`HashMap<K,V>` хранит отображения уникальных ключей в значения и использует хеширование для быстрого нахождения кандидатов на совпадение. `HashSet<E>` — множество уникальных элементов; в OpenJDK 21 оно использует `HashMap` внутри. Хеш-коллекции **не гарантируют порядок обхода** и требуют согласованного поведения `equals/hashCode`.

## Поиск, вставка и замена (CH-01)

При `put(key, value)` Java `HashMap` в OpenJDK 21 вычисляет хеш ключа, преобразует его для распределения по текущей таблице, выбирает позицию (bucket), затем ищет совпадающий ключ среди кандидатов. Совпадение может быть установлено по идентичности ссылки либо через `equals` при совпадении хеша. Если ключ уже есть, значение заменяется и `put` возвращает предыдущее; иначе создаётся новое отображение.

Для понимания различайте **хеш** и **равенство**: разные ключи вполне могут иметь один `hashCode`.

```java
record Key(int id) {
    @Override public int hashCode() { return 67; }
}
Map<Key, String> map = new HashMap<>();
map.put(new Key(1), "one");
map.put(new Key(2), "two");
System.out.println(map.size());          // 2
System.out.println(map.get(new Key(1))); // one
System.out.println(map.put(new Key(1), "updated")); // one
```

`record` сравнивает компонент `id` в автоматически созданном `equals`; явное переопределение `hashCode` создаёт коллизии. Две записи сосуществуют, потому что их ключи **не равны**. При повторном равном ключе значение заменяется. Для этого примера порядок `entrySet()` намеренно нигде не проверяется.

Разделение на `hash → bucket → equals` — объяснение работы **OpenJDK 21**, а не требование общего интерфейса `Map` иметь таблицу и бакеты. Гарантия `HashMap` для читателя выражается через поведение `Map`, а не вид внутренней таблицы.

## Изменяемый ключ разрушает предпосылку поиска (CH-02)

Поля, от которых зависят `equals` и `hashCode`, не следует менять, пока экземпляр выступает ключом. После изменения поиск может применить другой хеш/индекс и не обнаружить оставшуюся в карте запись.

```java
final class MutableKey {
    int id;
    MutableKey(int id) { this.id = id; }
    @Override public int hashCode() { return id; }
    @Override public boolean equals(Object other) {
        return other instanceof MutableKey k && id == k.id;
    }
}
var key = new MutableKey(1);
var map = new HashMap<MutableKey, String>();
map.put(key, "saved");
key.id = 67;
System.out.println(map.get(key)); // типично null для этой модели OpenJDK 21
```

Это **условное наблюдение**, а не обещание, что любая мутация любого ключа всегда приводит к `null`. Для текущей таблицы OpenJDK 21 размером 16 исходный хеш `1` даёт индекс `1`, а новый хеш `67` — индекс `3`. Ключ остался в исходном бакете. Даже изменение обратно не является универсальной процедурой восстановления некорректной структуры. Надёжный подход — неизменяемый ключ: см. [иммутабельность](../01-java-core/immutability.md).

## Порядок, null, HashSet (CH-03, CH-04, CH-12)

`HashMap` не обещает ни порядок вставки, ни сортировку, ни постоянный порядок после расширения таблицы; `HashSet` тоже. Поэтому тест вида «ожидаем именно такой текст `map.toString()`» неверен как переносимый контракт. Для encounter order используют, например, `LinkedHashMap`; сортировка — другой контракт ([COL-SORTED](sorted.md)).

`HashMap` допускает один `null`-ключ и отображения на `null`-значения:

```java
Map<String, Integer> map = new HashMap<>();
map.put(null, null);
map.put("x", null);
System.out.println(map.size());             // 2
System.out.println(map.get("missing"));     // null
System.out.println(map.containsKey(null));  // true
System.out.println(map.containsKey("x"));   // true
```

Если `get(k)` вернул `null`, без `containsKey(k)` неясно, отсутствует ли отображение. Фабрика `Map.of("x", (Integer) null)` бросает `NullPointerException`: её ограничения не наследуются всеми картами.

`HashSet.add(e)` возвращает `true`, когда добавился новый элемент, и `false`, когда равный элемент уже есть. Независимый `HashSet` не связан с `keySet()` другой карты: первый хранит собственные элементы, второй — backed view карты, изменения которого влияют на карту.

## Вместимость, коэффициент заполнения, порог роста (CH-05)

Вместимость (capacity) — число корзин таблицы, а не число отображений `size()`. Коэффициент заполнения (load factor) связывает вместимость и порог роста. У стандартной `HashMap` коэффициент 0,75; в рассматриваемой реализации при первом обычном выделении таблицы без заданной начальной вместимости создаются 16 корзин, порог равен 12. Важно различать контракт конструктора и внутреннее состояние: до первого выделения таблицы поле `threshold` может хранить целевую начальную вместимость, а не порог числа записей.

### Как определяется корзина и что меняется при росте (B1)

В [закреплённом OpenJDK 21, hash и putVal](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L631-L671) для ключа, отличного от `null`, распределённый хеш вычисляется как `h ^ (h >>> 16)`, где `h = key.hashCode()`. Для `null` он равен 0. Сдвиг без знакового расширения и XOR смешивают старшие 16 бит с младшими: при небольшой таблице старшие биты иначе не влияли бы на индекс. Это не делает хеши уникальными и не устраняет плохое распределение.

Длина таблицы — степень двойки, поэтому индекс равен `(n - 1) & hash`. Возьмём два разных ключа с хешами 1 и 17. У этих маленьких чисел старшие 16 бит нулевые, распределённые хеши совпадают с исходными.

| Хеш | Двоичное представление (5 младших бит) | Индекс при n=16, маска 01111 | Индекс при n=32, маска 11111 |
|---:|---|---:|---:|
| 1 | 00001 | 1 | 1 |
| 17 | 10001 | 1 | 17 |

Оба ключа сначала находятся в корзине 1. При удвоении таблицы в маске появляется ровно один новый бит, равный прежней вместимости (16). Поэтому для прежней корзины с индексом `i` действуют два варианта:

- `(storedHash & oldCap) == 0`: узел остаётся в корзине `i`;
- иначе узел переходит в корзину `i + oldCap`.

```text
до:    16 корзин       [1] → hash=1 → hash=17
после: 32 корзины      [1] → hash=1
                      [17] → hash=17
```

В [resize](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L683-L755) используются хеши, сохранённые в узлах при вставке. Для цепочки узлы распределяются в две части по одному биту, для одиночного узла вычисляется новый индекс по сохранённому хешу, для дерева вызывается `split`. Не требуется заново вычислять пользовательский `hashCode()` каждого ключа. Если оба распределённых хеша одинаковы, удвоение их не разделит. Именно поэтому рост помогает при одних коллизиях и не помогает при других.

Обычный рост после добавления нового отображения инициируется условием `++size > threshold`. При 16 корзинах и пороге 12 это тринадцатая новая запись, если ранее не сработало другое условие роста. Замена значения существующего ключа не увеличивает размер. Отдельный путь роста — слишком длинная цепочка в небольшой таблице (см. следующий раздел). В реализации `MAXIMUM_CAPACITY = 1 << 30`; если таблица уже достигла предела, `resize` возвращает её без удвоения и устанавливает `threshold = Integer.MAX_VALUE`. Это не обещание, что JVM располагает памятью для таблицы такого размера.

### Как задать ожидаемый размер

`new HashMap<>(1024)` принимает начальную вместимость, а не ожидаемое число отображений; размер новой карты равен нулю. Для заранее известного числа отображений в Java 21 есть фабрика [HashMap.newHashMap(expectedMappings)](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/HashMap.html#newHashMap(int)), появившаяся в Java 19. Например, `HashMap.<String,Integer>newHashMap(67)` выбирает начальную вместимость с учётом стандартного коэффициента заполнения. Она предназначена для размещения ожидаемого числа отображений без обычного расширения из-за заполнения, но это не абсолютная гарантия отсутствия роста при патологических коллизиях или иных условиях реализации. Не следует бездумно завышать вместимость: по Javadoc обход представлений `HashMap` пропорционален сумме вместимости и размера.

## Коллизии, цепочки и деревья: только OpenJDK 21 (CH-06, CH-10, CH-15)

| Константа реализации | Значение | Роль |
|---|---:|---|
| `TREEIFY_THRESHOLD` | 8 | Порог попытки преобразовать цепочку в дерево |
| `UNTREEIFY_THRESHOLD` | 6 | Порог размера каждой части дерева при разделении во время роста |
| `MIN_TREEIFY_CAPACITY` | 64 | Ниже этой вместимости вместо преобразования цепочки выбирается рост |

В обычном `putVal` сначала проверяется головной узел, затем существующее дерево либо цепочка. В цепочке счётчик `binCount` начинается с нуля на головном узле. Только когда достигнут конец и добавляется **новый отличный ключ**, проверяется `binCount >= TREEIFY_THRESHOLD - 1`. При восьми существующих узлах последний посещается со счётчиком 7; присоединение девятого вызывает `treeifyBin`. Если найден равный ключ, эта ветвь добавления не выполняется. Это точное условие указанного пути `putVal`, а не правило «восьмая/девятая вставка всегда создаёт дерево» для любых методов карты.

[treeifyBin](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L761-L775) при вместимости меньше 64 вызывает `resize`; при достаточной вместимости преобразует соответствующие узлы в древовидные и строит дерево. При росте уже существующего дерева [TreeNode.split](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L2297-L2340) разделяет его по тому же биту. Каждая непустая часть с числом узлов не более 6 переводится обратно в цепочку; большая часть сохраняется или перестраивается как дерево. Обычное удаление использует другой алгоритм: [removeTreeNode](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L2189-L2225) учитывает форму дерева и параметр `movable`, а не просто проверяет число узлов на равенство шести. Порог 6 нельзя переносить на все удаления.

### Почему сбалансированное дерево не гарантирует логарифмический поиск

В [TreeNode.find](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L2017-L2042) поиск сравнивает сохранённый хеш и хеш запроса, затем проверяет идентичность ссылок или `equals`. Если хеши различны, выбирается одна ветвь. Если они совпадают, совпадение по равенству не найдено и обе ветви существуют, используется пригодное сравнение `Comparable`, если оно даёт ненулевое направление. Иначе метод рекурсивно ищет в правом поддереве, при неуспехе продолжает в левом.

Рассмотрим ключи с неизменяемым целочисленным идентификатором, одинаковым хешем 67 и равенством по идентификатору. Класс не реализует `Comparable`.

```java
record CollisionKey(int id) {
    @Override public int hashCode() { return 67; }
}
var map = new HashMap<CollisionKey, Integer>(128);
for (int i = 0; i < 67; i++) {
    map.put(new CollisionKey(i), i);
}
System.out.println(map.get(new CollisionKey(66))); // 66
System.out.println(map.get(new CollisionKey(-1))); // null
```

У нового отсутствующего ключа нет равного узла, все хеши одинаковы и сравнение не даёт направления. Представьте корень с двумя непустыми поддеревьями: проверив корень, поиск должен проверить правое поддерево, а при неуспехе — левое. Такое решение повторяется на каждом уровне. Даже если высота сбалансированного дерева порядка `log m`, число посещённых узлов может достигать порядка `m`, где `m` — число узлов этой корзины. Это линейная стоимость поиска в худшем случае даже при постоянной цене `hashCode` и `equals`. Дополнительное правило выбора стороны при **вставке** (tie-break) не даёт пригодного порядка поиска по равенству: новый равный объект не обязан иметь ту же идентичность, что ранее сохранённый. При различимых хешах или пригодном сравнении, позволяющем выбирать одну ветвь, высота дерева действительно помогает сократить поиск.

В [практическом пакете C1](../../examples/collections/contracts-hash/README.md) обычный запуск проверяет только размер и результаты поиска равного и отсутствующего ключей. Режим `--observe-collisions` отдельно считает вызовы `equals` отсутствующего ключа. По отчёту 03 на Java 21.0.12.1 при начальной вместимости 128 и 16/32/67/128 ключах получены 17/33/68/129 вызовов; [независимый аудит §6.2](../../docs/audits/COLLECTIONS_FINAL_COVERAGE_2026-11-24.md) получил те же числа при начальной вместимости 256. Это два атрибутированных наблюдения конкретной реализации, не нормативное число сравнений, не доказательство формы дерева и не измерение времени. Возможность линейного обхода следует из алгоритма `find`, а не из четырёх значений счётчика. Отдельный фрагмент с record выше автором не запускался.

## Асимптотика с условиями (CH-07)

| Операция | Оценка и условия |
|---|---|
| `get`, `put`, `remove` | Ожидаемая близкая к O(1) стоимость при хорошем распределении и дешёвых `hashCode`/`equals`; не строгая граница худшего случая |
| Одна вставка с ростом таблицы | Перенос узлов и обход прежней таблицы; амортизация не ограничивает задержку отдельного вызова |
| Обход `HashMap` | O(capacity + size) по Javadoc |
| Операции `HashSet` | Ожидаемая постоянная стоимость при хорошем распределении хешей |
| Поиск в древовидной корзине OpenJDK 21 | O(log m) при выборе одной ветви и дешёвых сравнениях; O(m) в описанном случае одинаковых хешей без пригодного порядка |

Стоимость пользовательских методов и расширения таблицы учитывается отдельно. Размеры `Node`/`TreeNode` в байтах зависят от JVM и архитектуры; не делайте универсальных выводов о задержках и памяти без измерений. Методика — в [COL-TRADEOFFS](tradeoffs.md).

**Уточнения на собеседовании.** Почему удвоение не требует повторного хеширования ключей? Потому что сохранённый хеш уже есть, и новый индекс отличается только одним битом маски. Почему девятый ключ может не создать дерево? При небольшой таблице попытка преобразования приводит к росту; равный ключ вообще не добавляется. Почему сбалансированность дерева не спасает при всех одинаковых хешах? Она ограничивает длину пути, но без направления поиска приходится посещать обе ветви.

## Замена, null и callback-операции (CH-08, CH-14)

`put(k,v)` возвращает прежнее значение либо `null`; по этому результату нельзя отличить отсутствие ключа от прежнего отображения на `null`. `putIfAbsent(k,v)` записывает значение, когда ключ отсутствует или сопоставлен с `null`. `computeIfAbsent(k,f)` вызывает функцию вычисления значения в этих же случаях; если она вернёт `null`, новая запись не создаётся, а уже существующее отображение на `null` остаётся. `merge(k,value,remappingFunction)` требует **ненулевой аргумент `value`**: если ключ отсутствует или сопоставлен с `null`, записывает его непосредственно; иначе вызывает функцию объединения старого и нового значений. Если она возвращает `null`, запись удаляется.

```java
Map<String, Integer> m = new HashMap<>();
m.put("a", null);
System.out.println(m.computeIfAbsent("a", k -> 67)); // 67
System.out.println(m.computeIfAbsent("b", k -> null)); // null
System.out.println(m.containsKey("b"));                // false
System.out.println(m.merge("a", 1, Integer::sum));      // 68
System.out.println(m.merge("a", 1, (oldV, newV) -> null)); // null
System.out.println(m.containsKey("a"));                // false
```

Вычисляющая функция, переданная в `computeIfAbsent` или `merge`, **не должна изменять ту же карту в ходе вычисления** — запрет нельзя сводить только к добавлению или удалению ключей. Для операций `HashMap` предусмотрено обнаружение некоторых таких изменений с выбросом `ConcurrentModificationException` **по возможности**, без гарантии обнаружения каждого случая. Если функция бросает исключение, оно передаётся вызывающему коду; побочные эффекты функции вне карты не откатываются автоматически. Даже когда документация описывает сохранение сопоставлений при исключении, это **не общая транзакция** и не разрешение изменять карту внутри функции. Точные условия определяются Javadoc конкретного метода Java 21.

## Thread safety и fail-fast (CH-09, CH-11)

`HashMap` **не синхронизирована**. Если несколько потоков обращаются к ней и хотя бы один изменяет структуру, требуется внешняя синхронизация или подходящая конкурентная структура. `map.containsKey(k)` с последующим `put(k,v)` не становится атомарным действием от того, что каждый метод вызывается последовательно в одном потоке. Реализации `compute/merge`, предоставленные по умолчанию интерфейсом `Map`, **не гарантируют атомарности при конкурентном выполнении**; нельзя переносить свойства `ConcurrentHashMap.compute` на `HashMap`. Многоключевая атомарность также не следует автоматически из атомарности операций по одному ключу. Подробнее — [COL-CONCURRENT](concurrent.md); полный JMM остаётся темой `CON-JMM`.

Итераторы `HashMap` являются fail-fast по возможности: при обнаружении неподдерживаемых структурных изменений после создания итератора они могут бросить `ConcurrentModificationException`. **Обнаружение выполняется по возможности, а не гарантированно при каждой гонке; это не механизм потокобезопасности.** Замена значения уже существующего ключа в OpenJDK `HashMap` не добавляет и не удаляет сопоставление ключа со значением; однако нельзя обобщать детали `modCount` на все реализации `Map`.

## Сопоставление альтернатив (CH-13)

| Реализация | Отличительная особенность |
|---|---|
| `HashMap` | нет гарантий порядка, разрешает `null` |
| `LinkedHashMap` | определён encounter order, доступен `SequencedMap` |
| `TreeMap` | сортированный по ключам порядок; равенство ключей определяется сравнением, что требует аккуратности |
| `Hashtable` | исторический synchronized-класс; запрещает `null`-ключи и значения |
| `IdentityHashMap` | сравнивает ключи по `==`, а не `equals`; специальная семантика |
| `ConcurrentHashMap` | конкурентные операции, без `null`-ключей/значений; подробности в [COL-CONCURRENT](concurrent.md) |

Сравнение не означает, что все операции и граничные случаи этих реализаций эквивалентны. Изучать `TreeMap` и конкурентные варианты следует по отдельному нормативному контракту.

## Специальные границы (CH-16)

`HashMap` поддерживает сериализацию и клонирование в рамках своей документации, но эти механизмы не дают переносимой гарантии порядка обхода после восстановления, `resize` или обновления версии JDK. Ни текущее содержимое бакетов, ни детали расположения узлов не должны становиться частью бизнес-логики.

## Проверка понимания

1. Почему два ключа с одинаковым `hashCode` могут жить в одной карте и как выбирается значение при `get`?
2. Почему изменение ключа после `put` способно сделать запись недоступной, хотя `size` не уменьшился?
3. Когда `get` возвращает `null`, что проверяет `containsKey`?
4. Почему нельзя считать обход `HashMap` гарантированным O(size), а каждый `put` — строгим O(1)?
5. Почему 8/6/64 относятся к OpenJDK 21, а не к интерфейсу `Map`?
6. Чем `computeIfAbsent` и `merge` отличаются при null, и почему это не доказательство атомарности между потоками?
