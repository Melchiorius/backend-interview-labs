# CORE-COMPOSITION — композиция, делегирование и выбор между контрактами в Java 21

**Java SE 21 · Issue [#70](https://github.com/Melchiorius/backend-interview-labs/issues/70).** Основа: [G1-план CORE-INTERFACES-COMPOSITION](../../docs/plans/CORE-INTERFACES-COMPOSITION.md), принятый 00 в [Issue #64](https://github.com/Melchiorius/backend-interview-labs/issues/64#issuecomment-7049387322). Эта статья — **архитектурные последствия и работающий код**, а не перечень нормативных правил разрешения default: для этих правил есть [CORE-INTERFACES](interfaces.md).

## Проблема, которую не решает одно наследование

Предположим, сервис получает число 67 и должен обработать его по выбранной политике. Сегодня политика прибавляет единицу, завтра умножает на два, для отдельного клиента требуется журналирование или дополнительное ограничение. Прямое наследование от конкретной реализации вынудило бы сервис унаследовать больше, чем ему нужно: чужое поведение, иногда состояние и зависимости, а также обязательства поддерживать семантику суперкласса. При добавлении нескольких независимых вариантов дерево наследования может перестать выражать реальные сочетания.

**Композиция** означает, что один объект **хранит ссылки на другие объекты** и использует их для выполнения своей работы. **Делегирование** — более конкретная операция: объект передаёт часть выполнения другому объекту (делегату). Здесь «композиция объектов» используется в широком смысле, включая общие и заимствованные зависимости. В более узкой UML-композиции (composite aggregation) часть в каждый момент принадлежит не более чем одному составному объекту (см. [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/)). HAS-A и наличие поля сами по себе не доказывают исключительного владения. Java GC и явное закрытие ресурса не следуют из UML-отношения. Это не отдельная конструкция синтаксиса Java; компилятор видит поля, конструкторы, вызовы методов и интерфейсные типы.

Связанный вопрос не «композиция или наследование всегда лучше», а **какой публичный контракт должен зависеть от какого**, кто владеет объектами, кто отвечает за результат и какие изменения ожидаются. Архитектурные критерии вроде IS-A/HAS-A и принципа подстановки Лисков (LSP) — рекомендации, **не** проверки, выполняемые `javac`.

## Центральный пример: Strategy + constructor injection + Decorator

Ниже один **самодостаточный диагностический пример** в файле `CompositionWalkthrough.java`. Он нужен для последовательного разбора архитектуры без отдельного Gradle-модуля. Для сопоставления предусмотрен [общий многофайловый запускаемый пример для двух статей](../../examples/core/interfaces-composition/README.md). Его пакеты, имена классов и stdout **отличаются** от независимого inline-примера; это два разных набора исходников, а не два запуска одного файла.

```java
import java.util.Objects;

public final class CompositionWalkthrough {
    private CompositionWalkthrough() {}

    interface Policy {
        int apply(int input);
    }

    static final class AddOne implements Policy {
        @Override public int apply(int input) {
            return input + 1;
        }
    }

    static final class DoubleIt implements Policy {
        @Override public int apply(int input) {
            return input * 2;
        }
    }

    static final class AddTenDecorator implements Policy {
        private final Policy delegate;

        AddTenDecorator(Policy delegate) {
            this.delegate = Objects.requireNonNull(delegate);
        }

        @Override public int apply(int input) {
            return delegate.apply(input) + 10;
        }
    }

    static final class Service {
        private final Policy policy;

        Service(Policy policy) {
            this.policy = Objects.requireNonNull(policy, "policy");
        }

        int execute(int input) {
            return policy.apply(input);
        }
    }

    static final class RecordingPolicyFake implements Policy {
        int lastInput = -1;
        int calls;

        @Override public int apply(int input) {
            calls++;
            lastInput = input;
            return 900;
        }
    }

    public static void main(String[] args) {
        System.out.println("add=" + new Service(new AddOne()).execute(67));
        System.out.println("double=" + new Service(new DoubleIt()).execute(67));
        System.out.println("decorated=" +
                new Service(new AddTenDecorator(new AddOne())).execute(67));

        RecordingPolicyFake fake = new RecordingPolicyFake();
        int result = new Service(fake).execute(67);
        System.out.println("fake=" + result);
        System.out.println("observed=" + fake.lastInput + ",calls=" + fake.calls);
        if (result != 900 || fake.lastInput != 67 || fake.calls != 1) {
            throw new AssertionError("forwarding failed");
        }

        try {
            new Service(null);
            throw new AssertionError("null dependency accepted");
        } catch (NullPointerException ex) {
            if (!"policy".equals(ex.getMessage())) throw new AssertionError(ex);
            System.out.println("guard=" + ex.getMessage());
        }

        try {
            new Service(new AddTenDecorator(n -> {
                throw new IllegalStateException("rejected:" + n);
            })).execute(67);
            throw new AssertionError("exception swallowed");
        } catch (IllegalStateException ex) {
            if (!"rejected:67".equals(ex.getMessage())) throw new AssertionError(ex);
            System.out.println("failure=" + ex.getMessage());
        }

        System.out.println("CHECK PASSED");
    }
}
```

Команды с JDK 21 из каталога файла:

```sh
javac --release 21 CompositionWalkthrough.java
java CompositionWalkthrough
```

Полный ожидаемый stdout:

```text
add=68
double=134
decorated=78
fake=900
observed=67,calls=1
guard=policy
failure=rejected:67
CHECK PASSED
```

### Пошаговое объяснение

**1. Контракт задаётся как `Policy.apply(int)`.** Это публичная операция, а не готовая реализация расчёта. Два класса `AddOne` и `DoubleIt` реализуют одну сигнатуру, хотя делают разные вещи. Java-проверка интерфейсного контракта описана в [CORE-INTERFACES](interfaces.md); сама по себе эта проверка ещё не доказывает поведенческую взаимозаменяемость.

**2. `Service` содержит `Policy`, но не наследуется от `AddOne`.** Поле `private final Policy policy` создаёт явную связь *HAS-A*: сервис **имеет** объект политики. Тело `execute(int)` только передаёт аргумент в `policy.apply(input)`. Такой вызов и называется делегированием. По статическому типу `Policy` компилятор проверяет допустимость вызова, а во время выполнения виртуальный вызов выбирает реализацию фактического объекта.

**3. Две строки `add=68` и `double=134`.** Клиент создаёт два объекта `Service`, передав каждому свою реализацию. Исходник класса `Service` для этого не изменяется. На входе 67 одна политика прибавляет 1, другая умножает на 2. Важно: зависимость выбрана **при построении конкретного объекта**, а не переключается магически во всех существующих сервисах.

**4. Строка `decorated=78`.** `AddTenDecorator` сам реализует `Policy`, но хранит другую `Policy`. Он сначала вызывает `delegate.apply(67)` — результат `68` от `AddOne` — и затем прибавляет 10. Декоратор заменим **по типу** на любую политику. Если при этом договор требует, например, «проверка не должна увеличивать значение», такой декоратор уже может нарушить **поведенческий** контракт, несмотря на успешную компиляцию.

**5. Строки `fake=900` и `observed=67,calls=1`.** Вместо настоящей политики передан ручной **тестовый двойник** `RecordingPolicyFake`. Он возвращает заранее заданное число и записывает вход/количество вызовов. Отдельно проверяются возвращённое значение 900, переданный аргумент 67 и ровно один вызов зависимости. Двойник одновременно выполняет роль stub (заданный ответ) и записывает обращения; название fake здесь учебное и не обязано совпадать со строгой классификацией test doubles.

**6. Строка `guard=policy`.** В конструкторе используется `Objects.requireNonNull(policy, "policy")`. Поэтому пустая зависимость отвергается сразу, а не приводит позже к неясной ошибке в `execute()`. Это контракт стандартного [Java SE 21 Objects.requireNonNull](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Objects.html#requireNonNull(java.lang.Object,java.lang.String)), но не часть языкового синтаксиса constructor injection.

**7. Строка `failure=rejected:67`.** Политика-лямбда выбрасывает `IllegalStateException`. `AddTenDecorator` и `Service` не перехватывают исключение, поэтому оно распространяется до внешнего `catch`. Это демонстрирует конкретную политику **прозрачной передачи исключений**, но не общую гарантию для любого декоратора: обёртка может подавлять, оборачивать, повторять или преобразовывать ошибки — и должна явно отвечать за смысл таких изменений.

**8. `CHECK PASSED`.** Маркер означает, что явные проверки результата, аргумента, числа вызовов и обеих отрицательных ветвей не вызвали AssertionError в этом сценарии. Отсутствие ожидаемого исключения теперь само считается ошибкой; проверяется также сообщение. Сохранённый stdout дополнительно можно сравнить целиком. Она не доказывает корректность всех политик, отсутствие data races, полную LSP-подстановку или производительность.

## Почему это Strategy, а не только вызов поля

Условный алгоритм «сделать расчёт» меняется за счёт объекта, реализующего один контракт. Это **Strategy**: точка изменения поведения вынесена в отдельные взаимозаменяемые по типу алгоритмы. `Service` зависит от интерфейса, а клиент принимает решение, какой объект передать в конструктор.

Вместо:

```java
class Service {
    int execute(int input, boolean doubleIt) {
        return doubleIt ? input * 2 : input + 1;
    }
}
```

мы передаём поведение через `Policy`. В первом варианте при добавлении каждого нового вида политики растёт ветвление внутри сервиса. Во втором меняются реализации, но добавляется ответственность за организацию зависимостей. Для **двух навсегда фиксированных действий** простой условный оператор иногда понятнее. Strategy оправдана не названием паттерна, а реально независимой эволюцией политик и требованиями проверяемости.

## Constructor injection: что гарантируется, а что нет

В классе `Service` обязательная зависимость передана через конструктор. Это делает состояние «без Policy» явным недопустимым случаем и позволяет создать сервис с выбранной реализацией до первого запроса.

Однако из того, что поле `final`, **не следует**, что:

- реализация `Policy` неизменяема или потокобезопасна;
- объект `Policy` больше никем не используется или не модифицируется;
- разные реализации соблюдают одинаковое смысловое поведение;
- весь `Service` безопасно опубликован в других потоках;
- внедряемый объект будет автоматически закрыт при завершении использования.

`final` не позволяет присвоить другую ссылку в поле после конструирования, но не замораживает состояние объекта, на который она указывает. Тонкие гарантии final-field semantics и безопасной публикации относятся к JMM ([JLS 21 §17.5](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html#jls-17.5)), а не к самому слову «инъекция». В реальных системах нужно явно определить владение, срок жизни и синхронизацию. Отличие final-ссылки от неизменяемости самого объекта подробно разобрано в [CORE-IMMUTABLE](immutability.md).

**Constructor injection** — лишь одна техника; зависимости также могут создаваться фабрикой, передаваться аргументом метода или назначаться иным способом. Java не требует использовать Spring или контейнер. И напротив, наличие Spring не заменяет проектного решения о том, кто отвечает за жизненный цикл ресурса.

## Делегирование — не то же самое, что наследование, и за него приходится платить

При наследовании конкретного класса новый класс автоматически получает допустимые унаследованные члены и обязательства родительского типа. При композиции вызывающий код не может внезапно использовать произвольный метод вложенного объекта через внешний класс. Наружу доступны **только те операции**, которые явно выставлены публичным API владельца. Если wrapper реализует интерфейс, он должен осмысленно выполнить все его обязательные методы.

Например, у API появляется вторая операция:

```java
interface Policy {
    int apply(int input);
    String description();
}
```

Прежние классы-реализаторы должны реализовать `description()` или соответствующим образом изменить контракт. Вариант с `default String description() { ... }` уменьшит число обязательных реализаций, но **не гарантирует**, что поведение существующих реализаций станет корректным или не возникнет конфликт с другим интерфейсом. Подробно о конфликтах — [CORE-INTERFACES](interfaces.md); бинарная/исходная совместимость при эволюции API — отдельная граница IC-28.

Если `DecoratedPolicy` возвращает описание собственной операции, он должен решить, показывать ли `delegate.description()`, добавлять ли информацию о себе, скрывать ли детали реализации или вообще менять формат. Это **стоимость явной передачи вызовов** (*forwarding burden*), а не ошибка компилятора.

В общем многофайловом примере это различие видно на `Policy.describe(int)`: default вызывает `apply` на **том объекте**, которому отправили describe. Если делегат переопределил describe, а IncrementingDecorator реализует только apply, то у обёртки остаётся default, который не вызывает переопределённый describe делегата. Например, делегат с apply(n) = n и собственным describe(67) = "custom" вернёт "custom" при прямом вызове; для обёртки, прибавляющей единицу, унаследованный default вычислит через её apply строку `input=67 -> output=68`. Это намеренный пересчёт описания результата обёртки. Явное `return delegate.describe(input);` сохранило бы пользовательское описание, но могло бы скрыть добавленную операцию. Выбирать следует по смыслу каждой операции, а не механически перенаправлять все методы.

### Decorator отличается от просто хранимой зависимости

В центральном примере `Service` содержит `Policy`, но **сам не является Policy**. Он представляет собой потребителя (*client*) политики. `AddTenDecorator` также хранит `Policy`, но при этом **сам реализует Policy**: клиент может передать его в любое место, ожидающее этот интерфейс.

Декоратор оборачивает другую реализацию и добавляет поведение, сохраняя интерфейсный тип. Это не означает, что любая обёртка незаметна для её клиентов. Например:

- клиент, сравнивающий конкретные классы через `getClass()`, увидит другую обёртку;
- идентичность при сравнении через `==` не сохранится: обёртка — новый объект;
- `equals/hashCode/toString` по умолчанию принадлежат самой обёртке, даже если она делегирует предметные методы;
- ответственность за обработку исключений, блокировки, транзакции и повторные вызовы должна быть определена явно;
- вложенные декораторы могут изменить семантику и порядок побочных эффектов: `Audit(Guard(policy))` не всегда эквивалентен `Guard(Audit(policy))`.

Порядок декораторов становится частью внешнего поведения, когда они не коммутируют: если одна обёртка добавляет 10, а вторая удваивает результат, то для исходной тождественной политики и входа 67 получатся соответственно (67 × 2) + 10 = 144 и (67 + 10) × 2 = 154. Это важнее запоминания UML-картинки. Общий контракт Object и идентичности — [CORE-OBJECT](object.md), а контракт равенства — [CORE-EQUALITY](equality.md).

### Арифметический контракт — тоже часть поведения

В самостоятельном CompositionWalkthrough операции + и * над int допускают переполнение с усечением до 32 бит: AddOne для Integer.MAX_VALUE возвращает Integer.MIN_VALUE. В общем многофайловом примере AddTenPolicy, DoublePolicy и IncrementingDecorator используют Math.addExact/Math.multiplyExact: при выходе математического результата за диапазон int возникает ArithmeticException. Декоратор может получить исключение как от делегата, так и от собственной операции; если не перехватывает его, оно доходит до клиента.

~~~java
class WrapDemo { public static void main(String[] args){int n=Integer.MAX_VALUE;System.out.println(n+1);try{Math.addExact(n,1);throw new AssertionError();}catch(ArithmeticException expected){System.out.println("overflow");}} }
~~~

В отдельном файле WrapDemo.java команды `javac --release 21 WrapDemo.java`, `java WrapDemo` дают ожидаемые строки `-2147483648`, `overflow`. Это два различных контракта, а не универсальная гарантия exact-арифметики для произвольного входа. Подробнее: [CORE-TYPES](types.md), [CORE-CONVERSIONS](conversions.md), [CORE-NUMBERS](numbers.md), [Java 21 Math](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Math.html).

## Кто владеет внедрённой зависимостью и когда её закрывать

С точки зрения сборщика мусора владелец поля хранит ссылку; это **не** автоматически означает логическое *ownership*. Рассмотрим объект политики, который использует файловый дескриптор или HTTP-клиент.

Возможны разные контракты:

1. **Borrowed dependency:** клиент создал Policy и передал её нескольким Service. Сервис не должен закрывать общий ресурс при каждом завершении своей работы, иначе сломает других пользователей.
2. **Owned dependency:** Service или специально объявленный ресурсный агрегат создал policy и договорился быть единственным ответственным за закрытие.
3. **Shared managed lifecycle:** внешняя фабрика/контейнер управляет сроком жизни; сервис ничего не закрывает сам, если контракт не предусматривает обратного.

Java не выводит эти обязанности из слова `final` или `private`. О закрытии ресурсов и `AutoCloseable` см. [CORE-RESOURCES](resources.md). Нужна явная документация или тип/операция, например `AutoCloseable` с определённым владельцем. Даже если decorator реализует `AutoCloseable`, нельзя слепо закрывать delegate: он может быть общим.

Обратная цена внедрения — **передача ответственности наружу**: кто собирает объектный граф, выбирает реализации, проверяет конфигурацию и контролирует порядок запуска/остановки. Dependency injection делает зависимости видимыми, но не создаёт автоматически рабочую политику управления ресурсами.

## IS-A, HAS-A и LSP — вопросы о поведении, не о синтаксисе

Фраза **IS-A** полезна, когда объект должен действительно выполнять контракт суперкласса во всех значимых для клиента ситуациях. **HAS-A** полезна, когда объект использует чужую ответственность. Однако оба выражения — только стартовые эвристики:

- `class FasterPolicy extends SlowPolicy` может компилироваться и всё же нарушать предусловия, постусловия или исключения контракта SlowPolicy.
- `Service` может содержать `Policy`, но вызывать её дважды вместо одного или неправильно обрабатывать исключения. Композиция не мешает такой ошибке.
- `AddTenDecorator` реализует `Policy`, то есть формально подставляется по типу. Но если семантический договор гласит «apply возвращает число без дополнительной надбавки», этот декоратор нарушит договор, даже если Java не выдаст ни одной ошибки.

**LSP (принцип подстановки Лисков)** здесь критерий: может ли клиент опираться на обещания типа, не зная, какая конкретная реализация ему передана? Компилятор гарантирует, например, тип результата и допустимость checked throws, но **не** проверяет отсутствие вредных побочных эффектов, бизнес-лимиты, производительность, сетевую доступность и устойчивость к изменениям состояния.

Например, клиенту обещано: для каждого неотрицательного int метод apply завершится нормально и вернёт неотрицательный int. Реализация `n -> n` удовлетворяет этому договору. Реализация, которая выбрасывает IllegalArgumentException при n == 0, уже требует более сильного предусловия (n > 0), хотя типовая сигнатура та же. Другая реализация, возвращающая -1 при n == 0, ослабляет постусловие. Клиент, передающий допустимый 0, соответственно получит ошибку либо недопустимый результат.

~~~java
class ContractDemo { interface Policy { int apply(int n); } static int client(Policy p){int r=p.apply(0);if(r<0)throw new AssertionError();return r;} public static void main(String[] args){System.out.println(client(n->n));try{client(n->{if(n==0)throw new IllegalArgumentException();return n;});throw new AssertionError();}catch(IllegalArgumentException expected){System.out.println("contract violated");}} }
~~~

Отдельно сохраните ContractDemo.java: `javac --release 21 ContractDemo.java`, `java ContractDemo` — ожидается `0`, затем `contract violated`. В этом клиентском сценарии второе поведение нарушает договор. Это проверка конкретного входа, не доказательство поведения на всех входах. При подстановке реализации нельзя усиливать требования к клиенту или ослаблять обещанные ему результаты; нужно сохранять также значимые инварианты и ограничения на изменение состояния. Это проектное требование, не дополнительное правило Java. Теоретическая основа — [B. Liskov, J. Wing, A Behavioral Notion of Subtyping (1994)](https://doi.org/10.1145/197320.197383).

Перед выбором спросите: какое поведение клиент вправе ожидать, можно ли заменить стратегию без изменения этих обещаний, нужен ли общий state/constructor/template, сколько комбинаций поведения реально существуют, кто будет их тестировать?

## Интерфейсно-ориентированный дизайн не означает обязательное «всё через интерфейс»

Решение вводить отдельный интерфейс оправдано наличием **реальной границы изменения**, нескольких реализаций, устойчивого публичного контракта или явной потребности подменять зависимость. Интерфейс с одним классом на каждый метод только ради абстракции может создать лишнюю навигацию и усложнить отладку. С другой стороны, интерфейс может быть полезен даже при одной сегодняшней реализации, если он выражает независимый контракт между компонентами и должен существовать долго.

Сравним стратегии выбора:

| Требование | Наследование / abstract class | Композиция / interface + delegate | Цена |
|---|---|---|---|
| Нужна единая реализация с общим защищённым состоянием и инвариантами | Часто разумно: base state + protected/template steps | Возможна, но общий state приходится распределять по объектам | Тесная связь subclass с superclass |
| Независимые политики часто меняются | Подклассы могут множиться и конфликтовать по ответственности | Service хранит Policy, реализации меняются независимо | Настройка object graph; forwarding |
| Несколько независимых «надстроек» поведения | Жёсткие комбинации подклассов громоздки | Несколько decorators могут быть вложены | Порядок wrappers, identity, exceptions |
| Нужна простая реализация без долгоживущего расширения | Обычный конкретный класс может быть проще | Абстракция может оказаться избыточной | Когнитивная стоимость интерфейса |
| Важно контролировать lifecycle ресурсов | Конструктор суперкласса может централизовать часть правил | Владение каждым delegate должно быть определено | Закрытие и sharing ресурсов |
| Требуются несколько интерфейсных ролей при одном экземпляре | Класс может реализовать несколько interfaces | Композиция может разделить обязанности по объектам | Выбор границ контракта и обязанностей |

**Вывод:** ни одна колонка не является «победителем» для всех систем. Уместность определяется характером изменений и конкретным контрактом. Наличие интерфейса **не** доказывает слабую связанность, а применение наследования **не** означает ошибку дизайна.

## Проверяемость без Mockito: не путать fake с доказательством корректности

В примере `RecordingPolicyFake` — вручную написанная реализация интерфейса, которая возвращает контролируемое значение и фиксирует факт вызова. Это позволяет проверить **взаимодействие Service с зависимостью** без фреймворков, сети и базы данных. Если бы мы возвращали только фиксированное число и не записывали обращения, двойник в этой проверке играл бы чистую роль stub.

Сама запись `lastInput/calls` **не потокобезопасна**. Для данного последовательного сценария это достаточно; при многопоточном тесте нужны другие средства. И даже проверка `calls == 1` ничего не говорит о поведении настоящей политики при ошибках, больших числах или гонках — дополнительные tests должны быть обоснованы именно её контрактом.

Чтобы проверять и возвращаемое значение, и взаимодействие, в main сохраняется result от единственного вызова execute, затем выполняется явная проверка:

```java
if (result != 900 || fake.lastInput != 67 || fake.calls != 1) {
    throw new AssertionError("forwarding failed");
}
```

Утверждение относится к **локальным переменным result и fake внутри main**, а не является самостоятельным классом для запуска. При ошибке проверка прервёт выполнение; строка `CHECK PASSED` не появится. В JUnit тот же контракт можно выразить обычными asserts; Mockito для него необязателен. Встречное правило: наличие легко внедряемой зависимости само по себе ещё не означает хорошего тестового покрытия.

## Исключения, инварианты и корректность forwarding

У простой композиции с `delegate.apply(input)` исключение естественным образом распространяется дальше. Но при добавлении кэша, ретраев, timeout или fallback wrapper уже меняет наблюдаемую клиентом семантику:

- повторный вызов может повторить денежную транзакцию;
- fallback может скрыть важную ошибку;
- кэш должен решить, какие ошибки кешировать и когда инвалидировать результат;
- сравнение результата до/после decorator может перестать удовлетворять инвариантам клиента.

Не рекомендуется объявлять wrapper «прозрачным», пока не проверены контракт результата, ошибки, побочные эффекты, идентичность и жизненный цикл. Эта проверка нужна даже при идеальной совместимости Java-сигнатур.

## Откуда берётся стоимость производительности

Дополнительный объект и уровень вызова могут влиять на размещение в памяти, профилирование и динамическую диспетчеризацию, но **из одного дополнительного Java-вызова нельзя вывести универсальную потерю производительности**. JVM может встроить вызов, оптимизировать распределение объектов или не сделать этого — исход зависит от workload и реализации. Если производительность действительно ограничивает выбор, требуется профиль реального сценария и воспроизводимый benchmark; в данной статье таких измерений нет.

У наследования тоже есть стоимость: ограничения изменения класса, зависимость от внутренней реализации суперкласса, хрупкость переопределяемых template hooks и возможные побочные эффекты вызовов во время конструирования (см. [CORE-INIT](initialization.md)). Нельзя оценивать только скорость прямого вызова и игнорировать стоимость изменения архитектуры.

## Интегрированный общий пример: те же границы на уровне пакетов

[README и 10-строчный stdout](../../examples/core/interfaces-composition/README.md) · [Policy.java](../../examples/core/interfaces-composition/src/api/Policy.java) · [Service.java](../../examples/core/interfaces-composition/src/client/Service.java) · [IncrementingDecorator.java](../../examples/core/interfaces-composition/src/impl/IncrementingDecorator.java).

У общего runnable роли 03 другие конкретные имена и операции, чем у `CompositionWalkthrough` выше. Зафиксируем разницу, чтобы не смешивать два вывода:

| Деталь | Inline CompositionWalkthrough | Общий multi-file runnable |
|---|---|---|
| Реализации политики | `AddOne` и `DoubleIt` | `impl.AddTenPolicy` и `impl.DoublePolicy` |
| Декоратор | `AddTenDecorator` добавляет 10 | `impl.IncrementingDecorator` добавляет 1 |
| Сервис | вложенный `Service.execute` | `client.Service.execute/explain` |
| Проверка инъекции | `Objects.requireNonNull(policy, "policy")` | То же в отдельном классе client.Service |
| Контракт интерфейса | Одна abstract операция | `api.Policy.apply` + default `describe` + private formatter |
| Арифметика | Обычные int + и * (переполнение без исключения) | Math.addExact/multiplyExact (ArithmeticException при переполнении) |
| Демонстрация тестирования | Ручной recording fake и случай исключения | Вывод 10 строк и явные проверки в точке входа; точные проверяемые условия и команды — в README общего примера |

Для общего проекта вход равен 67: `AddTenPolicy` возвращает 77, `DoublePolicy` возвращает 134, `IncrementingDecorator(DoublePolicy)` — 135. Вызов `Service.explain(67)` попадает в default `Policy.describe`, который по своему телу вызывает `apply(67)` и форматирует `input=67 -> output=77`. Проверка форматированной строки сама по себе не доказывает число вызовов apply: для этого нужен делегат с наблюдаемым счётчиком. Null dependency отбрасывается через `Objects.requireNonNull`. В конце сценарий разрешает независимый default/default как `left|right` и показывает class precedence как `class` — эти правила подробно описаны в [CORE-INTERFACES](interfaces.md).

