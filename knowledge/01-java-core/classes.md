# CORE-CLASSES — классы, объекты, поля, методы и конструкторы

**Java 21 · предпосылки:** [типы и ссылки](types.md), [передача аргументов](parameters.md).

## Класс и объект — не одно и то же

**Класс** описывает тип объектов: какие данные они хранят (**поля**), какие действия поддерживают (**методы**) и как создаются в корректном состоянии (**конструкторы**). **Объект** в Java — экземпляр класса или массив ([JLS §4.3.1](https://docs.oracle.com/javase/specs/jls/se21/html/jls-4.html#jls-4.3.1)). Здесь прежде всего рассматриваются экземпляры классов; массив, даже `int[]`, тоже объект, см. [CORE-ARRAYS](arrays.md).

Допустим, система учитывает условные кредиты пользователей. Два счёта подчиняются одним правилам, но остаток у каждого свой.

```java
CreditAccount first = new CreditAccount("А", 67);
CreditAccount second = new CreditAccount("Б", 10);
CreditAccount alias = first;

System.out.println(first == second); // false — два экземпляра
System.out.println(alias == first);  // true — ссылки на один объект
```

Два выражения `new CreditAccount(...)` создают два экземпляра; при нормальном завершении результат каждого выражения — значение ссылки на новый объект, а не сам объект в переменной. Переменная `alias` получает **копию ссылки**, а не копию объекта. Поэтому изменение объекта через `alias` будет видно и через `first`. Полная модель переменных и ссылок уже раскрыта в [CORE-TYPES](types.md).

**Важно:** фрагменты кода ниже независимы; объявления типов и методов размещаются в подходящем классе/файле, выполняемые строки — в методе. Отрицательные варианты закомментированы. Самостоятельную демонстрацию основных механизмов, не всех контрпримеров, см. в [ClassesAndObjectsDemo.java](../../examples/core/ClassesAndObjectsDemo.java).

## Поля, методы и состояние экземпляра

Рассмотрим класс со строго положительными пополнениями и запрещённым перерасходом. Для простоты суммы считаются **условными целыми кредитами**, а не деньгами.

```java
class CreditAccount {
    private final String owner;
    private long balance;

    CreditAccount(String owner, long openingBalance) {
        if (owner == null || owner.isBlank()) {
            throw new IllegalArgumentException("Имя владельца обязательно");
        }
        if (openingBalance < 0) {
            throw new IllegalArgumentException("Отрицательный остаток");
        }
        this.owner = owner;
        this.balance = openingBalance;
    }

    long balance() {
        return balance;
    }

    void deposit(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Сумма должна быть положительной");
        }
        balance = Math.addExact(balance, amount);
    }

    void withdraw(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Сумма должна быть положительной");
        }
        if (amount > balance) {
            throw new IllegalStateException("Недостаточно кредитов");
        }
        balance -= amount;
    }
}
```

**Кто выполняет действия:** вызывающий код создаёт экземпляр через конструктор. Конструктор проверяет переданные значения и заполняет поля **этого объекта**. Затем при вызове `account.deposit(10)` метод меняет поле `balance` **этого экземпляра**, а не всех счетов.

- Поле `owner` хранит владельца и объявлено `final`: после инициализации ссылку в нём нельзя переназначить.
- Поле `balance` изменяемое: операции счёта вправе менять остаток.
- Метод `balance()` возвращает значение; он сам по себе не даёт вызывающему коду право записать новое значение в поле.
- Поле `private` недоступно напрямую обычному независимому внешнему клиенту, даже из того же пакета. В пределах охватывающего верхнеуровневого объявления разрешён доступ к private-членам из вложенных типов (включая соседние вложенные классы); это не абсолютный барьер для reflection. Подробные правила `public`, `protected`, package-private и `private` разобраны в [CORE-ACCESS](access.md).

### Инвариант и зачем прятать поля

**Инвариант объекта** — условие, которое корректный объект обязан сохранять после успешного создания и завершения разрешённых операций. Для показанного `CreditAccount`: `owner != null && !owner.isBlank()` и `balance >= 0`.

Если бы внешний код мог записать `balance = -67`, класс не контролировал бы собственные правила. Поэтому проверки нужно сосредоточивать в конструкторе и изменяющих методах. Здесь `Math.addExact` дополнительно предотвращает незаметное переполнение при пополнении: если сумма не представима как `long`, исключение возникает до присваивания и остаток не меняется. Отрицательные/нулевые суммы и перерасход отклоняются до изменения поля. Эти гарантии относятся к последовательным вызовам собственных проверяющих операций после нормального завершения конструктора. Класс в статье не `final`; нельзя отсюда вывести контракт произвольного переопределённого метода наследника. Не обещаем безопасную публикацию или потокобезопасность. В самостоятельном примере класс счёта объявлен `final`.

> [!note]- Исключение из конструктора
> Если конструктор завершился исключением, выражение `new` не даёт вызывающему коду обычного результата. Это **не** означает, что JVM вообще не выделяла память или что никакие побочные эффекты не успели произойти. Действия в конструкторе и опасность преждевременной публикации `this` разобраны в [CORE-INIT](initialization.md); гарантии видимости — будущая тема `CON-JMM`.

## Экземплярные и статические члены: чей это счётчик?

Без `static` поле принадлежит **каждому объекту**. Статическое поле — **член класса**: его не нужно дублировать в каждом экземпляре.

```java
class Counter {
    private int value;
    private static int createdCount;

    Counter() {
        createdCount++;
    }

    void increment() {
        value++;
    }

    int value() {
        return value;
    }

    static int createdCount() {
        return createdCount;
    }
}

Counter first = new Counter();
Counter second = new Counter();
first.increment();

System.out.println(first.value());          // 1
System.out.println(second.value());         // 0
System.out.println(Counter.createdCount()); // 2
```

| Вопрос | Экземплярный член | Статический член |
|---|---|---|
| Кому относится? | Конкретному объекту | Классу |
| Типичный вызов | `first.increment()` | `Counter.createdCount()` |
| Есть ли неявный `this` в методе? | Да | Нет |
| Нужен ли экземпляр для доступа к члену? | Да, неявный `this` или явная ссылка | Нет; предпочтительно имя класса |

**Типичный вопрос собеседования:** почему из статического метода нельзя обратиться к обычному полю только по его имени?

```java
class Example {
    int value;

    static void wrong() {
        // value++;      // ошибка: нет текущего экземпляра
        // this.value++; // ошибка: this в static-контексте недоступен
    }

    static void correct(Example target) {
        target.value++;  // экземпляр предоставлен явно
    }
}
```

В `static`-методе нет неявного текущего объекта: обращение к экземплярному полю через `this` или одно его имя здесь недопустимо, но через явно предоставленную ссылку `target` — допустимо. Это другое правило, чем доступ к самому статическому члену, для которого экземпляр вообще не нужен. Вызов статического метода через выражение ссылочного типа возможен, но выбирается по правилам компиляции, а не виртуальной диспетчеризации по фактическому объекту. Используйте имя класса. Контраст с `null` и вычислением квалификатора — ниже, см. также [CORE-PARAMS](parameters.md).

`createdCount` здесь считает выполненные увеличения в конструкторе (при последовательных вызовах и без переполнения), а не количество ещё живых объектов: сборка мусора ничего из него не вычитает. В runnable счёта увеличение находится после проверок, поэтому отклонённые конструктором аргументы не увеличивают счётчик. `int` ограничен диапазоном и может переполниться.

> [!note]- Static и многопоточность
> Поле `static` не становится потокобезопасным. Например, `createdCount++` не является атомарным увеличением и может терять обновления при конкурентном создании объектов. Кроме того, `static` не следует без оговорок описывать как «одно поле на всю JVM»: один и тот же именованный класс может быть определён разными загрузчиками классов. Идентичность типа и определяющий загрузчик разобраны в [CORE-CLASSLOADER](classloaders.md); `CON-RACE`, `CON-JMM` и более широкая тема `JVM-LOADING` остаются отдельными.

## Конструктор: как объект получает допустимое начальное состояние

Конструктор имеет **имя класса** и **не имеет типа возвращаемого значения**, даже `void`. Это особый элемент языка, а не обычный метод:

```java
class Point {
    int x;
    int y;

    Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
}
```

Запись `void Point(int x, int y)` была бы **методом**, а не конструктором: совпадение имени с классом этому не мешает. Конструкторы **не наследуются** и **не переопределяются**, но могут иметь разные списки параметров (**перегрузка конструкторов**). В теле обычного конструктора допустим `return;` без выражения (при соблюдении остальных правил, например инициализации final-полей); `return 67;` недопустим ([JLS §14.17](https://docs.oracle.com/javase/specs/jls/se21/html/jls-14.html#jls-14.17)).

### Неявный конструктор по умолчанию ≠ любой no-args

Для обычного класса Java неявно объявляет default constructor **только если нет ни одного объявленного конструктора**. В простом верхнеуровневом классе он не имеет формальных параметров:

```java
class EmptyPoint {
    int x;
}
new EmptyPoint(); // работает: компилятор объявил default constructor

class FixedPoint {
    FixedPoint(int x) { }
}
// new FixedPoint(); // ошибка: неявного конструктора больше нет
new FixedPoint(67);
```

Если требуются и `FixedPoint()`, и `FixedPoint(int)` — оба нужно объявить самостоятельно. **Конструктор, написанный разработчиком без параметров, не называется «неявным конструктором по умолчанию»** в смысле JLS. Модификатор доступа у неявного конструктора также определяется правилами спецификации; подробности — в [CORE-ACCESS](access.md).

Добавлять no-args «на всякий случай» не всегда правильно: если для корректного состояния нужны аргументы, такой конструктор может позволить создать неполноценный объект.

### Почему неявный конструктор может не скомпилироваться

Для обычного подкласса без своего конструктора (кроме самого `Object`) подразумевается вызов `super()` с нулём фактических аргументов. Должен существовать доступный однозначно применимый конструктор родителя. Нулевое число фактических аргументов не означает нулевое число формальных параметров: varargs допускает пустой массив.

```java
class Parent { Parent(int... values) { System.out.println(values.length); } }
class Implicit extends Parent {}
class Explicit extends Parent { Explicit() {} }
new Implicit(); // 0: default constructor
new Explicit(); // 0: явно объявленный no-args, внутри неявный super()

class NeedsInt { NeedsInt(int value) {} }
// class Broken extends NeedsInt {} // ошибка: нет применимого super()
class Working extends NeedsInt { Working() { super(67); } }
```

Недоступный конструктор родителя (например, private в другом самостоятельном верхнеуровневом классе), либо две несравнимые varargs-перегрузки `Parent(int...)` и `Parent(String...)` также могут сделать `super()` недопустимым. Применимость и выбор перегрузки — [CORE-CONVERSIONS](conversions.md).

Ещё одна граница — исключения. Неявный default constructor не объявляет `throws`. [JLS 21 §8.8.9](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.8.9) формулирует условие через доступный конструктор родителя, принимающий ноль аргументов, без секции `throws`. Если выбранный конструктор объявляет проверяемое исключение, которое должно быть объявлено, неявный конструктор не подходит. Явно объявленный конструктор может объявить такое исключение:

```java
class CheckedParent { CheckedParent() throws java.io.IOException {} }
// class BadChild extends CheckedParent {} // ошибка: checked exception
class CheckedChild extends CheckedParent {
    CheckedChild() throws java.io.IOException { super(); }
}
class UncheckedParent { UncheckedParent() throws IllegalStateException {} }
class UncheckedChild extends UncheckedParent {} // javac 21.0.12.1: компилируется
```

Последний вариант — диагностическое наблюдение на OpenJDK 21.0.12.1, а не безусловная гарантия для всех компиляторов: буквальное условие §8.8.9 строже такого результата, тогда как [JLS §11.2.3](https://docs.oracle.com/javase/specs/jls/se21/html/jls-11.html#jls-11.2.3) требует объявления проверяемых исключений. Не делаем вывода, что любая секция `throws` разрешена или спецификация ошибочна. Развёрнутое сопоставление §8.8.7, §8.8.9, §15.12.2 и диагностик — в [CORE-INIT](initialization.md).

Для неприватного нестатического класса-члена (inner member class) default constructor имеет неявный первый формальный параметр, представляющий непосредственно охватывающий экземпляр. Например, `new Outer().new Inner()` требует экземпляра `Outer`, даже если в объявлении `Inner` не написано ни одного конструктора. Это не параметр, который разработчик добавляет руками; см. [CORE-NESTED](nested-classes.md). У record при отсутствии явного канонического конструктора действует отдельное правило неявного канонического конструктора по компонентам record, а не обычный default constructor ([CORE-RECORDS](records.md)).

## Два разных применения this

Слово `this` употребляется и при обращении к текущему объекту, и при **делегировании одному из конструкторов** этого же класса:

```java
class Point {
    int x;
    int y;

    Point(int x) {
        this(x, 0); // вызов другого конструктора
    }

    Point(int x, int y) {
        this.x = x; // поле экземпляра, а x — параметр
        this.y = y;
    }
}
```

В строке `this.x = x` слева находится **поле объекта**, справа — **параметр**. Вызов `this(x, 0)` — не метод, а передача управления другому конструктору.

Для **Java 21** явный вызов конструктора `this(...)` либо `super(...)` должен находиться **первым оператором** тела конструктора; циклическое делегирование конструкторам запрещено. Не пытайтесь трактовать их как методы, которые можно вызвать из любого места.

> [!note]- Конструкторы наследования
> Если класс наследует другой класс, до выполнения инициализации собственного состояния участвуют конструктор и инициализаторы суперкласса. Это принципиально важно, в частности при вызове переопределённого метода из конструктора. Правила выбора переопределённой реализации объясняются в [CORE-INHERITANCE](inheritance.md); полный порядок создания разобран в [CORE-INIT](initialization.md).

## Что именно происходит при new

Для обычного `new` экземпляра класса, после необходимой инициализации класса, при нормальном ходе конструкторной цепочки полезна такая схема ([JLS §12.5](https://docs.oracle.com/javase/specs/jls/se21/html/jls-12.html#jls-12.5)):

1. Выделяется экземпляр, все его экземплярные поля (включая унаследованное состояние) получают **значения по умолчанию** (`0`, `false`, `null`).
2. Вызовы `this(...)` делегируют внутри класса до конструктора, вызывающего `super(...)`; цепочка обработки конструктора родителя завершается до собственных инициализаторов данного класса.
3. В каждом классе цепочки его инициализаторы полей и блоки инициализации экземпляра выполняются в **их текстовом порядке**, один раз при нормальном создании, даже если несколько конструкторов класса связаны через `this(...)`.
4. Выполняются оставшиеся части тел конструкторов в порядке возврата из делегирования; при нормальном завершении выражение `new` даёт ссылку на объект.

Это не полный алгоритм вычисления аргументов, выбора конструктора и обработки исключений. Подробности — в [CORE-INIT](initialization.md). Для класса без явно указанного суперкласса с собственными инициализаторами пример прост:

```java
class Initialized {
    int first = 67;
    int second;
    { second = first + 1; } // блок инициализации экземпляра

    Initialized() {
        second++;
    }
}
Initialized example = new Initialized();
System.out.println(example.first);  // 67
System.out.println(example.second); // 69
```

### Делегирование не повторяет инициализаторы

```java
class Base {
    Base() { System.out.print("P"); show(); }
    void show() {}
}
class Child extends Base {
    int value = 67;
    { System.out.print("I"); }
    Child() { this(0); System.out.print("D"); }
    Child(int ignored) { System.out.print("C"); }
    @Override void show() { System.out.print(value); }
}
new Child(); // P0ICD
```

Вызов `show()` из конструктора `Base` виртуальный: у объекта `Child` он выбирает переопределённую реализацию, хотя собственный инициализатор `value = 67` ещё не выполнился. Поэтому видно `0`. Затем выполняются инициализатор поля, блок `I`, тело `Child(int)` и оставшаяся часть `Child()`. Блок `I` не повторяется. Из конструктора не следует вызывать переопределяемые методы, полагающиеся на уже готовое состояние наследника.

Правило относится к обычной конструкторной процедуре, а не ко всем способам получения объекта. Например, `Object.clone()` при поддерживаемом клонировании копирует поля без выполнения конструкторов и экземплярных инициализаторов нового экземпляра; обычная десериализация `Serializable` также имеет особую процедуру (конструктор первого несериализуемого суперкласса, специальные правила record). См. [CORE-OBJECT](object.md) и [CORE-SERIAL](serialization.md). Статические инициализаторы выполняются при **инициализации класса**, не просто при его загрузке.

Нюанс для собеседования: использование `static final` константы времени компиляции может **не вызвать инициализацию класса** так же, как вызов его `static`-метода. Нельзя формулировать правило как «любое обращение к классу всегда запускает static block». Подробный разбор — в [CORE-INIT](initialization.md); различие загрузки и инициализации разобрано в [CORE-CLASSLOADER](classloaders.md), более широкий жизненный цикл JVM — будущая тема `JVM-LOADING`.

## Методы и перегрузка

Обычный метод может получать параметры, возвращать значение и менять состояние объекта. **Перегрузка** означает наличие нескольких методов с одним именем, но различающимися списками параметров.

```java
class Converter {
    String describe(int number)  { return "int"; }
    String describe(long number) { return "long"; }

    // int describe(int number) { return number; }
    // ошибка: нельзя перегрузить метод одним только возвращаемым типом
}
```

Выбор подходящей перегрузки выполняется компилятором исходя из **типов выражений в месте вызова**. Например, выбор между `long` и `Integer` уже подробно объяснён в [CORE-CONVERSIONS](conversions.md).

Не путайте перегрузку с **переопределением**: последняя операция касается реализации у наследников и динамической диспетчеризации. Её следует разбирать в [CORE-INHERITANCE](inheritance.md), не выдавая короткий пример за исчерпывающее объяснение.

## Private-конструктор и статический фабричный метод

Не всякий конструктор должен быть доступен извне. Класс может предложить фабричный метод с именем и проверками:

```java
class Token {
    private final String value;

    private Token(String value) {
        this.value = value;
    }

    static Token of(String value) {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("Токен пуст");
        }
        return new Token(value);
    }
}

Token token = Token.of("67");
// new Token("67"); // ошибка компиляции: конструктор private
```

Фабрика может выполнять проверку, возвращать заранее подготовленный объект или выбирать реализацию. Но **наличие фабрики не обещает кэш или singleton**. Конструктор может быть вызван из других конструкторов и методов того же класса; прямое создание обычным независимым внешним клиентом ограничено модификатором доступа; допустимый вложенный доступ описан в [CORE-ACCESS](access.md).

> [!note]- Создать объект без прямого вызова new
> В Java есть способы получить экземпляр, не записав `new SomeClass()` в вызывающем коде: фабрики, reflection, десериализация и другие механизмы. Они не равнозначны друг другу по тому, что именно выполняется при создании. Подробнее о базовых методах и идентичности — [CORE-OBJECT](object.md); [CORE-REFLECTION](reflection.md) уже разбирает получение `Class`, вызовы отражённых конструкторов и ограничения доступа. Особенности восстановления объектов разобраны в [CORE-SERIAL](serialization.md).

## Абстрактный класс и конструктор

`abstract` запрещает непосредственное создание экземпляра самого абстрактного класса. При этом такой класс может иметь поля, реализованные методы и конструкторы — даже если в нём вообще нет абстрактных методов. Конструктор абстрактного класса выполняется при создании конкретного подкласса:

```java
abstract class Shape {
    private final int value;
    Shape(int value) { this.value = value; }
    int value() { return value; }
}
class Concrete extends Shape { Concrete() { super(67); } }
// new Shape(67); // ошибка компиляции
System.out.println(new Concrete().value()); // 67
System.out.println(new Shape(68) {}.value()); // 68: анонимный конкретный подкласс
```

Фабрика — способ предоставить именованный API получения объекта, а абстрактность — ограничение создания экземпляров данного класса. Это разные механизмы. См. [CORE-INHERITANCE](inheritance.md) и [JLS §8.1.1.1](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.1.1.1).

## Три разных смысла final

| Где стоит `final` | Что запрещено | Что остаётся допустимым |
|---|---|---|
| Поле | Повторное присваивание значения | Изменение состояния объекта по сохранённой ссылке, если объект mutable |
| Экземплярный метод | Переопределение | Вызов и наследование, когда допускают правила доступа и наследования |
| Статический метод | Скрытие наследником | Вызов и наследование, когда применимо |
| Класс | Создание подкласса | Изменяемое состояние экземпляра |

```java
class Parent {
    final StringBuilder text = new StringBuilder("A");
    final int read() { return 67; }
    static final int code() { return 68; }
}
class Child extends Parent {
    // int read() { return 68; } // ошибка: override final
    // static int code() { return 67; } // ошибка: hide final
}
Child item = new Child();
item.text.append("B"); // допустимо: AB
System.out.println(item.read()); // 67
System.out.println(Child.code()); // 68
final class Closed {}
// class Other extends Closed {} // ошибка
```

Запрет переопределения/скрытия относится именно к методам, которые могли бы быть переопределены/скрыты: одноимённое самостоятельное объявление в наследнике при private-методе — отдельный случай. `final` не является обещанием неизменяемости: подробнее [CORE-INHERITANCE](inheritance.md), [CORE-TYPES](types.md) и [CORE-IMMUTABLE](immutability.md).

## Тип ссылки, фактический класс и равенство объектов

```java
Object a = new String("67");
Object b = new String("67");
System.out.println(a.getClass() == String.class); // true
System.out.println(a == b);                     // false
System.out.println(a.equals(b));                // true
System.out.println(a.hashCode() == b.hashCode()); // true
```

Объявленный тип `a` — `Object`, фактический класс объекта — `String`. `getClass()` возвращает его runtime-класс; `==` сравнивает ссылочную идентичность, `equals` использует контракт реализации (для `String` — содержимое). Равные по `equals` объекты должны иметь одинаковый `hashCode`, но одинаковые хеши не доказывают равенство. См. [CORE-OBJECT](object.md) и [CORE-EQUALITY](equality.md).

Конструктор копирования — обычная перегрузка, например `Point(Point source) { this(source.x, source.y); }` при наличии `Point(int, int)`. У Java нет специального синтаксиса, который автоматически обеспечивал бы глубокую копию. Для примитивных полей копируются значения; при ссылочных полях автор выбирает контракт — разделять ссылки либо копировать требуемое состояние. См. [CORE-IMMUTABLE](immutability.md).

## Частые вопросы собеседования

| Вопрос | Ключ к ответу |
|---|---|
| Чем класс отличается от объекта и что даёт `new`? | Объект — экземпляр класса или массив; `new` при успехе даёт ссылку |
| `a = b` создаёт копию объекта? | Нет: копируется ссылка |
| У двух объектов разные `balance`, но общий `static count`? | Да, это разные категории полей |
| Почему в `static` методе нет `this`, но допустимо `target.value`? | Нет неявного экземпляра; явная ссылка предоставляет его |
| Конструктор отличается от метода только названием? | Нет: нет возвращаемого типа, особая семантика создания |
| Когда появляется default constructor обычного класса? Почему `super()` может не скомпилироваться? | Нет объявленных конструкторов; доступность, применимость, однозначность и исключения; varargs может принимать ноль аргументов |
| Что означает `this.x = x`? | Слева поле объекта, справа параметр |
| Можно перегрузить только возвращаемым типом? | Нет |
| Можно ли получить отрицательный остаток без проверки? | Да, если API не защищает инвариант |
| Чем отличаются `final` поле, экземплярный метод, статический метод и класс? | Запрет повторного присваивания, переопределения, скрытия и наследования класса соответственно |
| Почему абстрактный класс может иметь конструктор? | Он выполняется при создании конкретного подкласса |
| Почему `new Child()` в примере делегирования печатает `P0ICD`? | Виртуальный вызов до инициализации наследника; его инициализаторы один раз |
| Почему `a == b` может быть false при `a.equals(b)` true? | Идентичность и семантическое равенство — разные контракты |
| Почему счётчик конструктора не отражает число живых объектов? | Считает обновления при вызовах; GC не уменьшает, int может переполниться |
| Безопасно ли увеличивать `static int` из разных потоков? | Не автоматически |
| Всегда ли вызов `static` через `null` вызывает NPE? | Нет: статический вызов имеет иные правила, чем метод экземпляра |

**Контрпример для `static` и `null`:** Java разрешает обращение к статическому методу через переменную ссылочного типа, даже если в ней `null`. Однако это затрудняет чтение и не должно использоваться в обычном коде:

```java
class Marker {
    static String name() { return "Marker"; }
}

Marker absent = null;
System.out.println(absent.name()); // Marker, не NullPointerException
System.out.println(Marker.name()); // так правильно и понятно
```

Здесь вызывается именно **статический метод класса**, а не метод объекта `absent`. При статическом вызове через выражение оно вычисляется, результат отбрасывается; `null` сам по себе не вызывает NPE. Если вычисление квалификатора выбрасывает исключение, аргументы и тело вызова не выполняются. При обычном вызове метода экземпляра проверка сохранённого `null`-получателя происходит после нормального вычисления аргументов. Это правило [JLS §15.12.4.1](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.12.4.1) и [§15.12.4.4](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.12.4.4), а не особенность JVM.

```java
static Marker qualifier() {
    System.out.print("Q:");
    return null;
}
System.out.println(qualifier().name()); // Q:Marker; javac -Xlint:static предупреждает
```

В обычном коде используйте `Marker.name()`; если вычисление `qualifier()` нужно ради побочного эффекта, выполните его явно отдельно.

**Не путайте класс и объект с хранением в конкретной области памяти.** JLS описывает поведение, но не требует от всех реализаций одинакового расположения объектов или локальных ссылок. Это другая задача — `JVM-MEMORY`.

## Практика

[ClassesAndObjectsDemo.java](../../examples/core/ClassesAndObjectsDemo.java) показывает два счёта, ссылки на один экземпляр, перегруженные конструкторы с `this(owner, 0)`, общий `static` счётчик и проверки недопустимых операций. В отличие от учебного фрагмента, класс `CreditAccount` в файле `final`; счётчик увеличивается после проверок владельца и начального остатка. Самопроверки подтверждают раздельные остатки, общую мутацию через alias, счётчик после отклонённых конструкторов, отказ при перерасходе и неизменность остатка при переполнении. Они не проверяют все новые случаи default constructor, abstract, final, clone или static qualifier; эти механизмы объяснены отдельно.

```powershell
java examples/core/ClassesAndObjectsDemo.java
```

В конце должно появиться `CHECK PASSED`. Короткие недопустимые фрагменты в статье **преднамеренно закомментированы**: это примеры ошибок компиляции, а не содержимое запускаемой программы.
