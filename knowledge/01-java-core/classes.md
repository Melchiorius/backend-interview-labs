# CORE-CLASSES — классы, объекты, поля, методы и конструкторы

**Java 21 · предпосылки:** [типы и ссылки](types.md), [передача аргументов](parameters.md).

## Класс и объект — не одно и то же

**Класс** описывает тип объектов: какие данные они хранят (**поля**), какие действия поддерживают (**методы**) и как создаются в корректном состоянии (**конструкторы**). **Объект** — отдельный экземпляр класса.

Допустим, система учитывает условные кредиты пользователей. Два счёта подчиняются одним правилам, но остаток у каждого свой.

```java
CreditAccount first = new CreditAccount("А", 67);
CreditAccount second = new CreditAccount("Б", 10);
CreditAccount alias = first;

System.out.println(first == second); // false — два экземпляра
System.out.println(alias == first);  // true — одна и та же ссылка
```

Выражения `new CreditAccount(...)` создают два экземпляра. Переменная `alias` получает **копию ссылки**, а не копию объекта. Поэтому изменение объекта через `alias` будет видно и через `first`. Полная модель переменных и ссылок уже раскрыта в [CORE-TYPES](types.md).

**Важно:** фрагменты кода ниже показывают отдельные случаи и не предполагаются одним общим файлом. Законченную исполняемую программу см. в [ClassesAndObjectsDemo.java](../../examples/core/ClassesAndObjectsDemo.java).

## Поля, методы и состояние экземпляра

Рассмотрим класс со строго положительными пополнениями и запрещённым перерасходом. Для простоты суммы считаются **условными целыми кредитами**, а не деньгами.

```java
class CreditAccount {
    private final String owner;
    private long balance;

    CreditAccount(String owner, long openingBalance) {
        if (owner == null || owner.isBlank()) {
            throw new IllegalArgumentException("Имя владельца обязательно");
        }
        if (openingBalance < 0) {
            throw new IllegalArgumentException("Отрицательный остаток");
        }
        this.owner = owner;
        this.balance = openingBalance;
    }

    long balance() {
        return balance;
    }

    void deposit(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Сумма должна быть положительной");
        }
        balance = Math.addExact(balance, amount);
    }

    void withdraw(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Сумма должна быть положительной");
        }
        if (amount > balance) {
            throw new IllegalStateException("Недостаточно кредитов");
        }
        balance -= amount;
    }
}
```

**Кто выполняет действия:** вызывающий код создаёт экземпляр через конструктор. Конструктор проверяет переданные значения и заполняет поля **этого объекта**. Затем при вызове `account.deposit(10)` метод меняет поле `balance` **этого экземпляра**, а не всех счетов.

- Поле `owner` хранит владельца и объявлено `final`: после инициализации ссылку в нём нельзя переназначить.
- Поле `balance` изменяемое: операции счёта вправе менять остаток.
- Метод `balance()` возвращает значение; он сам по себе не даёт вызывающему коду право записать новое значение в поле.
- Поле `private` недоступно клиентскому коду напрямую. Подробные правила `public`, `protected` и package-private разберёт будущая `CORE-ACCESS`.

### Инвариант и зачем прятать поля

**Инвариант объекта** — условие, которое корректный объект обязан сохранять после успешного создания и завершения разрешённых операций. Для этого класса: `balance >= 0`.

Если бы внешний код мог записать `balance = -67`, класс не контролировал бы собственные правила. Поэтому проверки нужно сосредоточивать в конструкторе и изменяющих методах. Здесь `Math.addExact` дополнительно предотвращает незаметное переполнение при пополнении.

> [!note]- Исключение из конструктора
> Если конструктор завершился исключением, выражение `new` не даёт вызывающему коду обычного результата. Это **не** означает, что JVM вообще не выделяла память или что никакие побочные эффекты не успели произойти. Действия в конструкторе и опасность преждевременной публикации `this` — отдельные темы `CORE-INIT` и `CON-JMM`.

## Экземплярные и статические члены: чей это счётчик?

Без `static` поле принадлежит **каждому объекту**. Статическое поле — **член класса**: его не нужно дублировать в каждом экземпляре.

```java
class Counter {
    private int value;
    private static int createdCount;

    Counter() {
        createdCount++;
    }

    void increment() {
        value++;
    }

    int value() {
        return value;
    }

    static int createdCount() {
        return createdCount;
    }
}

Counter first = new Counter();
Counter second = new Counter();
first.increment();

System.out.println(first.value());          // 1
System.out.println(second.value());         // 0
System.out.println(Counter.createdCount()); // 2
```

| Вопрос | Экземплярный член | Статический член |
|---|---|---|
| Кому относится? | Конкретному объекту | Классу |
| Типичный вызов | `first.increment()` | `Counter.createdCount()` |
| Есть ли неявный `this` в методе? | Да | Нет |
| Нужен ли объект для доступа к его полям? | `this` — текущий объект | Нужна явная ссылка на объект |

**Типичный вопрос собеседования:** почему из статического метода нельзя обратиться к обычному полю только по его имени?

```java
class Example {
    int value;

    static void wrong() {
        // value++;      // ошибка: нет текущего экземпляра
        // this.value++; // ошибка: this в static-контексте недоступен
    }

    static void correct(Example target) {
        target.value++;  // экземпляр предоставлен явно
    }
}
```

В `static`-методе нет текущего объекта, поэтому и поля экземпляра без явной ссылки нет. Вызов статического метода через объектную ссылку синтаксически возможен, но вводит в заблуждение; используйте имя класса.

> [!note]- Static и многопоточность
> Поле `static` не становится потокобезопасным. Например, `createdCount++` не является атомарным увеличением и может терять обновления при конкурентном создании объектов. Кроме того, `static` не следует без оговорок описывать как «одно поле на всю JVM»: один и тот же именованный класс может быть определён разными загрузчиками классов. Детали — `CON-RACE`, `CON-JMM` и `JVM-LOADING`.

## Конструктор: как объект получает допустимое начальное состояние

Конструктор имеет **имя класса** и **не имеет типа возвращаемого значения**, даже `void`. Это особый элемент языка, а не обычный метод:

```java
class Point {
    int x;
    int y;

    Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
}
```

Запись `void Point(int x, int y)` была бы **методом**, а не конструктором: совпадение имени с классом этому не мешает. Конструкторы **не наследуются** и **не переопределяются**, но могут иметь разные списки параметров (**перегрузка конструкторов**).

### Неявный конструктор по умолчанию ≠ любой no-args

Java автоматически объявляет конструктор без аргументов **только если в классе нет ни одного объявленного конструктора**:

```java
class EmptyPoint {
    int x;
}
new EmptyPoint(); // работает: компилятор объявил default constructor

class FixedPoint {
    FixedPoint(int x) { }
}
// new FixedPoint(); // ошибка: неявного конструктора больше нет
new FixedPoint(67);
```

Если требуются и `FixedPoint()`, и `FixedPoint(int)` — оба нужно объявить самостоятельно. **Конструктор, написанный разработчиком без параметров, не называется «неявным конструктором по умолчанию»** в смысле JLS. Модификатор доступа у неявного конструктора также определяется правилами спецификации; подробности — в `CORE-ACCESS`.

Добавлять no-args «на всякий случай» не всегда правильно: если для корректного состояния нужны аргументы, такой конструктор может позволить создать неполноценный объект.

## Два разных применения this

Слово `this` употребляется и при обращении к текущему объекту, и при **делегировании одному из конструкторов** этого же класса:

```java
class Point {
    int x;
    int y;

    Point(int x) {
        this(x, 0); // вызов другого конструктора
    }

    Point(int x, int y) {
        this.x = x; // поле экземпляра, а x — параметр
        this.y = y;
    }
}
```

В строке `this.x = x` слева находится **поле объекта**, справа — **параметр**. Вызов `this(x, 0)` — не метод, а передача управления другому конструктору.

Для **Java 21** явный вызов конструктора `this(...)` либо `super(...)` должен находиться **первым оператором** тела конструктора; циклическое делегирование конструкторам запрещено. Не пытайтесь трактовать их как методы, которые можно вызвать из любого места.

> [!note]- Конструкторы наследования
> Если класс наследует другой класс, до выполнения инициализации собственного состояния участвуют конструктор и инициализаторы суперкласса. Это принципиально важно, в частности при вызове переопределённого метода из конструктора. Полный анализ порядка — будущие `CORE-INIT` и `CORE-INHERITANCE`.

## Что именно происходит при new

Для обычного создания экземпляра полезно представить последовательность:

1. Выделяется экземпляр, его поля получают **значения по умолчанию** (`0`, `false`, `null`).
2. С учётом вызовов конструкторов суперклассов выполняются инициализаторы полей и блоки инициализации экземпляра в **их текстовом порядке**.
3. Выполняется тело выбранного конструктора; при нормальном завершении `new` возвращает ссылку на созданный объект.

Это **упрощённая схема**. Предсказать точный порядок в иерархии по ней нельзя — для этого предназначена `CORE-INIT`. Для одного класса без наследования с собственными инициализаторами пример прост:

```java
class Initialized {
    int first = 67;
    int second;
    { second = first + 1; } // блок инициализации экземпляра

    Initialized() {
        second++;
    }
}
Initialized example = new Initialized();
System.out.println(example.first);  // 67
System.out.println(example.second); // 69
```

Инициализаторы экземпляра выполняются **при создании каждого объекта**; статические инициализаторы класса выполняются **при инициализации самого класса**.

Нюанс для собеседования: использование `static final` константы времени компиляции может **не вызвать инициализацию класса** так же, как вызов его `static`-метода. Нельзя формулировать правило как «любое обращение к классу всегда запускает static block». Разбор — `CORE-INIT` и `JVM-LOADING`.

## Методы и перегрузка

Обычный метод может получать параметры, возвращать значение и менять состояние объекта. **Перегрузка** означает наличие нескольких методов с одним именем, но различающимися списками параметров.

```java
class Converter {
    String describe(int number)  { return "int"; }
    String describe(long number) { return "long"; }

    // int describe(int number) { return number; }
    // ошибка: нельзя перегрузить метод одним только возвращаемым типом
}
```

Выбор подходящей перегрузки выполняется компилятором исходя из **типов выражений в месте вызова**. Например, выбор между `long` и `Integer` уже подробно объяснён в [CORE-CONVERSIONS](conversions.md).

Не путайте перегрузку с **переопределением**: последняя операция касается реализации у наследников и динамической диспетчеризации. Её следует разбирать в `CORE-INHERITANCE`, не выдавая короткий пример за исчерпывающее объяснение.

## Private-конструктор и статический фабричный метод

Не всякий конструктор должен быть доступен извне. Класс может предложить фабричный метод с именем и проверками:

```java
class Token {
    private final String value;

    private Token(String value) {
        this.value = value;
    }

    static Token of(String value) {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("Токен пуст");
        }
        return new Token(value);
    }
}

Token token = Token.of("67");
// new Token("67"); // ошибка компиляции: конструктор private
```

Фабрика может выполнять проверку, возвращать заранее подготовленный объект или выбирать реализацию. Но **наличие фабрики не обещает кэш или singleton**. Конструктор может быть вызван из других конструкторов и методов того же класса; прямое создание извне ограничено модификатором доступа.

> [!note]- Создать объект без прямого вызова new
> В Java есть способы получить экземпляр, не записав `new SomeClass()` в вызывающем коде: фабрики, reflection, десериализация и другие механизмы. Они не равнозначны друг другу по тому, что именно выполняется при создании. Подробнее — `CORE-REFLECTION`, `CORE-SERIAL`, `CORE-OBJECT`.

## Частые вопросы собеседования

| Вопрос | Ключ к ответу |
|---|---|
| Чем класс отличается от объекта? | Тип/описание и конкретный экземпляр |
| `a = b` создаёт копию объекта? | Нет: копируется ссылка |
| У двух объектов разные `balance`, но общий `static count`? | Да, это разные категории полей |
| Почему в `static` методе нет `this`? | Нет текущего экземпляра |
| Конструктор отличается от метода только названием? | Нет: нет возвращаемого типа, особая семантика создания |
| Когда появляется default constructor? | Только если вообще нет объявленных конструкторов |
| Что означает `this.x = x`? | Слева поле объекта, справа параметр |
| Можно перегрузить только возвращаемым типом? | Нет |
| Можно ли получить отрицательный остаток без проверки? | Да, если API не защищает инвариант |
| Обязательно ли поле `final` делает объект неизменяемым? | Нет; `final` запрещает переназначить поле |
| Безопасно ли увеличивать `static int` из разных потоков? | Не автоматически |
| Всегда ли вызов `static` через `null` вызывает NPE? | Нет: статический вызов имеет иные правила, чем метод экземпляра |

**Контрпример для `static` и `null`:** Java разрешает обращение к статическому методу через переменную ссылочного типа, даже если в ней `null`. Однако это затрудняет чтение и не должно использоваться в обычном коде:

```java
class Marker {
    static String name() { return "Marker"; }
}

Marker absent = null;
System.out.println(absent.name()); // Marker, не NullPointerException
System.out.println(Marker.name()); // так правильно и понятно
```

Здесь вызывается именно **статический метод класса**, а не метод объекта `absent`. Если выражение слева само содержит побочные эффекты или исключение, его вычисление всё ещё имеет значение; пример с простой переменной лишь подчёркивает отсутствие разыменования ссылки для статического вызова.

**Не путайте класс и объект с хранением в конкретной области памяти.** JLS описывает поведение, но не требует от всех реализаций одинакового расположения объектов или локальных ссылок. Это другая задача — `JVM-MEMORY`.
