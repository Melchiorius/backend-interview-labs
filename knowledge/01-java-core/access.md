# CORE-ACCESS — модификаторы доступа и инкапсуляция в Java 21

**Java:** 21. **Основной вопрос:** кто может обратиться к типу, полю, методу или конструктору — и как эти ограничения помогают не разрушать состояние объекта? **Исследовательская основа:** [CORE-ACCESS](../../docs/plans/CORE-ACCESS.md) (AC-01–AC-20).

## Зачем вообще ограничивать доступ

Представим сервис со счетами пользователей. Объект счёта хранит остаток и должен соблюдать правило: после допустимой операции остаток неотрицателен. Если любой код может записать в поле `balance` произвольное значение, конструктор и метод списания теряют возможность обеспечивать это правило. Ограничение прямого доступа заставляет внешние компоненты пользоваться предусмотренными операциями.

Но **инкапсуляция не равна наличию `private`**. Это проектирование границы: что клиент может делать с объектом, какие гарантии получает и какие внутренние детали можно менять, не переписывая клиентов. Модификаторы доступа — один из инструментов такой границы.

В Java действуют **три ключевых слова** `public`, `protected`, `private` и **четвёртый режим** — отсутствие модификатора доступа (*package access*, часто говорят *package-private*). Ключевого слова `default` для обозначения package-private **нет**: `default` имеет другое назначение, например в интерфейсных методах.

Прежде чем смотреть таблицу, разберём три разных вопроса:

1. **Можно ли вообще назвать тип?** Если класс недоступен из другого пакета, объявленный в нём публичный метод этого не исправляет.
2. **Разрешён ли доступ к конкретному члену или конструктору?** Здесь действуют его собственный модификатор, местоположение вызывающего кода и иногда тип выражения.
3. **Доступно ли простое имя именно здесь?** Область действия имени (`scope`) и доступность (`accessibility`) — не одно и то же. Можно иметь доступный член, но обращаться к нему по квалифицированному имени, либо скрыть его простое имя локальной переменной.

Под «клиентом» ниже понимается другой класс, пытающийся использовать тип или его член. В примерах с разными пакетами участники и места вызова указаны явно. Базовые понятия класса, объекта, поля и конструктора разобраны в [CORE-CLASSES](classes.md), а объявленный и фактический тип ссылки — в [CORE-TYPES](types.md).

## Четыре режима доступа: ориентир, а не полное правило

Для **члена доступного класса** в обычном коде без дополнительных границ именованных модулей:

| Режим объявления | Внутри допустимого окружения того же верхнеуровневого типа | Другой класс того же пакета | Подкласс в другом пакете | Посторонний класс другого пакета |
|---|---|---|---|---|
| `public` | Да | Да | Да | Да |
| `protected` | Да | Да | С условиями для полей/методов экземпляра | Нет |
| Без модификатора (*package-private*) | Да | Да | Нет | Нет |
| `private` | Да | Нет | Нет | Нет |

Это **таблица для ориентации**. В ней нельзя отразить все правила для `protected` между пакетами, отдельные правила конструкторов, особенности вложенных типов и модульной системы. Ниже эти случаи разобраны отдельно. Источник языковых правил — [JLS 21 §6.6](https://docs.oracle.com/javase/specs/jls/se21/html/jls-6.html#jls-6.6).

Ни один из режимов не следует понимать как ограничение доступа «на уровне конкретного пользователя приложения»: `public` и `private` — правила Java-кода и компиляции, не замена авторизации и проверки входных данных.

## Пакеты: где проходит граница

`package` группирует типы в **пакет** — пространство имён Java. Классы в одном пакете могут обращаться к чужим package-private и `protected` членам, даже если **не наследуют** их владельца. Подпакеты при этом не получают привилегий родительского пакета.

Например, `api` и `api.internal` — **разные** пакеты. Сходство имён не создаёт дополнительного доступа. Имена директорий примеров совпадают с именами пакетов ради понятности компиляции, но правило определяется объявлениями `package`, а не расположением исходных файлов на диске.

Рассмотрим упрощённый пример класса в пакете `api`. Поле `secret` добавлено специально, чтобы показать действие `private`:

```java
// api/Parent.java
package api;

public class Parent {
    protected int value = 67;
    protected static int total = 67;
    int packageValue = 7;
    private int secret = 9;

    protected Parent() {}
    protected void touch() { value++; }
}
```

Обычный сосед **того же пакета** может прочитать `value` и `packageValue`, а также статическое поле `total`, не наследуя `Parent`:

```java
// api/Neighbor.java
package api;

public class Neighbor {
    public static int readFromSamePackage() {
        Parent parent = new Parent(); // protected конструктор доступен в пакете
        return parent.value + parent.packageValue + Parent.total; // 67 + 7 + 67
    }
}
```

Но `parent.secret` в классе `Neighbor` — **ошибка компиляции**: другой верхнеуровневый тип не получает доступа к `private` только за счёт общего пакета. Наоборот, посторонний класс пакета `client` не может прочитать `packageValue` или `value`: для первого поля нет пакетного доступа, а для второго отсутствуют условия `protected`.

**Важный вывод:** `protected` означает **не только наследование**: право доступа есть и у обычных классов того же пакета. А члены с package-private не становятся доступными только потому, что класс другого пакета наследует `Parent`.

## Доступность самого типа, его члена и конструктора

Верхнеуровневый (*top-level*) класс или интерфейс, объявленный непосредственно в файле-компиляционной единице, может быть `public` или package-private. Объявления `private class Hidden {}` и `protected class Hidden {}` **на верхнем уровне** запрещены; это ошибки компиляции по [JLS 21 §7.6](https://docs.oracle.com/javase/specs/jls/se21/html/jls-7.html#jls-7.6). Для верхнеуровневого `public` типа в обычном файловом расположении имя файла должно соответствовать имени типа.

Член класса может быть публичным, однако **внешний код сначала должен иметь доступ к самому объявляющему типу**:

```java
// api/Hidden.java
package api;

class Hidden {
    public static class Visible {}
}
```

В другом пакете строка `api.Hidden.Visible v;` **не компилируется**: `Hidden` недоступен, хотя его вложенный тип объявлен `public`.

Аналогично доступность класса **не гарантирует**, что его можно создать через `new`:

```java
// api/Token.java
package api;

public final class Token {
    private final String text;

    private Token(String text) { this.text = text; }

    public static Token of(String text) {
        if (text == null || text.isBlank()) {
            throw new IllegalArgumentException("Пустой токен");
        }
        return new Token(text);
    }

    public String text() { return text; }
}
```

```java
// client/UseToken.java
package client;

import api.Token;

class UseToken {
    Token make() { return Token.of("67"); } // работает
}
```

В `UseToken` выражение `new Token("67")` **не компилируется**, хотя `Token` — публичный класс. Конструктор `private`, а фабрика `of` публична. Так класс сохраняет контроль над созданием объектов.

Конструктор **по умолчанию**, который компилятор объявляет при полном отсутствии конструкторов, тоже имеет правила доступности — не следует автоматически считать его `public` для любого публичного класса. Подробно о default constructor и создании объектов см. [CORE-CLASSES](classes.md) и [JLS 21 §8.8.9](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.8.9).

## Protected между пакетами: наследник — ещё не свободный доступ

Это самая частая ошибка заученной таблицы. Когда `protected` поле **экземпляра** или метод **экземпляра** объявлены в `api.Parent`, а код находится внутри подкласса `client.Child`, недостаточно сказать: «`Child` — наследник, значит может обращаться к любому `Parent`».

Для доступа из другого пакета должны выполняться условия [JLS 21 §6.6.2.1](https://docs.oracle.com/javase/specs/jls/se21/html/jls-6.html#jls-6.6.2.1):

- Доступ происходит **в теле подкласса** `S` класса, где объявлен член; в нашем примере `S` = `Child`.
- Если доступ к экземплярному члену квалифицирован выражением (например, `other.value`), **статический тип этого выражения** должен быть `S` или его подклассом. Статический тип — тип, известный компилятору, а не фактический класс объекта при исполнении.

Пример в другом пакете:

```java
// client/Child.java
package client;

import api.Parent;

public class Child extends Parent {
    public Child() {
        super(); // protected конструктор родителя: разрешён
    }

    public int ok(Child otherChild) {
        touch();       // унаследованный protected метод
        super.touch(); // явное обращение к родительскому методу
        return this.value + otherChild.value; // оба обращения разрешены
    }
}
```

Оба типа квалификаторов `this` и `otherChild` — `Child`. То, что `otherChild` представляет **другой объект**, не мешает доступу: важно, что код находится в `Child` и обращается через разрешённый статический тип. Этот метод также может менять значение своего объекта при вызове `touch()` — это отдельный эффект и не часть проверки доступа.

### Отрицательные случаи: каждый рассматривается отдельно

Следующие фрагменты — **преднамеренные ошибки компиляции**, а не код, который надо объединить с предыдущим рабочим файлом. Каждый мысленно помещён в тело `client.Child`; `Sibling` — другой подкласс `api.Parent` из пакета `client`.

```java
// НЕ компилируется внутри Child:
int readParent(Parent parent) {
    return parent.value;
}
```

```java
// НЕ компилируется внутри Child:
int readCast(Child child) {
    return ((Parent) child).value;
}
```

```java
// НЕ компилируется внутри Child:
int readSibling(Sibling sibling) {
    return sibling.value;
}
```

В первом случае статический тип `parent` — `Parent`, во втором после явного приведения выражение имеет статический тип `Parent`, в третьем `Sibling` — другой наследник, но **не** `Child` и не его подкласс. Три фактических объекта могут даже оказаться связаны наследованием; проверка выполняется компилятором по типу квалификатора.

Ниже ещё два отдельных случая **неуспешной компиляции** в `Child`:

```java
int readPackageMember() {
    return packageValue; // член Parent без модификатора недоступен из client
}
```

```java
void invokeOnParent(Parent parent) {
    parent.touch(); // защищённый экземплярный метод через тип Parent
}
```

Для метода экземпляра действует та же существенная проверка типа квалификатора, что и для поля. В приведённом выше учебном фрагменте `Child.ok` вызовы `touch()` и `super.touch()` допустимы. В запускаемом примере вызов `super.touch()` вынесен в `Child.touchUsingSuper()`.

> [!note]- Где это правило заканчивается
> В [JLS 21 §6.6.2.1](https://docs.oracle.com/javase/specs/jls/se21/html/jls-6.html#jls-6.6.2.1) дополнительно перечислены формы доступа к полям, вызовам методов и method references. Не нужно угадывать решение для каждой новой синтаксической формы только по таблице. Специальное ограничение qualifying type относится к **instance** полям и методам. Оно **не** применяется по той же схеме к `protected static` членам и **не** заменяет отдельное правило для конструкторов.

### Почему protected static — не тот же случай

`total` в `Parent` — **статическое** поле. Из тела `Child`, находящегося в другом пакете, допустимо:

```java
// внутри client.Child
void incrementGlobalCount() {
    Parent.total++;
}
```

Имя класса `Parent` здесь подходит, несмотря на то, что `Parent` — не `Child`. Дополнительная проверка статического типа квалификатора для **экземплярных** членов сюда не переносится. Однако произвольный посторонний класс пакета `client` не получает права читать `Parent.total`: `protected` по-прежнему ограничивает место обращения. И `static` не означает потокобезопасность; см. [CORE-CLASSES](classes.md).

## Protected конструктор: отдельное правило

Конструктор не является обычным методом и **не наследуется**. Правило [JLS 21 §6.6.2.2](https://docs.oracle.com/javase/specs/jls/se21/html/jls-6.html#jls-6.6.2.2) нужно рассматривать самостоятельно. В примере `Parent` имеет `protected Parent()`, и пакеты различаются:

```java
// client/Child.java
package client;

public class Child extends api.Parent {
    public Child() {
        super(); // разрешённый вызов конструктора суперкласса
    }
}
```

Из чужого пакета **обычное** выражение `new api.Parent()` не компилируется — даже если оно записано в методе `Child`. Но специальная форма создания **анонимного подкласса** допускается:

```java
// внутри client.ClientFactory, не обязанного наследовать Parent
api.Parent make() {
    return new api.Parent() {}; // создаётся анонимный подкласс Parent
}
```

Фигурные скобки `{}` после `new api.Parent()` имеют значение: создаётся **анонимный подкласс** с вызовом родительского конструктора. Удаление `{}` меняет ситуацию, и простой `new api.Parent()` вне пакета будет отвергнут. Не распространяйте это исключение на обычный `new`. Подробная семантика анонимных классов разобрана в [CORE-NESTED](nested-classes.md).

## Private и вложенные типы

`private` запрещает доступ **из соседнего самостоятельного верхнеуровневого типа**, даже в том же пакете. Но вложенные типы, находящиеся в пределах допустимого окружения того же верхнеуровневого класса, могут обращаться к его `private` членам:

```java
class Outer {
    private int secret = 67;

    static class Nested {
        int read(Outer owner) {
            return owner.secret; // разрешено
        }
    }
}
```

`Nested` — статический вложенный класс. Он получает ссылку на конкретный `Outer` через аргумент `owner`; собственного неявного экземпляра `Outer` здесь нет. Соседний верхнеуровневый `Friend` даже того же пакета не может выполнить `outer.secret`.

Это **правила доступа исходного языка**. Языковые правила вложенных и анонимных классов разобраны в [CORE-NESTED](nested-classes.md). Технические детали nestmates / NestHost и байткода JVM остаются отдельной темой и не выводятся из этой статьи. Не утверждайте, что компилятор обязан реализовать доступ определённым машинным способом.

## Особенности интерфейсов и типов-членов

В **классе** можно объявить `private` или `protected` вложенный тип, если форма его объявления допускает такой модификатор; это не делает `private` или `protected` законными для *top-level* класса.

В **интерфейсе** правила иные: тип-член (класс или интерфейс), объявленный внутри интерфейса, неявно `public static`. Попытка написать для него `private` или `protected` — ошибка компиляции по [JLS 21 §9.5](https://docs.oracle.com/javase/specs/jls/se21/html/jls-9.html#jls-9.5).

```java
interface Rules {
    class PublicNested {} // неявно public static

    private int helper() {
        return 67;
    }

    default int result() {
        return helper(); // разрешено в Java 21
    }
}
```

Отдельные **не компилируемые** объявления внутри интерфейса:

```java
// protected int helper(); // ошибка: интерфейсный метод не может быть protected
// private class Hidden {} // ошибка: тип-член интерфейса не может быть private
```

Для методов интерфейса отсутствие модификатора **не** означает package-private: обычные абстрактные и `default` методы имеют `public` доступ; `private` методы допустимы для вспомогательных реализаций (Java 21), но не являются частью публичного контракта. Полное рассмотрение интерфейсов — в [CORE-INTERFACES](interfaces.md).

## Доступ и переопределение — не одно действие

**Переопределение (overriding)** — реализация унаследованного метода экземпляра в подклассе при соблюдении правил сигнатур и совместимости. При этом нельзя **уменьшать доступность** по отношению к переопределяемому методу ([JLS 21 §8.4.8.3](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.4.8.3)).

```java
class Base {
    protected void act() {}
}

class Derived extends Base {
    @Override
    public void act() {} // допустимо: доступ расширен
}
```

В другом, отдельно рассматриваемом варианте `@Override void act() {}` в `Derived` **не компилируется**: package-private уже, чем `protected`.

Есть и обратная ловушка. Если метод `void internal() {}` объявлен package-private в `api.Base`, одноимённый `public void internal() {}` в `client.Derived extends api.Base` **не переопределяет** недоступный пакетный метод родителя. Аннотация `@Override` здесь помогает обнаружить заблуждение: компилятор отвергнет её применение. Вопросы наследования и динамической диспетчеризации разбирает [CORE-INHERITANCE](inheritance.md).

**Проверка доступа происходит до выполнения программы.** Допустим, класс `Child` публично переопределил `touch()`, а переменная имеет объявленный тип `Parent`:

```java
// внутри постороннего класса пакета client:
api.Parent parent = new Child();
// parent.touch(); // ошибка компиляции: Parent.touch() защищён
```

Даже если фактический объект — `Child` и его override публичен, обращение через статический тип `Parent` не превращается в допустимое. Через `Child` как объявленный тип публичный override доступен. **Access control** решает, можно ли записать вызов; **runtime dispatch** решает, какая реализация допустимого виртуального вызова будет исполнена.

## Инкапсуляция — границы поведения, а не шаблон getters/setters

Вернёмся к счёту из [CORE-CLASSES](classes.md). Его поле `balance` имеет `private`, а методы `deposit`/`withdraw` проверяют аргументы и сохраняют инвариант `balance >= 0`. API предлагает осмысленные операции вместо публичного `setBalance`, который позволил бы обойти проверку.

Но даже `private` поле не обеспечивает сохранность состояния, если наружу отдать **сам изменяемый объект**, лежащий в нём:

```java
import java.util.ArrayList;
import java.util.List;

class Tasks {
    private final List<String> entries = new ArrayList<>();

    void add(String task) {
        entries.add(task);
    }

    List<String> unsafeEntries() {
        return entries; // клиент сможет вызвать clear() и менять внутренний список
    }

    List<String> snapshot() {
        return List.copyOf(entries); // отдельный неизменяемый снимок для String
    }
}
```

`final` здесь запрещает переназначение поля `entries`, **но не изменение содержимого списка**. Метод `snapshot()` позволяет читать копию списка без прямого изменения внутренней коллекции. Важно: `List.copyOf` не делает глубоко неизменяемыми произвольные изменяемые элементы; здесь элементы — строки. Кроме того, пакетный доступ показанных методов выбран для краткости, а не как универсальная рекомендация для внешнего API.

Качество инкапсуляции определяется не количеством `private` полей, а тем, **какие состояния и операции допускает контракт**. `protected` иногда уместен для документированных точек расширения, package-private — для тесно связанных реализаций в одном пакете, `public` — для устойчивых операций клиента. Выбирайте минимальную область доступа, которая действительно соответствует дизайну; менять доступность опубликованного API без оценки совместимости нельзя.

## Область действия имени и доступность — разные ограничения

У локальной переменной есть область действия: часть исходного кода, где её можно назвать простым именем. У поля есть доступность: разрешено ли обратиться к этому полю из данного места. Даже общедоступное поле может быть **затенено** локальной переменной:

```java
class Counter {
    public int value = 5;

    void print() {
        int value = 67;
        System.out.println(value);      // 67: локальная переменная
        System.out.println(this.value); // 5: доступное поле
    }
}
```

Здесь `this.value` доступно, но простое имя `value` означает другую сущность. И наоборот, импорт не превращает package-private тип чужого пакета в доступный. Важны **и разрешение имён, и контроль доступа**, а не только модификатор в объявлении.

## Как анализировать вопрос на собеседовании

Получив незнакомый фрагмент, сначала назовите **место обращения**, затем **объявленный тип выражения** и **владельца члена**:

1. Где записан код: тот же верхнеуровневый тип/допустимое вложение, тот же пакет, подкласс другого пакета или посторонний класс?
2. Доступен ли сам тип, к которому пытаются обратиться? Не скрыт ли он package-private или границей модуля?
3. Это поле, метод экземпляра, `static` член или конструктор? Для `protected` конструктора правила другие.
4. Если это `protected` instance член в чужом пакете — находится ли обращение в подходящем подклассе, и каков **статический тип квалификатора**?
5. Если обращение к методу допустимо, только после этого спрашивайте о переопределении, фактическом типе объекта и поведении во время исполнения.

Не отвечайте «сработает, ведь фактически там наследник», не уточнив статический тип переменной. И не считайте текст диагностики `javac` частью нормативной спецификации: стабильное правило — **допустимость или запрет конструкции**, а сообщения компилятора зависят от реализации и версии.

## Воспроизводимые примеры и ограничения проверки

Приведённые выше фрагменты иллюстрируют отдельные правила, а **полный многофайловый пример** находится в [CORE-ACCESS — рабочие и отрицательные сценарии](../../examples/core/access/README.md). Это реальные пакеты `api` и `client`, положительные проверки и восемь независимо компилируемых отрицательных вариантов. В исходниках примерного проекта методы `Child.ownValue()`, `Child.otherChildValue(...)` и `Child.touchUsingSuper()` разделяют операции, объединённые в упрощённом фрагменте `Child.ok` выше.

Из корня репозитория на **JDK 21**:

```sh
bash examples/core/access/verify.sh
```

Скрипт сначала вызывает `javac --release 21` для работающей программы и запускает `client.AccessDemo`, затем отдельно проверяет каждый из восьми запрещённых вариантов. Положительный исход — `CHECK PASSED`, для каждого отрицательного случая — ненулевой exit code `javac` с диагностикой, далее `ALL EXPECTED OUTCOMES OBSERVED`. На Windows без Bash порядок команд и способ проверки `$LASTEXITCODE` описаны в [README примера](../../examples/core/access/README.md). Сам по себе ненулевой exit code не доказывает ожидаемую **причину** ошибки: диагностику нужно сопоставлять с JLS 21.

## Границы темы и дальнейшее чтение

- [CORE-CLASSES](classes.md) — класс, объект, `this`, конструкторы, фабрики и инварианты.
- [CORE-TYPES](types.md) — объявленный тип ссылки и фактический объект.
- [CORE-CONVERSIONS](conversions.md) — приведения типов, в том числе почему cast меняет статическую проверку выражения.
- [CORE-PARAMS](parameters.md) — передача значения ссылки и разделяемый объект.
- **Следующая тема:** [CORE-INHERITANCE](inheritance.md) — overriding, dispatch и hiding. **Интерфейсы:** [CORE-INTERFACES](interfaces.md). **Вложенные классы:** [CORE-NESTED](nested-classes.md). **Ещё не опубликованы:** `CORE-IMMUTABLE`, `CORE-MODULES`, `CORE-SERIAL`, `SPR-DI` и совместимость бинарного API.

Последние темы важны для продвинутых случаев, но их не следует выдавать за покрытые этой статьёй. **JPMS:** в именованном модуле внешний код обычно должен читать модуль и иметь доступ к экспортированному пакету; один `public` не обещает доступ из любого модуля. `exports` для обычного использования и `opens` для рефлексии — разные вещи ([JLS 21 §7.7](https://docs.oracle.com/javase/specs/jls/se21/html/jls-7.html#jls-7.7)). **Reflection:** условия глубокой рефлексии определяются Java API и модулями; `private` не является универсальной защитой от всех механизмов запуска. **Совместимость:** изменение доступа опубликованного члена может повлиять не только на исходную компиляцию, но и на бинарное связывание; отдельная тема — JLS §13/JVMS, здесь не обещается полное объяснение.

**Связанный runtime-механизм:** [CORE-REFLECTION](reflection.md) показывает, почему `getDeclaredMethod` может найти private метод, но `invoke` запрещён по access checks; отдельно разбираются nestmates, `canAccess`/`trySetAccessible` и реальный JPMS `exports` vs `opens`. [CORE-ANNOTATIONS](annotations.md) объясняет, как `@Target` и `@Retention` влияют на доступность *метаданных*, но не заменяют модификаторы доступа JLS.
