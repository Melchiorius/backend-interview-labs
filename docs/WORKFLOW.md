# Процесс разработки и проверки материала

**Статус:** процедура исполнения [ролевой модели](ROLE_MODEL.md) для учебных статей, больших примеров и упражнений. Основные нормы остаются в [AGENTS.md](../AGENTS.md), технический контракт — в [EXERCISE_AND_TESTING_STANDARD.md](EXERCISE_AND_TESTING_STANDARD.md). Этот документ не меняет принятых технологических решений.

## Источники истины и условия старта

- `main` и конкретный **base SHA** определяют состояние файлов для начала работы. Перед правкой повторно сверять актуальный `main`; не считать ранее прочитанную версию постоянной.
- [CURRICULUM](CURRICULUM.md) — **что может входить в базу**; [COVERAGE](COVERAGE.md) — **что существует и проверено**; [ROADMAP](ROADMAP.md) — необязательные маршруты чтения, **не** план обязательного прохождения.
- `AGENTS.md` определяет качество текста, исследование JLS/JVMS/API/интервью и ограничения технических гарантий.
- Задачи и доказательства работы фиксировать в Issues/PR, не полагаясь на память переписки. Не обещать автору результата команды, не выполнявшейся фактически.

## Этапы и контрольные точки

| Gate | Ответственные | Достаточное свидетельство | Следующий шаг |
|---|---|---|---|
| **G0 — задача определена** | 00 | Issue: ID темы, вопрос читателя, границы, зависимости, критерии успеха, base SHA, ответственные роли | 01 |
| **G1 — полнота исследована до текста** | 01; оценка scope — 00 | `docs/plans/<ID>.md`: нормативные и интервью-источники, матрица P0/P1/P2, ошибки компиляции и прочие контрпримеры, существенные связи, ограничения, версия Java | 02/03 |
| **G2 — материал реализован** | 02 и при необходимости 03 | Статья с P0-ответами; code/tests только при предметной необходимости; ясные контракт и команды; локальные ссылки; фактические результаты запуска и известные непроверенные случаи | 05 |
| **G3 — редакционная согласованность** | 05 | Проверены ясность, роли участников примера, терминология, навигация и обратные ссылки; визуализацию отмечать только если открывали в целевой среде | 04 |
| **G4 — независимое ревью** | 04 | Проверка на конкретный HEAD SHA: научно-техническая точность, соответствие исследованию P0/P1/P2, кодовые/компиляционные контрпримеры, ограничения гарантий тестов, отсутствие ложных статусов; вердикт и блокеры | 00 |
| **G5 — решение о публикации** | 00 — решение и merge без отдельного одобрения владельца | Актуальный HEAD SHA, G4 по применимому содержанию, CI/проверки без домыслов, решённые blockers, обозначенные остаточные риски, зафиксированное решение 00 | Интеграция |
| **G6 — сверка после merge** | 06 и ответственная за содержание роль | В `main` есть ожидаемые файлы, ссылки и статусы; `COVERAGE` отражает реализацию/проверки, Issues/PR актуальны; отсутствие нового green CI фиксируется как непроверенное | Следующий Issue |

G0–G6 — название контрольных состояний, не новая система автоматизации и не требование создавать отдельный PR на каждый шаг. Для исправления опечатки возможен облегчённый путь. Для новой содержательной статьи G1/G4 обязательны; при изменении содержания G4 обновляется.

## Рабочий маршрут

1. **00 создаёт Issue.** Указывается минимум: название/ID, зачем читателю материал, объём P0, зависимости и границы, исполнители, критерии готовности, текущий base SHA, соответствующие документы. Договорённости сверх `AGENTS.md` фиксировать явно.
2. **01 исследует ДО текста.** Начать с [SOURCE_REGISTRY](SOURCE_REGISTRY.md), далее адресно уточнить спорное. Отделить нормативные источники (JLS/JVMS/API) от пояснений и неофициальных подборок. Передать матрицу 02/03 и 04.
3. **02 пишет теорию; 03 делает оправданную практику.** Поддерживать однозначные ссылки теория ↔ код ↔ README упражнения ↔ тесты. Примеры могут быть встроенными и не обязаны породить самостоятельную задачу. Для concurrency учитывать interruption, исключения, освобождение ресурсов и недетерминизм.
4. **05 проверяет текст и навигацию.** Перед схемой должен быть указан состав участников и смысл стрелок. Не выдавать простое чтение Markdown за реальное тестирование Mermaid в IntelliJ/Obsidian.
5. **04 проверяет интегрированную версию.** В ревью указывает полный HEAD SHA и применённые источники/команды. Для блокера: место, воспроизводимый контрпример, требуемый результат. Если один человек исполнял 02/03 и 04, назвать проверку самопроверкой, а не независимой.
6. **При правках после review** автор указывает исправления и новый HEAD SHA. 04 повторно проверяет затронутую область; старый вердикт не распространяется автоматически на изменённый код/текст. Конфликты и существенные изменения base должны быть рассмотрены перед публикацией.
7. **00 фиксирует состояние** `ready / blocked / deferred` с основаниями и **самостоятельно принимает решение о merge** подготовленного PR, не запрашивая одобрения владельца для каждого объединения. Право делегировано владельцем на постоянной основе; обязательные проверки и неустранённые блокеры сохраняют силу. Не требуется останавливать обычную работу ради повторного согласования уже принятых стандартов.
8. **06 сверяет после объединения** реальное содержимое `main`, пути, `COVERAGE`, Issue и PR. Не менять тему или приоритет самостоятельно. Возникающие пробелы — отдельная задача для 00/01.

## Передача эстафеты: обязательный завершающий блок каждого отчёта

**Отправитель сам определяет следующую роль и оформляет передачу** по [норме AGENTS](../AGENTS.md#обязательная-передача-эстафеты-между-ролями-0006). Это относится к содержательным GitHub-комментариям и review всех ролей 00–06 — в том числе к PASS/CHANGES, G5-публикации, G6-сверке, приостановке и повторному назначению. Роль 06 больше не обязана вручную собирать адресатов для каждого завершённого отчёта.

В конце GitHub-отчёта используйте шаблон (текст полей заполняется реальными данными):

```text
### Передача эстафеты
Кому: 04 — Independent Reviewer
Что сделать: выполнить независимое G4 по PR #92 на проверенном HEAD <полный SHA>.
Передать: оператор пересылает прямую ссылку на этот комментарий после публикации.
```

**В чате после публикации** (а не до получения GitHub URL) завершить ответ готовой строкой:

```text
Кому передать: 04 — Independent Reviewer.
Действие: G4 PR #92, HEAD <полный SHA>.
Ссылка для передачи: https://github.com/OWNER/REPO/pull/92#issuecomment-<реальный ID>
```

Верхнее `Кому: NN` в адресном GitHub-комментарии по-прежнему допустимо и полезно; **обязателен также последний блок**, чтобы получатель и оператор видели эстафету без поиска по середине отчёта. Если нет следующего действия: `Кому: никому. Причина: ...`, а в чате `Передача не требуется`. Если требуется решение о следующей роли — адресный вопрос координатору 00. Если два независимых адресата — два комментария и две прямые ссылки. Не выдумывать SHA, результаты CI, URL комментария и статусы gates.

## Требования к Issue, PR и ревью

**Issue**: ID, вопрос/цель, границы, зависимые статьи, первичные требования, роль-исполнитель, base SHA, критерии приёмки, известные риски.

**PR**: ссылка на Issue, base и HEAD SHA, затронутые файлы, существенные решения, существующие локальные ссылки, результаты *фактически запущенных* команд (или `not run`), ожидаемые и не проверенные свойства, изменения `COVERAGE`. Не утверждать, что все P0 закрыты, пока план и готовый материал не сопоставлены.

**Review**: идентификатор проверяемого SHA, степень независимости ревьюера, `APPROVE / CHANGES REQUESTED / COMMENT`, блокеры с точными местами, результат повторной проверки после поправок. Формальный статус GitHub `closed` не доказывает `merged`: сверять наличие изменений в `main`.

**Статусные формулировки:** `planned`, `implemented`, `verified`, `requires expansion`, `unknown` относятся к материалам, не к уровню знаний человека. Техническое `verified` (CI/команда) не доказывает полноту для собеседования. Непроверенное не выдавать за провал или успех.

## При конфликтах и обнаружении пробелов

- Сначала проверить фактический base/HEAD, содержимое файлов и область действия решения. Не делать force-push в общие ветки.
- Содержательный спор 01/02/03 → техническая проверка 04 → координационное решение 00; спор о полномочиях/политике → владелец. Роль 06 фиксирует историю и технический факт, но не голосует за математическую/языковую истину.
- Новая зависимость от ещё отсутствующей статьи: дать минимально необходимое объяснение на месте, отметить ID пробела в `COVERAGE`, не делать фиктивную ссылку.
- Если причина технической неисправности не ясна, действовать по [DECISION_AND_WORKFLOW](DECISION_AND_WORKFLOW.md): после двух безрезультатных попыток пересмотреть гипотезу, не запускать миграцию сборки «для лечения» единичной ошибки.

## Границы этого регламента

Не менять Java 21 и Gradle без отдельного решения. Не превращать базу в LMS. Не создавать ритуальные тесты, диаграммы, PR и упражнения на каждую мелочь. Схемы и код должны помогать читателю, а не подтверждать наличие чекбокса. **Действующий уровень требований считается достаточной исходной базой:** новые правила вводить при конкретной обнаруженной проблеме и с обоснованием, не расширять регламент профилактически.
