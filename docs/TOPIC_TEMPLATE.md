# Шаблон содержательной статьи

> Этот файл — ориентир для автора, **не обязательная форма с пунктами для заполнения**. Удаляй ненужные разделы; не допускай пустых и формальных абзацев. Статья должна быть понятна человеку, который открыл её без преподавателя.

ID темы: `CON-...` (если есть в каталоге) · Java: 21 (или иная применимая версия) · Связанные материалы: [название](относительный-путь.md)

# Название понятия или механизма

**Что это.** Одно точное определение с расшифровкой новых терминов.

**Зачем.** Конкретная проблема и когда возникает; не писать пространное введение.

## Как работает

Опиши модель, действия и гарантии, причины выбора конструкции. Для структуры данных — устройство и операции; для алгоритма — инвариант, шаги и сложность; для framework — жизненный цикл и архитектурную идею.

**Схема, если она проясняет механизм лучше текста.** Mermaid или переносимая иллюстрация; обозначения должны быть расшифрованы. Не дублируй схему тремя абзацами.

## Пример и проверка

Короткий фрагмент с пояснением существенных строк располагается **прямо здесь**. Отдельные .java-файлы и упражнения добавлять только для большого связного примера или полноценного задания. Ссылки давать только на существующие файлы; команда запуска нужна только для действительно исполняемого примера.

## Гарантии, ошибки, альтернативы

Что обещает спецификация/API, чего не обещает, типичная ошибка с конкретным контрпримером. Когда применить другой механизм.

## Дополнительная глубина (по необходимости)

Не нужно создавать отдельные разделы для всех трёх уровней. Если углубление короткое, помести его **после основной идеи** в сворачиваемый блок Obsidian:

```markdown
> [!note]- Углубление: особенности реализации (Senior)
> Здесь содержится необязательная информация.
```

Если углубление достаточно самостоятельное, лучше отдельная связанная статья, а не гигантский блок. Основной текст всегда остаётся понятным без этих деталей. В GitHub callout может **не сворачиваться**; не скрывай критическую информацию. Акценты выделяй умеренно; не полагайся на цвет как единственный смысловой сигнал.

## Связанные знания и источники

Короткие ссылки на необходимые понятия и первичные источники. Все ссылки относительные, когда это файлы репозитория.

---

**Редакторская проверка:** человек, впервые открывший статью, может определить термин, понять принцип, найти и запустить пример и вернуться к тексту после ошибки. Нет необъяснённых терминов, расплывчатых обещаний, лишних слов, искусственного ограничения длины, сломанных ссылок и нарисованной вместо объяснения бессмысленной схемы.

## Зависимости и перекрёстная навигация

Если статья использует важный термин из другой **уже существующей** статьи, в момент его первого содержательного употребления дать **рабочую относительную Markdown-ссылку** с кратким пояснением, зачем требуется это понятие. Для комплексного алгоритма перечислить все непосредственные теоретические зависимости, а не только одну основную; не включать весь транзитивный граф. У примеров Java и заданий должны быть обратные ссылки на этот материал в комментариях и README. Неразработанные статьи — в реестре пробелов, а не как битые ссылки.

Ссылки пополнять при последующих итерациях разработки базы: возвращаться к старым статьям, когда появляется ранее отсутствовавший материал. Не создавать отдельные заметки ради одной микромысли.
