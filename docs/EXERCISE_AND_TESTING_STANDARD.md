# Стандарт учебного задания, тестов и IDE

Статус: проектная спецификация; **не утверждает, что эта инфраструктура уже создана**. Связано с [архитектурой курса](COURSE_ARCHITECTURE.md) и [реестром](COVERAGE.md).

## Контракт задания
Каждое упражнение имеет стабильный ID (например, `EX-CON-SEM-01`), prerequisites и ссылку на статью. В директории задания: `README.md` (требования, инварианты, API, ограничения, запуск, критерии), `src/main/java/` (компилируемая заготовка), `src/test/java/` (JUnit Jupiter), `build.gradle.kts` или единое конфигурирование из корня. Решение отдельно; не подсовывать готовый ответ до самостоятельного опыта.

### Уровни обучения тестированию
1. Прочитать примеры и существующие тесты.
2. Исправить дефект, подтвердить регрессию тестом.
3. Добавить boundary/exception tests.
4. Самостоятельно спроектировать тесты по контракту.
5. Отличить unit, integration, concurrency и performance tests; объяснить ограничения каждого.

## JUnit 5 + Mockito
- JUnit Jupiter — базовая тестовая библиотека; Mockito + `mockito-junit-jupiter` и `MockitoExtension` там, где уместна изоляция зависимости.
- Ставить Mockito в тестовый classpath, не добавлять в runtime production-кода.
- Изолировать внешние системы моками, но **не подменять настоящие потоки/семафоры моками при проверке их синхронизации**.
- Моки не доказывают корректность конкурентных interleavings; тесты не должны завязываться исключительно на `verify` вызовов, когда важнее observable state и контракт.
- Учить dummy/stub/fake/mock/spy; выбирать двойник по назначению. Не мокать всё подряд.
- Не завышать уверенность: unit-тесты, включая конкурентные, не являются формальным доказательством корректности.

## Изоляция и запуск
Желаемый путь: один Gradle-подпроект на **независимое упражнение**, а не на статью. Упражнение должно иметь автономные компиляцию, тесты, ресурсы и простой запуск без сборки всех независимых упражнений.
Пример предполагаемой команды **после создания подпроекта**:
```powershell
.\gradlew.bat :exercises:concurrency:semaphore-limited-service:test
.\gradlew.bat :exercises:concurrency:semaphore-limited-service:test --tests "*LimitedServiceTest"
```
Сейчас эти команды — целевая форма, не действующие команды существующего main. Gradle выполняет необходимые зависимости задачи; «только один модуль» не означает ноль зависимостей.

Не включать десятки учебных подпроектов в обычный `build` без явного решения. Отдельно определить динамическое подключение подпроектов и стоимость конфигурации Gradle, когда появятся реальные метрики. Не внедрять сложную build-logic заранее.

## IntelliJ IDEA
- Разделяемые конфигурации запуска в `.run/*.run.xml` — задача пилота; одна кнопка для тестов конкретного упражнения.
- Проверять конфигурации на чистом клоне и не коммитить пользовательские абсолютные пути, секреты или machine-specific JDK locations.
- Документировать работу через Gradle Tool Window и JUnit runner; CLI — эквивалентный резервный путь.
- Следить, чтобы готовые примеры не зависели от состояния IDE.

## CI, student и reference
- Основной CI обязан собирать эталонный код и выполнять его тесты.
- Студенческие заготовки могут компилироваться, но функциональные тесты намеренно не проходят до решения: не делать это причиной красного main CI.
- Для режима student выбрать отдельную task / source set / CI job или другой явно задокументированный механизм в пилоте; не заявлять, что он уже существует.
- Параллельный запуск независимых модулей (в том числе CI matrix) — **будущее расширение**, не путать с изолированным локальным запуском.
- Для синхронизации использовать `CountDownLatch`, `CyclicBarrier` и другие контролируемые примитивы вместо `Thread.sleep` как средства упорядочивания. Таймауты — для предотвращения бесконечных зависаний. Проверять инварианты, исключения, отмену, освобождение ресурсов.
- Результаты `BUILD SUCCESSFUL` и число тестов записывать только после фактического запуска.

## Эталонное упражнение-пилот: EX-CON-SEM-01
Ограниченный внешний сервис: одновременно не более N операций, корректное освобождение permit в `finally`, поведение при исключениях, interruption, таймаут, отсутствие бесконечных блокировок. Включить:
- теоретическую статью CON-SEM;
- разобранный рабочий пример;
- компилируемую заготовку без готовой логики;
- JUnit-тесты на инвариант ограничений и ошибки;
- Mockito для имитации удалённого API (если нужен), но реальный Semaphore;
- reference-решение, независимый Gradle task и общую CI-проверку;
- самопроверку и сравнение Semaphore/Lock/BlockingQueue.

## Определение готовности задания
Все ссылки рабочие; student и reference запускаются указанными командами; тесты реально выполнены; тесты демонстрируют существенные требования; IntelliJ-конфигурация переносима; README фиксирует альтернативы, ограничения и непроверяемые тестами свойства.
