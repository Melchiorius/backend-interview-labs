# Стандарт крупных Java-примеров и самостоятельных задач

Этот документ описывает **практику**, не требует создавать задачу для каждой статьи. Авторские требования к содержанию: [AGENTS.md](../AGENTS.md).

## Когда выносить код
- **Небольшой фрагмент**, демонстрирующий один метод/свойство, — прямо в Markdown.
- **Крупный связный пример** (несколько методов/классов, сложная последовательность, реализация алгоритма) — в Java с командой запуска; пример может иллюстрировать несколько статей.
- **Самостоятельная задача** — отдельно от примера, если она приносит пользу: README, заготовка, JUnit-тесты, необязательное эталонное решение.

## Контракт отдельной задачи
README рядом с заданием содержит: ID (если назначен), условие с входами/выходами и инвариантами, ограничения, локальные ссылки Obsidian на все прямо необходимые статьи, расположение заготовки, конкретную команду тестирования, описание того, что тесты проверяют и чего не гарантируют.

В начале Java-файла примера/заготовки/эталона — короткий блок, например:
```java
// Theory: knowledge/03-concurrency/semaphore.md
// Theory: knowledge/03-concurrency/thread-interruption.md
```
**Эти пути условные**: при публикации они должны вести к реальным файлам. Это пути **от корня репозитория**, не автоматически кликабельные ссылки IDE. Для README, который расположен по пути `exercises/concurrency/semaphore-limited-service/README.md`, относительная Markdown-ссылка к `knowledge/` начинается с `../../../knowledge/`. В Obsidian можно также применять wikilinks с явным путём от корня vault. Действительные пути проверять, а не копировать по аналогии вслепую.

Если код комплексный, указать **все существенные непосредственные теоретические зависимости** (включая темы тестирования в тестах, если без них непонятна логика); не перечислять транзитивно всю Java.

## Проверка решения
- JUnit Jupiter — базовый инструмент. Mockito + MockitoExtension — только там, где оправданно имитировать внешнюю зависимость или проверять взаимодействие; реальную синхронизацию проверять с реальными примитивами.
- Проверять обычный сценарий, граничные случаи, ошибки и заявленные инварианты. Тесты, особенно конкурентные, **не доказывают** корректности при всех расписаниях потоков.
- В конкурентных тестах использовать координацию (`CountDownLatch`, `CyclicBarrier` и т. п.), ограниченные ожидания, корректное освобождение ресурсов. `Thread.sleep` не использовать как основной способ синхронизации.
- Не требовать mock или отдельный набор тестов, если предметная задача этого не обосновывает. Тесты самих эталонов обязаны выполняться в общей CI.

## Независимый запуск
**Неизменное требование:** читатель должен запускать проверки *только выбранного упражнения*, не компилируя все независимые упражнения. Конкретная схема — один Gradle-подпроект, отбор тестов, source sets или иной простой механизм — **решение пилота**, а не обязательная структура всего курса.

Будущий пример команды для отдельного подпроекта (**пока не существует**):
```powershell
.\gradlew.bat :exercises:concurrency:semaphore-limited-service:test --tests "*LimitedServiceTest"
```
Gradle по-прежнему может собрать зависимости данной задачи. Предусмотреть эквивалентный запуск через CLI и удобную IntelliJ run-конфигурацию **без абсолютных путей**; не создавать по конфигурации на микрофрагмент.

Незавершённые student-заготовки не должны делать красным основной CI эталонов. Способ разделения student/reference проверить на пилоте. Эталоны в обычном скачиваемом репозитории доступны читателю: не строить искусственную систему их «секретности». Обязательно отличать **выполнение тестов отдельной задачи** от распределения тестов по исполнителям CI.

## Минимальная приёмка
На чистом клоне с указанными JDK и инструментами читатель без преподавателя находит статью → большой пример или упражнение → заготовку → команду тестов конкретной задачи → понятный результат → работающую ссылку обратно к теории. Тесты и команды считать проверенными **только после реального запуска**; не обещать полноценный offline-build без проверки первоначальной загрузки зависимостей и кеша.
