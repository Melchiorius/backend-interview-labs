# Протокол передачи задач между ролями (пилот v1)

**Ответственная роль:** 06 — Research Operations. Это дополнение к [WORKFLOW](WORKFLOW.md), [ROLE_MODEL](ROLE_MODEL.md) и [AGENTS](../AGENTS.md); изменения учебного содержания не предусмотрены.

## Принцип работы

1. Роль выполняет задачу и **ОБЯЗАТЕЛЬНО при любом результате, кроме явно объявленной общей остановки всей работы**, фиксирует результат в GitHub Issue/PR и публикует **один** JSON-блок с маркером языка **backend-handoff** в комментарии того Issue, где выполняется передача. Это условие завершения ролевой работы даже при CHANGES, BLOCKED, частичном результате или отсутствии готового следующего шага.
2. [Python-диспетчер](../tools/role_dispatcher.py) считывает комментарии через официальный GitHub REST API, проверяет автора GitHub, целевой Issue, PR, HEAD SHA и заявленные машинно проверяемые условия.
3. Если условия выполнены, создаются локальные файлы **.dispatcher/inbox/00** … **.dispatcher/inbox/06** с готовыми текстами для соответствующих чатов. Ранее доставленное событие не дублируется (SQLite).
4. Необязательный параметр **--publish** дополнительно записывает адресные комментарии для получателей в исходный GitHub Issue. По умолчанию GitHub **не изменяется**.
5. **Обычные чаты ChatGPT не активируются сами**: оператор должен перенести сообщение из inbox в нужный чат либо роль при следующем запуске прочитает опубликованное сообщение в Issue. Управления HTML интерфейсом ChatGPT нет.

Для облегчения ручной доставки добавлен [отдельный инструмент](MANUAL_CHAT_DELIVERY.md), который открывает адрес выбранного чата и копирует подготовленное сообщение в буфер обмена Windows. **Вставку и отправку выполняет человек**. Скрипт не читает ответы ChatGPT и не использует Selenium. Подтверждение отправки — только отдельной командой после реального действия пользователя.

## Инвариант: после любого результата следует передача

**ОБЯЗАТЕЛЬНОЕ ПРАВИЛО ЗАВЕРШЕНИЯ РАБОТЫ** действует для всех ролей 00–06 и всех исходов. Завершить задачу только текстовым отчётом, GitHub review, PR или сообщением «передано» **ЗАПРЕЩЕНО**. Сначала опубликуйте фактический результат/вердикт, затем подготовьте валидный `backend-handoff`; проверяйте, не создано ли уже эквивалентное событие.

| Результат | Поле `action` | Получатель и смысл |
|---|---|---|
| Следующий этап действительно готов | `READY` | Роль, которой назначено следующее конкретное действие |
| `CHANGES`, необходимость исправить или подтвердить | `QUESTION` | Автор исправлений/проверяющий; `message` описывает работу и критерий |
| `BLOCKED`, зависимость не выполнена | `BLOCKED` | Роль, способная устранить блокер, либо 00; чёткая причина |
| Работа частична / не определён следующий этап / нужен выбор | `QUESTION` | Координатор 00 для решения о продолжении |
| Всё содержательно завершено, новых задач нет | `QUESTION` от ролей 01–06 к 00; решение 00 | Роль 00 фиксирует новые задачи либо **явную общую остановку**; пустой круг 00↔06 не создавать |
| Общая остановка всей работы, явно объявленная владельцем или зафиксированная решением 00 | *Не нужен* | Единственное штатное исключение; оформить факт остановки в GitHub |

**Внимание:** `PASS`, `CHANGES`, `WAITING` — описательные статусы, не допустимые значения `action` в v1. Вложенное поле `issue` **обязательно совпадает с Issue комментария**. Событие нужно публиковать в целевом Issue, если получатель работает в другом Issue (например, G3 CHANGES → Issue 02); использовать новый `event_id` и, при ссылке на PR, актуальный полный `head_sha` и предикаты `requires`. Не объявляйте `READY`, если не выполнены gate-предпосылки, и не используйте handoff как фиктивное разрешение merge.

Если GitHub недоступен, сообщите об ошибке, а передачу считайте **не выполненной** до записи комментария. Сценарий «нет следующего поручения» **не равен** общей остановке: это решение принимает 00/владелец.

## Формат

После обычного человеческого отчёта роль оставляет блок. Ниже — **демонстрационный** Issue #67, не реальное поручение:

~~~markdown
```backend-handoff
{
  "protocol": "backend-labs-handoff/v1",
  "event_id": "demo-g0-task-0001",
  "from": "00",
  "to": ["01"],
  "issue": 67,
  "gate": "G0",
  "action": "READY",
  "message": "Исследуй тему, подготовь матрицу P0/P1/P2 и отдельный PR. Перед началом сверь main и Issue #67.",
  "requires": ["issue_open"]
}
```
~~~

**Не публикуйте демонстрационный блок.** Перед каждым новым поручением используйте фактические номера и новый уникальный идентификатор события.

| Поле | Значение |
|---|---|
| protocol | Ровно **backend-labs-handoff/v1** |
| event_id | Уникальный неизменный ID, от 8 до 96 символов из букв латиницы, цифр, точки, дефиса и подчёркивания |
| from | Роль-отправитель: **00** … **06**; значение заявляет автор, а не подтверждает диспетчер |
| to | Непустой массив ролей-получателей, без дублей и отправки самому себе |
| issue | Номер того Issue, под которым расположен комментарий |
| gate | Контрольная точка G0 … G6 |
| action | **READY** (передача), **QUESTION** (вопрос), **BLOCKED** (блокер) |
| message | Предметное поручение: что сделать, где материалы, критерий готовности; максимум 6000 символов |
| pr | Необязательный номер существующего PR |
| head_sha | Полный 40-символьный HEAD SHA PR, который будет сверяться с GitHub |
| requires | Допустимые условия: **issue_open**, **pr_open**, **pr_merged**, **head_matches**, **ci_success** |

Условия проверяются только если перечислены в **requires**. При указании PR и HEAD SHA диспетчер **всегда** проверяет их совпадение. Для проверок PR укажите **pr**; для **head_matches** и **ci_success** дополнительно нужен **head_sha**. Условие **pr_merged** требует фактической интеграции; **ci_success** сверяет Check Runs на конкретном SHA и при неопределённости блокирует передачу. При squash merge HEAD исходного PR и squash SHA в main — **разные** идентификаторы.

**Ни одно условие не подтверждает содержательную корректность JLS, полноту P0/P1/P2 или независимое ревью.** Решение о прохождении G1/G3/G4/G5 остаётся за соответствующими ролями и 00. Сообщение о блокере или вопросе отправляйте с действительным event_id, но не выдавайте его за одобрение gate.

## Рекомендуемый маршрут

| Этап | Источник → получатель | Предпосылки |
|---|---|---|
| G0 | 00 → 01 | Issue поставлен, scope и base SHA определены |
| G1 review | 01 → 04 → 00 | 01 публикует план; 04 оставляет независимое заключение и **отдельный валидный `backend-handoff`** в Issue для решения 00. Один лишь текстовый review не активирует следующую роль. |
| G1 принято | 00 → 02 и, если нужна практика, 03 | 00 явно принял исследовательскую матрицу; G1-review PASS от 04 не заменяет этого решения |
| G2 | 02/03 → 05 | Теория и/или практика готовы к редактуре на интегрированном HEAD; **обычный комментарий о завершении недостаточен** — на целевом G3 Issue нужен блок `backend-handoff` для 05. Перед созданием проверять, нет ли уже такой передачи от другого автора. |
| G3 | 05 → 04 при **PASS**; 05 → 02/03 при **CHANGES** | Любой итог G3 требует явного события в целевом Issue. **CHANGES**: адресное поручение авторам интегрировать патч и вернуть единый HEAD для повторного G3 (можно `action=QUESTION` или `BLOCKED`; такого action как `CHANGES` протокол не определяет). **PASS**: передача независимому 04 на точный интегрированный HEAD. Отзыв и текст «прошу интегрировать» без блока `backend-handoff` не активируют чат. |
| G4 | 04 → 00 или авторам на доработку | Независимый вердикт на точном HEAD SHA |
| G5 | 00 → 06 | Merge выполнен после проверок, известен SHA main |
| G6 | 06 → 00 | Реальный main и статусы синхронизированы |

## Запуск на Windows (PowerShell)

Python **3.10+**, только стандартная библиотека; сторонних пакетов не требуется.

~~~powershell
# Из корня клонированного репозитория
$env:GITHUB_TOKEN = "<ваш fine-grained token>"
python tools/role_dispatcher.py --issue 67
python tools/role_dispatcher.py --interval 120

# Опционально: адресные комментарии в GitHub (требует Issues: write)
python tools/role_dispatcher.py --interval 120 --publish

# Автономная проверка без сети и GitHub-токена
python -m unittest discover -s tools/tests -v
~~~

При запуске без **--interval** выполняется один проход. С **--interval 120** процесс опрашивает GitHub каждые 120 секунд **только пока запущен**. Параметр **--issue N** позволяет читать один Issue, даже если он закрыт; без него опрашиваются открытые Issues. Результаты сохраняются в **.dispatcher/**, который следует исключить из Git.

Токен с минимальными разрешениями: **Issues: read**, **Pull requests: read**, **Checks: read** (для проверки CI), **Issues: write** только при **--publish**. Никогда не добавляйте токен в файлы репозитория, комментарии, исходники и переписку. Для приватного репозитория необходим доступ.

## Безопасность и ограничения

- Принимаются комментарии только от доверенных GitHub-логинов (**--allowed-actors**; по умолчанию владелец из owner/repo). Если все чаты пишут от одного аккаунта, заявленную роль **from** нельзя проверить независимо по GitHub-автору.
- Новый event_id обязателен при каждом изменении поручения; повтор с изменённым payload отвергается. При невыполненных предикатах событие ждёт следующего опроса.
- Диспетчер **не выполняет** содержимое message как программу, не запускает Java, не мержит PR и не утверждает независимость ревью.
- Публикации диспетчера имеют отдельный маркер доставки и не порождают повторную маршрутизацию.
- Автоматическая доставка **в существующие чаты ChatGPT** в эту версию не входит; переход к агентам на официальном OpenAI API потребует отдельной реализации и решения.


**Правило для ролей:** актуальные Issue/PR/HEAD и непройденные gates проверяются по назначению и нормативным инструкциям, а не по повторяющейся фразе в каждом доставленном поручении. Диспетчер прикладывает идентификаторы и ссылки, но не объявляет качество или завершение gate подтверждёнными.

## Опрос GitHub и доставка в активную роль по номеру вкладки Firefox

Для непрерывного локального запуска без Selenium используйте [ROLE_CYCLE.md](ROLE_CYCLE.md) и [role_cycle.py](../tools/role_cycle.py). На проверенной схеме пользователя 00–06 = вкладки №1–7. Процесс повторяет GitHub scan, выбирает вкладку роли через обычные клавиатурные сокращения и копирует поручение в буфер. **Пользователь сам нажимает Ctrl+V и Enter**, дополнительного подтверждения в терминале нет; статус `prepared` означает подготовку, а не доказанную отправку. Ответы ChatGPT Python **не читает**. Для следующего шага отправившая роль обязана создать **новый GitHub Issue comment** с одним корректным `backend-handoff` и новым event_id. Прочитанные факты GitHub и подтверждение человека не означают утверждения содержательного gate. Никакого самостоятельного merge и никаких OpenAI API вызовов в этом режиме нет.
