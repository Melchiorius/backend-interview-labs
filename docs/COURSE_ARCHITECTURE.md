# Архитектура курса Java Backend

Статус: проектное решение (документация; реализация ещё не выполнена). Базовая Java: 21.
См. [учебный каталог](CURRICULUM.md), [реестр покрытия](COVERAGE.md), [тестовую архитектуру](EXERCISE_AND_TESTING_STANDARD.md), [методику](STUDY_METHOD.md), [план](ROADMAP.md).

## Цель: система знаний, НЕ система управления обучением
Создать максимально полную, структурированную и расширяемую базу знаний Java Backend, а не приложение, управляющее траекторией ученика. Человек **сам** выбирает порядок, темп, глубину, необходимость повторного прохождения и практики. Репозиторий предоставляет информацию, ориентиры глубины, связи между понятиями, готовые демонстрации, задачи и проверки кода, но НЕ ведёт обязательные персональные оценки и не предписывает персональный маршрут.

**Принцип охвата:** лучше включить специализированный материал как необязательное углубление, чем потерять важную тему. Не следует смешивать полноту карты со требованием освоить всю карту за один проход.
**Принцип глубины:** не завышать уровень сложности и не объявлять тему «Senior» из-за её редкости или того, что отдельный вопрос оказался трудным. Отделять общеупотребимый минимум для Middle/Middle+ от действительно специализированного Senior-углубления. Это ориентиры для чтения, не аттестация человека.
**Повторное прохождение:** слои статьи должны оставаться полезными отдельно; читатель может освоить основу сейчас, а детали реализации — через год без переписывания материала.
Курс объединяет Obsidian-совместимые статьи, запускаемый код, самостоятельные задания и автоматические тесты.

## Единственный основной сценарий читателя

`Открыть статью → понять термин и механизм → открыть рабочий код → изменить/написать своё решение → запустить конкретные тесты → вернуться к статье → углубиться или выбрать другую тему.`

Никаких обязательных профилей, аккаунтов, прогресс-баров, заданного порядка, автооценки, персональной диагностики или обязательного прохождения тестов. **Система знаний должна быть полезной без автора и ассистента.** Каждая статья должна читаться отдельно; каждая задача должна объяснять запуск без обращения к чату.

## Редакционный стандарт: точность, компактность, наглядность
- **Термин → точное определение → как устроено / как работает → зачем нужно → пример → ограничения**. Каждый абзац обязан отвечать на определённый вопрос.
- Не допускать общих рассуждений, повторов, длинных вступлений, перечней терминов без объяснения или искусственного заполнения разделов.
- При объяснении алгоритма, структуры данных, последовательности событий, потока данных или состояний **предпочесть схему**, если она яснее текста. Нужны подписи, пояснение обозначений и при необходимости короткий пример.
- Схемы хранить рядом с материалами в переносимом формате: Mermaid в Markdown, SVG/PNG при необходимости. Проверить отображение в GitHub и Obsidian; диаграммы не должны содержать непроверенных технических гарантий.
- Небольшой код — в статье, если он поясняет одну мысль; полный рабочий пример — в исходном файле со ссылкой и понятной командой запуска.
- Обязательна достаточная глубина **смысла**, а не объём: спецификация поведения, внутреннее устройство, логика разработчиков API/фреймворка и типичные ошибки должны быть раскрыты без пропусков.
- Не устанавливать искусственные лимиты слов и обязательное число разделов; лучше разбить независимые вопросы на связанные короткие заметки, чем создавать длинную монолитную статью.
- Middle/Middle+/Senior — **необязательные читательские слои**, только где различие действительно полезно; без механического троекратного повторения определения.
- Проверка качества: удаление абзаца не должно терять существенное знание; добавление схемы должно реально уменьшать усилия понимания.
- Никакой документационной инфраструктуры ради инфраструктуры: существующие Markdown, Git, Gradle, JUnit, Mockito, IntelliJ достаточно для пилота. Не добавлять генераторы страниц, базы знаний или метаданные, пока не выявлена проверяемая потребность.

## Divide → Understand → Merge
1. **Divide:** делить предметную область на понятия, зависимости и небольшие законченные единицы; не создавать файлы автоматически по каждой строке каталога.
2. **Understand:** установить задачу, модель, терминологию, API, гарантии, ограничения, ошибки и альтернативы. Сначала полный разобранный пример, затем постепенная самостоятельная работа.
3. **Merge:** статьи явно показывают связи и сравнения; интеграционные примеры демонстрируют композицию. Читатель сам решает, когда применять и объединять знания.
4. **Depth:** материал размечен по глубине Middle / Middle+ / Senior; глубокие ответвления доступны, но их чтение необязательно для освоения базового слоя. Не превращать редкий нюанс в обязательное условие.
5. Дерево тем служит навигацией, **граф предпосылок** — подсказкой читателю, какие знания полезны для понимания, но не жёстким порядком обучения.

## Границы знания
- Отличать утверждение из JLS/JVMS, контракт Java API, подробность HotSpot/OpenJDK и гипотезу.
- Фиксировать версию Java; Java 21 — исходный baseline; новые API оформлять как отдельное расширение.
- Обязательно сопоставлять с альтернативами и производственными компромиссами, не обещать универсальности.
- Учёт покрытия фиксирует наличие и качество **материалов**, а не личное освоение пользователем. Успешная сборка демонстрирует техническую проверку, а не понимание.

## Планируемая структура (НЕ считать созданной)
```text
knowledge/           # Obsidian vault: карта знаний и статьи
  03-concurrency/
examples/            # эталонные демонстрации Java
exercises/           # изолированные задания с заготовками и тестами
solutions/           # отдельно доступные эталоны (конкретный способ размещения — решение пилота)
.run/                # разделяемые конфигурации IntelliJ
docs/                # архитектура, реестр, правила, roadmap
labs/                # УЖЕ существующие Gradle-подпроекты; сохраняются
```
Сейчас реально существуют `labs/concurrency`, `labs/collections`, `labs/jvm`, `labs/async`. Новые каталоги не создавать до проверки вертикального пилота. Отдельный Gradle-подпроект допускается для **упражнения**, когда это обеспечивает реальную изоляцию; не создавать подпроект для каждой теоретической страницы.

## Документы и ссылки
- Основной формат — UTF-8 Markdown, читаемый в GitHub и Obsidian.
- Основные ссылки — **относительные Markdown-ссылки** `[JMM](java-memory-model.md)`; Obsidian wikilinks факультативны, но не должны быть единственным способом навигации.
- Для каждой статьи: ID, версия, статус, prerequisite-ссылки (справочные, не принудительные), соседние темы, слои Middle/Middle+/Senior, модель проблемы, терминология, гарантии, примеры, контрпримеры, альтернативы, практика и первичные источники.
- Код НЕ дублировать большими фрагментами в нескольких документах: ссылка на конкретный файл в `examples/` или `labs/`, небольшой фрагмент только для пояснения.
- Для всех плановых материалов использовать [шаблон темы](TOPIC_TEMPLATE.md) и реестр покрытия; проверять относительные пути при PR.
- Стабильные ID тем, например `CON-SEM`, упражнений `EX-CON-SEM-01`; переименование файла не меняет ID.

## Многослойная статья
- **Middle — основной рабочий слой:** назначение, терминология, стандартный контракт и API, минимальные корректные сценарии, распространённые ошибки и выбор между обычными альтернативами.
- **Middle+ — инженерные нюансы:** граничные случаи, композиция с другими механизмами, диагностика, тестируемость, производственные компромиссы, управляемые исключения и отказы.
- **Senior / specialized — факультативное углубление:** сложные сценарии, ограничения масштабирования, внутренние детали реализации и редкие trade-offs **когда они действительно требуют такого уровня**, а не по одному лишь названию.
- Уровень назначать **конкретному подтезису или подразделу**, а не всей теме. Например, существование Semaphore и acquire/release — не Senior; углублённая конкурентная диагностика может быть специализированной.
- Разделы для базового прохода должны быть самодостаточными; сложный слой не должен быть необходим для их понимания.
- Для каждой области сохранять полноту карты, даже если подробные специализированные материалы будут написаны позже. Статус написания и глубина — независимые измерения.
- Практика факультативна и разная: прочитать готовый пример, найти дефект, дописать тест, реализовать свою версию; тесты проверяют код, не оценивают человека.

## Стратегия внедрения
Сначала полная карта покрытия и зависимости, но НЕ сотни пустых файлов. Инфраструктурный пилот (НЕ обязательная первая тема для читателя) — `CON-SEM`: статья Semaphore + демонстрация + заготовка задачи + JUnit/Mockito где уместно + отдельный запуск в Gradle/IDE + эталон + интеграционное сравнение. После проверки UX/CI — масштабирование шаблона.

## Границы пилота и неизвестное
- Не утверждать, что `Semaphore`, Mockito, изолированные упражнения или .run-конфигурации уже реализованы.
- Вопрос о размещении эталона (solutions/ либо отдельная ветка) пока открыт; исключить случайный доступ из student workflow.
- Изоляция запуска одного упражнения и **распределённое тестирование на нескольких исполнителях** — разные возможности; последнее планировать отдельно после стабильной локальной схемы.
- Обновлять [COVERAGE.md](COVERAGE.md) при каждом PR, меняющем содержание или статус.

## Непременное требование: независимость от автора

Считать отсутствие преподавателя и ИИ **нормальным состоянием**. Полезные дополнительные объяснения не должны быть недостающими обязательными частями курса. Пользователь должен самостоятельно открыть статью, уточнить термины по ссылкам, запустить код, выполнить задание и разобраться с результатом тестирования. Скачанный репозиторий должен быть достаточен для чтения и изучения, с явно документированными внешними предпосылками (JDK, инструменты и начальная загрузка зависимостей). Проверять самостоятельность на чистом клоне, а не в среде автора.

## Сквозные ссылки — навигация без преподавателя

Текст, код и самостоятельные задачи образуют двусторонние связи:
- **Статья → теория:** если определение, алгоритм или механизм зависит от другого материала, дать относительную ссылку на него в месте использования и короткое описание зависимости. Не заставлять читателя самостоятельно угадывать prerequisites.
- **Статья → практика:** дать ссылки на соответствующие рабочие примеры и задачи, когда они реально существуют.
- **Java → теория:** комментарий в начале каждого существенного примера, заготовки и эталона перечисляет все непосредственно используемые теоретические темы как пути от корня репозитория; для комплексного решения — все необходимые темы, а не одну «главную».
- **Задание → теория:** в README задачи использовать кликабельные относительные Markdown-ссылки на все эти материалы; возвращение от задачи к определению должно занимать один переход.

**Формат:** в Markdown — `[Мониторы](../03-concurrency/monitors.md)`, в Java — `// Theory: knowledge/03-concurrency/monitors.md` и другие строки `// Theory:`. Путь в комментарии Java — репозиторно-относительный, а не гарантированная гиперссылка IDE; кликабельность обеспечивает README. Примеры путей иллюстративны и не означают наличие этих файлов.

Связывать **существенные непосредственные зависимости**, а не все транзитивные знания вплоть до примитивных типов: иначе комментарии превратятся в шум. Проверять существование путей и синхронизацию списка при изменениях. Незавершённые статьи — в реестре пробелов; не выдавать недействительную ссылку за рабочую.
