## 3. Блокеры итоговой готовности

### B1 — COL-HASH: глубина механизма HashMap для Middle+/Senior (CH-05/06/07 P0; CH-10/15)

**Где:** [hash-collections.md:71–103](https://github.com/Melchiorius/backend-interview-labs/blob/e79869614bc5b1fda51ef1b6346bc1188998e308/knowledge/02-collections/hash-collections.md#L71-L103) и [tradeoffs.md:35–50](https://github.com/Melchiorius/backend-interview-labs/blob/e79869614bc5b1fda51ef1b6346bc1188998e308/knowledge/02-collections/tradeoffs.md#L35-L50). Материал не утверждает ложное универсальное O(log n), правильно маркирует 8/6/64 как I и предупреждает об условиях. Однако предупреждение без разбора алгоритма не позволяет ответить на типичные уточнения: почему doubling не требует нового hashCode каждого ключа; при каком количестве узлов именно putVal вызывает treeifyBin; почему балансированное дерево не обязательно даёт O(log n) поиска по равенству. Для указанного уровня это существенный P0 depth gap, не новое обнаружение прямой нормативной ошибки.

**Независимое I evidence:** pinned OpenJDK21 HashMap.java:
- [putVal L631–671](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L631-L671): индекс (n-1)&spreadHash, проверка hash и identity/equals, при добавлении **нового отличного** ключа в list bin с уже восемью узлами `binCount >= TREEIFY_THRESHOLD - 1` (попытка на девятом для этого пути), `++size > threshold` вызывает resize. Не обещать девятую вставку при других методах/размерах; существующий ключ не наращивает size.
- [resize L683–755](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L683-L755): обычно doubling (предел MAXIMUM_CAPACITY), при старой ёмкости 16 и новой 32 узел прежнего бакета i остаётся i либо переходит в i+16 в зависимости от `(storedHash & oldCap)`, например spread 1 и 17 (для этих малых hash values spread совпадает с исходным), оба имели index 1, после роста 1 и 17. В этом пути используются сохранённые хеши, а не обязательный повторный вызов пользовательского hashCode. Число записей 13 при default threshold 12 — отдельное условие роста при отсутствии иных triggers; слишком длинный bin может вызвать resize раньше.
- [treeifyBin L761](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L761-L775) — capacity <64 выбирает resize; [split L2297–2340](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L2297-L2340) — 6 относится к размеру части tree bin после split; обычное удаление имеет другой алгоритм (см. [removeTreeNode](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L2189)).
- [TreeNode.find L2017–2042](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L2017-L2042): сначала сравниваются hash, затем equality; если hash совпадает и Comparable не даёт различимого направления, поиск может рекурсивно посетить обе стороны. Tie-break при вставке не превращает поиск по equals в обычный поиск бинарного дерева по полному ключу. В худшем случае посещается O(m) узлов этого bin даже при постоянной цене hash/equals. **Локальный независимый probe §6** подтвердил число equals для absent lookup 17/33/68/129 при 16/32/67/128 не-Comparable ключах с hash=67. Это наблюдение OpenJDK, не нормативная гарантия числа сравнений; доказательство возможности линейного посещения даёт сам source, не четыре измерения.
- A [Java21 HashMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/HashMap.html), конструкторы и [newHashMap(int)](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/HashMap.html#newHashMap(int)): отдельно initial bucket capacity vs ожидаемое число mappings; newHashMap с Java19; не обещать абсолютного отсутствия resize из-за pathological collisions.

**Критерий устранения:** 02 добавляет в существующую статью пошаговый пример индекс/resize/split, точное условие putVal и различие split vs deletion, объяснение двух ветвей поиска и контрпример equal-hash non-comparable. Согласовать с tradeoffs, без переносимости конкретных порогов. 03 по решению 00 может добавить небольшое наблюдение счётчика equals и устойчивый логический пример (не приватная reflection, не фиксация layout/identity tie-break, не benchmark). Вариант с аналитическим контрпримером допустим при явной маркировке. 05 → 04 exact changed HEAD; 00 принимает решение. Не требовать расширения в JVM/JIT.

### B2 — COL-HASH/CONTRACTS/TRADEOFFS: LinkedHashMap и LinkedHashSet представлены ярлыками, не механизмом выбора

**Где:** [hash-collections.md:53,130–141](https://github.com/Melchiorius/backend-interview-labs/blob/e79869614bc5b1fda51ef1b6346bc1188998e308/knowledge/02-collections/hash-collections.md#L130-L141), [contracts.md:37–71](https://github.com/Melchiorius/backend-interview-labs/blob/e79869614bc5b1fda51ef1b6346bc1188998e308/knowledge/02-collections/contracts.md#L37-L71), [tradeoffs.md:112–126](https://github.com/Melchiorius/backend-interview-labs/blob/e79869614bc5b1fda51ef1b6346bc1188998e308/knowledge/02-collections/tradeoffs.md#L112-L126). Есть правильные слова encounter order и reversed, но нет отдельного механизма связей порядка и hashing, insertion vs access-order, cost iteration size vs capacity+size, контрпримера чтения как structural change и bounded LRU. Вопрос о сравнении HashSet/LinkedHashSet/TreeSet и HashMap/LinkedHashMap/TreeMap реально найден у teamlead, Chernyshov, Baeldung (см. §4). CH-13 исходно P1; **предлагаю 00 признать новый обязательный P0 для финальной готовности**, не менять принятую историческую матрицу. Для backend интервью это не экзотическая JVM тема.

**A evidence:** [Java21 LinkedHashMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/LinkedHashMap.html) class description и [constructor](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/LinkedHashMap.html#%3Cinit%3E(int,float,boolean)), [removeEldestEntry](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/LinkedHashMap.html#removeEldestEntry(java.util.Map.Entry)), [LinkedHashSet](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/LinkedHashSet.html), Sequenced API. Дополнительная двусвязная структура поддерживает порядок, обычная вставка/перезапись existing key не меняет insertion order, access-order перемещает accessed entry в конец (не каждый метод является access; views не изменяют порядок). Access-order get может изменять порядок и считается структурной модификацией; нельзя переносить HashMap replacement/iterator reasoning на эту реализацию. LinkedHashMap views обходятся O(size) независимо от capacity, HashMap O(size+capacity). LRU с `removeEldestEntry` — простая политика по числу записей, не TTL, не memory bound и не concurrent cache. LinkedHashSet.add existing не меняет обычный insertion order, Java21 addFirst/addLast позволяют явное перепозиционирование.

**Контрпример:** a,b вставлены; get(a) оставляет insertion [a,b], меняет access-order на [b,a]. При следующем put(c) и max size=2 access-order LRU удаляет b, получаем [a,c]. Для set обычный повторный add(1) сохраняет [1,67,2], addLast(1) даёт [67,2,1]. Независимый local probe §6 реально подтвердил эти состояния. Не проверять детерминированное CME как гарантию.

**Критерий устранения:** 02 добавляет связное объяснение с двумя режимами, cost and null/ordering policy, Java21 explicit positioning, LRU и оговорками, сравнение HashSet/LinkedHashSet/TreeSet и HashMap/LinkedHashMap/TreeMap в decision table. 03 — при назначении 00 компактный deterministic probe для порядка и eviction; никаких обещаний concurrent safety. 05 редакция, 04 повторное ревью по exact HEAD. Не требуется новый отдельный curricular ID/файл, если существующая статья достаточна.

class AuditProbe {
    static final class K {
        static int calls;
        final int id;
        K(int id) { this.id = id; }
        public int hashCode() { return 67; }
        public boolean equals(Object o) {
            calls++;
            return o instanceof K k && id == k.id;
        }
    }

        if (!Objects.equals(expected, actual))
            throw new AssertionError(expected + " != " + actual);
    }
    public static void main(String[] args) {
        for (int n : new int[]{16,32,67,128}) {
            var m = new HashMap<K,Integer>(256);
            for (int i=0;i<n;i++) m.put(new K(i),i);
            K.calls=0; check(null,m.get(new K(-1)));
            System.out.println("same-hash non-Comparable n="+n+
                " absent equals calls="+K.calls);
        }
        var insertion = new LinkedHashMap<String,Integer>();
        var access = new LinkedHashMap<String,Integer>(16,0.75f,true) {
            protected boolean removeEldestEntry(Map.Entry<String,Integer> e) {
                return size()>2;

            m.put("a",1); m.put("b",2); m.get("a");
