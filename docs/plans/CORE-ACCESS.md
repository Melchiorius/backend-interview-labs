## 1. Вопрос читателя, обещание и границы

**Вопрос:** какие обращения к типам, полям, методам и конструкторам допустимы из разных пакетов и подклассов, почему простой ответ «protected доступен наследникам» бывает неверен и как ограничение доступа помогает проектировать инкапсулированный API?

**Обещание:** читатель умеет (1) отличать три ключевых слова `public`, `protected`, `private` и отсутствие модификатора — package access; (2) предсказывать компиляцию в двух пакетах, особенно для `protected`-члена экземпляра; (3) отличать доступность типа от доступности члена и конструктора; (4) пояснять, зачем минимизировать публичную поверхность и сохранять инварианты, а не механически создавать getter/setter.

**Включено:** top-level и member types, поля, методы, конструкторы, граница пакета, private/nested на необходимом уровне, cross-package protected с qualifying type, краткая связь с наследованием/overriding, инкапсуляция и контракт. **Не включено подробно:** синтаксис всех nested/local/anonymous классов (`CORE-NESTED`), полная модель overriding/dispatch (`CORE-INHERITANCE`), JPMS (`CORE-MODULES`), reflection (`CORE-REFLECTION`), JavaBeans/Spring proxy (`SPR-DI`), глубокая иммутабельность (`CORE-IMMUTABLE`). Эти ID не объявляются опубликованными ссылками.

**Термины:** *accessible* (доступно по правилам компиляции) ≠ *scope* (область действия простого имени) ≠ *visibility* в неформальной таблице ≠ фактическая возможность менять состояние через публичный API/рефлексию. `package-private` — устоявшееся название отсутствия модификатора, не ключевое слово `default`; доступ по пакетам не распространяется автоматически на подпакеты. P0/P1/P2 означают приоритет раскрытия содержания, не Middle/Senior и не частотность интервью.

## 2. Источники: версия, авторитет, назначение

### A — нормативные тексты Java SE 21

- **[JLS 21 §6.6, §6.6.1](https://docs.oracle.com/javase/specs/jls/se21/html/jls-6.html#jls-6.6)** — accessibility, условия для top-level/членов/конструкторов, private в пределах охватывающего top-level типа, различие scope/accessibility.
- **[JLS 21 §6.6.2.1](https://docs.oracle.com/javase/specs/jls/se21/html/jls-6.html#jls-6.6.2.1)** — защищённые поля и методы при наследовании между пакетами; тип квалифицирующего выражения.
- **[JLS 21 §6.6.2.2](https://docs.oracle.com/javase/specs/jls/se21/html/jls-6.html#jls-6.6.2.2)** — отдельно защищённые конструкторы, `super(...)`, anonymous class creation, запрет обычного `new Base(...)` вне пакета.
- **[JLS 21 §7.4–7.6](https://docs.oracle.com/javase/specs/jls/se21/html/jls-7.html#jls-7.6)** — пакет, top-level class/interface и запрет `private`/`protected` у top-level.
- **[JLS 21 §8.2, §8.4.8.1, §8.4.8.3](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.4.8.3)** — наследование доступных методов, overriding и запрет сужать доступ.
- **[JLS 21 §8.5, §8.8.3, §8.8.9](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.8.9)** — member types, модификаторы и неявные конструкторы.
- **[JLS 21 §9.3–9.5](https://docs.oracle.com/javase/specs/jls/se21/html/jls-9.html#jls-9.4)** — особенности членов интерфейса: методы по умолчанию `public`, допустимые `private` методы; `protected` интерфейсного метода запрещён.
- **[JLS 21 §7.7](https://docs.oracle.com/javase/specs/jls/se21/html/jls-7.html#jls-7.7)** и **[Java SE 21 AccessibleObject API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/reflect/AccessibleObject.html)** — граница именованных модулей, экспорта и глубокого рефлексивного доступа; только как направление дальнейшего изучения.

## 3. Нормативная карта — что разрешает компилятор

| Объявление / место обращения | Тот же top-level / разрешённое вложение | Другой тип в том же пакете | Подкласс в другом пакете | Произвольный тип в другом пакете | Основание |
|---|---|---|---|---|---|
| `public` член доступного типа | да | да | да | да, при доступности типа/пакета/модуля | §6.6.1 |
| `protected` поле/метод | да | да | да **при соблюдении §6.6.2.1** | нет | §6.6.1–2.1 |
| член без модификатора | да | да | нет | нет | §6.6.1 |
| `private` член | да, включая допустимые вложенные типы | нет | нет | нет | §6.6.1 |
| top-level тип без модификатора | да | да | нет | нет | §7.6 |
| top-level `public` тип | да | да | да | да, с учётом JPMS | §6.6.1, §7.6 |

Таблица — **лишь ориентир**: наличие `protected` не делает объект произвольного типа `Base` доступным для изменения из подкласса другого пакета; правила для `protected` конструктора **отличаются** от правил полей/методов. `public` член недоступного снаружи типа не делает сам тип доступным. Пакет `a.b` не считается тем же пакетом, что `a.b.c`.

## 5. Протокол граничных случаев для 02/03/04

**Ключевой сценарий в двух пакетах:** файл `api/Parent.java` и варианты `client/Child.java`. В примерах ниже строки с пометкой `НЕ компилируется` следует проверять **по отдельности**, а не оставлять в одном компилируемом файле. Базовая форма:

```java
// api/Parent.java
package api;
public class Parent {
    protected int value = 67;
    protected Parent() {}
    protected void touch() { value++; }
    int pkgField = 7;
    private int secret = 9;
}
```

```java
// client/Child.java, варианты P1/P2 — компилируются
package client;
public class Child extends api.Parent {
    public int ok(Child other) {
        touch();
        super.touch();
        return this.value + other.value;
    }
}
```

**Отдельные отрицательные варианты в теле `Child`:**

```java
int p1(api.Parent parent) { return parent.value; }       // НЕ компилируется
int p2(Child child) { return ((api.Parent) child).value; } // НЕ компилируется
int p3() { return pkgField; }                            // НЕ компилируется
Object c1() { return new api.Parent(); }                 // НЕ компилируется
```

- **P1–P3:** у `api.Parent` квалифицирующий тип родителя, либо доступ package-private из чужого пакета; static type важнее предполагаемого runtime-объекта. Положительный контраст: `Child other` имеет подходящий квалифицирующий тип.
- **P4:** соседний `client.Sibling extends api.Parent`; в теле `Child` выражение `sibling.value` не компилируется, поскольку `Sibling` не является `Child` или его подклассом.
- **P5:** в том же пакете `api` класс `Neighbor` может читать `new Parent().pkgField` и `new Parent().value` без наследования (при доступном конструкторе; для показанного `protected` конструктора пакет доступа достаточен).
- **C1:** `Child() { super(); }` допустимо в другом пакете.
- **C2:** `new api.Parent()` из `client` недопустимо и внутри `Child`, и снаружи.
- **C3:** `new api.Parent() {}` (анонимный подкласс) допустимо в `client` даже из класса, который сам не наследует `Parent`; это **специальное правило конструктора** (§6.6.2.2), не универсальное разрешение на вызов `new Parent()`.
- **N1:** `class Outer { private int secret = 67; static class Nested { int read(Outer o) { return o.secret; } } }` компилируется. **N2:** соседний top-level `Friend` не имеет доступа к `Outer.secret` даже в одном пакете.
- **T1:** `private class Hidden {}` и `protected class Hidden {}` на top-level не компилируются (§7.6). `public static class Visible` внутри package-private `Hidden` не делает выражение `api.Hidden.Visible` доступным в другом пакете.
- **O1/O2:** родительский `protected void m(){}`, подкласс с `@Override public void m(){}` — допустимо, с `@Override void m(){}` — ошибка снижения доступа.
- **O3:** пакетный `void m(){}` в `api.Parent`, `@Override public void m(){}` в `client.Child` — ошибка: не переопределяет метод доступного предка.
- **I1/I2:** интерфейс с `private int helper(){return 67;}` и вызовом из `default` метода компилируется; `protected int helper();` в интерфейсе — нет (§9.4).

## 6. Практическая инкапсуляция — обязательная граница понятий

- **Правило языка**: модификатор ограничивает допустимые обращения в исходном коде; его предназначение — не заставлять клиентов зависеть от деталей реализации (§6.6).
- **Дизайн API (не гарантия JLS)**: делать поле `private`, предоставлять операции `deposit(amount)`/`withdraw(amount)` с проверкой суммы и состояния, сохранять инварианты; не добавлять публичные setters без бизнес-смысла. Связь с уже опубликованным примером `CreditAccount` из `CORE-CLASSES`.
- **Контрпример**: `private List<String> items` с публичным `getItems()`, возвращающим сам изменяемый список, допускает внешнее изменение внутреннего состояния; решение зависит от контракта — неизменяемый вид, копия или доменная операция. Не обещать «getter = инкапсуляция», «private = безопасность от reflection» или «final = deep immutable».
- **Минимальный доступ — не универсальная догма**: `protected` разумен для документированных extension points, package access — для тесно связанных внутренних типов, `public` — для осознанного API. Выбор зависит от контрактов библиотеки/фреймворка, а не только от таблицы доступа.

## 8. Непроверенные гипотезы и ограничения результата

- Не проверена исчерпывающая репрезентативность банков C, не оценивалась частота вопросов на интервью; источник C не определяет JLS-гарантию.
- Не выполнялась визуальная проверка Obsidian и полного Markdown-рендера. Ссылки на нормативные источники проверялись поиском/чтением соответствующих разделов, но не выполнялась автоматическая проверка всех ссылок репозитория.
- `javac` проверяет конкретные примеры, а не доказывает нормативный контракт; следовательно, спорные утверждения привязаны к JLS 21, а не к поведению компилятора как единственному источнику.
- Контроль доступности разных именованных модулей, reflection/`setAccessible`, NestHost/NestMembers и JVM runtime access checks оставлен для отдельного исследования. Не выдавать «public виден всем» или «private невозможно обойти» за универсальную норму.
- Перед написанием статьи 02 повторно сверить фактический `main`, тексты JLS 21 и файл плана; после написания выполнить coverage gate по каждому P0 и ретроспективно проверить не использованный при планировании C-источник.
