# Непрерывный цикл GitHub → Firefox → роли 00–06

**Назначение:** один постоянно работающий Python-процесс опрашивает GitHub Issue comments, проверяет условия `backend-handoff`, выбирает вкладку роли в **обычном Firefox**, копирует поручение и ждёт ручной отправки. После подтверждения (`y`) возвращается к опросу GitHub. **Selenium, Marionette и платный OpenAI API не используются**.

## 1. Что уже известно про ваш Firefox

В одном открытом окне Firefox роли закреплены за вкладками слева направо:

| Роль | Вкладка |
|---|---:|
| 00 | 1 |
| 01 | 2 |
| 02 | 3 |
| 03 | 4 |
| 04 | 5 |
| 05 | 6 |
| 06 | 7 |

Это **позиции**, а не неизменные идентификаторы вкладок. Если вкладки перемещены, открыты или закрыты, таблица может перестать соответствовать реальности. Скрипт **не читает URL** открытой вкладки: перед `Ctrl+V` проверяйте глазами выбранную роль.

## 2. Быстрый запуск (Windows PowerShell)

Распакуйте комплект, откройте PowerShell **в каталоге с `tools/`** и выполните:

```powershell
# Сохранить проверенную таблицу 00→1, …, 06→7 (один раз)
py tools/role_cycle.py init-tabs

# Проверить привязки и очередь без изменения браузера
py tools/role_cycle.py status

# Если предыдущий тест demo-event-0001 в чате 06 действительно отправлен,
# подтвердите его, чтобы старое тестовое поручение не мешало очереди:
py tools/manual_chat_delivery.py confirm --role 06 --event demo-event-0001

# Для приватного GitHub-репозитория нужен токен с Issues: read,
# Pull requests: read и Contents: read (при необходимой проверке PR/CI):
$env:GITHUB_TOKEN = "ВСТАВЬТЕ_ВАШ_ТОКЕН_ЛОКАЛЬНО"

# Пилот по одному Issue: только посмотреть задания (без нажатий/копирования)
py tools/role_cycle.py run --issue 34 --once --dry-run

# Пилот по одному Issue: непрерывный цикл (Ctrl+C останавливает)
py tools/role_cycle.py run --issue 34 --interval 60
```

**Не вставляйте токен в GitHub Issue или чат.** Для проверки всех открытых Issues вместо `--issue 34` выполните:

```powershell
py tools/role_cycle.py run --interval 120
```

Без `--once` процесс работает, пока открыт терминал. В режиме `--dry-run` вызов GitHub всё равно **сохраняет/обновляет локальные файлы inbox и локальный SQLite диспетчера**, но не меняет браузер и не подтверждает доставку. GitHub не изменяется при опросе. После старта проверьте очередь через `py tools/role_cycle.py status`, чтобы не передавать случайно исторические задания.

## 3. Что делает оператор

Когда обнаружится ожидающее поручение, скрипт:

1. Покажет получателя, событие, текущий статус и номер вкладки.
2. Активирует единственное окно Firefox, выберет соответствующую вкладку, скопирует Markdown поручения в буфер обмена Windows.
3. Остановится на запросе подтверждения.

**Проверьте, что открыт нужный чат**, щёлкните в поле ввода, нажмите `Ctrl+V`, затем `Enter`. Вернитесь в PowerShell и введите:

- `y` — **только после реальной отправки**; отметить событие как подтверждённое и продолжить цикл;
- `s` — отложить событие, оставить в очереди без подтверждения; в этом запуске оно больше не предлагается;
- `q` — остановить процесс, оставив неподтверждённое событие в очереди.

Пустой Enter **не подтверждает** отправку. За один проход выполняется **не больше одной передачи каждой роли**. После прохода диспетчер снова опрашивает GitHub. Роль, завершившая задачу, должна создать **новый Issue comment с одним fenced `backend-handoff` JSON-блоком** согласно [ROLE_HANDOFF_PROTOCOL.md](ROLE_HANDOFF_PROTOCOL.md). Результаты и следующий маршрут читаются через GitHub, не через страницу ChatGPT.

## 4. Как запустить настоящий переход между чатами

Для пилота используйте [Issue #34](https://github.com/Melchiorius/backend-interview-labs/issues/34). Роль 06 создаёт там тестовое, но **явно идентифицированное** поручение роли 00 (`from: "06"`, `to: ["00"]`, `gate: "G6"`, `action: "READY"`, уникальный `event_id`). Комментарий должен быть написан от разрешённого GitHub login. Это поручение является запуском теста доставки, **не основанием для merge PR #35**.

Когда роль 00 получит сообщение в первой вкладке, она может выполнить процессную проверку и затем опубликовать новое поручение (например, роли 01) **в том же Issue #34**, с новым уникальным `event_id` и другим `from`/`to`. `role_cycle.py` обнаружит комментарий на следующем цикле. **Важно:** роль 00 не должна объявлять G1/G4 одобренными или мержить PR только ради демонстрации маршрутизации.

## 5. Ограничения и безопасность

- Требуется **Windows** и **ровно одно видимое окно Firefox**. Переключение использует Windows `SendInput`, а не браузерную автоматизацию.
- **Ручной шаг обязателен для каждого сообщения:** `Ctrl+V`, `Enter`, `y`. Скрипт не знает, принял ли ChatGPT сообщение, и доверяет вашему подтверждению.
- При падении/перезапуске состояние `prepared` остаётся в SQLite; событие **не считается отправленным**. Возможна повторная передача уже отправленного, если забыть `y`. Сначала проверьте чат и только потом подтвердите.
- Цикл ждёт человека и **не проверяет GitHub, пока ожидает ввод `y/s/q`**. После подтверждения он продолжает автоматически. Для полностью бесконтрольной работы с существующими чатами механизм не предназначен.
- `GITHUB_TOKEN` хранится в переменной окружения, не в файлах проекта. Репозиторий приватный, запросы выполняются через официальный GitHub REST API.
- Локальная директория `.dispatcher/` содержит URL, положение вкладок, очередь и SQLite; не коммитьте её. При обновлении программы **не удаляйте `.dispatcher/`**.
- `--issue` сканирует один Issue (в том числе закрытый); без него опрашиваются открытые Issues. При сетевых сбоях процесс повторяет запрос с ограниченной задержкой; при ошибке данных/неправильном переключении прекращает работу без автоматического подтверждения.

## 6. Проверки

```powershell
py -m py_compile tools/role_dispatcher.py tools/manual_chat_delivery.py tools/role_cycle.py
py -m unittest discover -s tools/tests -v
```

Автоматические тесты не управляют реальным Firefox и не обращаются к GitHub. Сначала пробуйте `--once --dry-run`; функциональную проверку на вашем компьютере выполните под вашим контролем.
