# Аудит полноты Java Core: исследование перед написанием статей

**Дата:** 2026-11-19. **Объект проверки:** три существующие статьи Java 21 — `CORE-TYPES`, `CORE-CONVERSIONS`, `CORE-PARAMS`. **Цель:** выявить значимые вопросы, которых нет в материале или которые лишь упомянуты. Это не утверждение, что статьи содержат фактические ошибки, и не статистическая оценка «процента освоения».

**Важное разделение:** [CURRICULUM.md](CURRICULUM.md) — перечень тем; [JAVA_CORE_PLAN.md](JAVA_CORE_PLAN.md) — первоначальная карта будущих статей; этот документ — результаты *ревизии покрытия* уже написанных материалов и проверяемый план дополнений. **Готовность к собеседованию не равна полноте JLS:** надо знать типовые практические вопросы, но не нужно переписывать спецификацию целиком.

## Метод исследования

1. **Текст источника:** прочитать статью полностью и перечислить, на какие вопросы она отвечает явно; упоминания без объяснения считать только «обозначено».
2. **Нормативный источник:** проверить применимые разделы JLS и Java SE API именно целевой версии. Различать гарантии Java, особенности HotSpot, наблюдения на одной машине и распространённые мифы.
3. **Независимые интервью-источники:** сравнить с несколькими перечнями Java Core вопросов, предпочтительно тематическими. Списки дают *кандидатов на проверку*, но не нормативные ответы. Не считать количество повторений доказательством корректности.
4. **Тестовые контрпримеры:** для каждого концептуального риска сформулировать «что выведет код?», «почему?», «изменится ли результат при другом типе/перегрузке/значении?»; воспроизвести в Java 21, когда наблюдаемое поведение определено.
5. **Классификация:** **P0** — существенный пробел текущей статьи; **P1** — важное расширение, для которого можно дать минимум здесь и отдельную статью позже; **P2** — специализированный нюанс с явным «хвостом». Не маркировать всё как «углубление» ради видимости завершённости.
6. **Публикация:** сперва карта вопросов с критериями, затем текст, затем независимый проход «какого ожидаемого вопроса по названию статьи мы всё ещё не можем объяснить?».

Использованные источники: [JLS 21 §4 (Types, Values, Variables)](https://docs.oracle.com/javase/specs/jls/se21/html/jls-4.html), [§5 (Conversions)](https://docs.oracle.com/javase/specs/jls/se21/html/jls-5.html), [§8 (Classes and Methods)](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html), [§15 (Expressions)](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html), [§16 (Definite Assignment)](https://docs.oracle.com/javase/specs/jls/se21/html/jls-16.html); [Baeldung: Core Java Interview Questions](https://www.baeldung.com/java-interview-questions), [Baeldung: Java Type System Interview Questions](https://www.baeldung.com/java-type-system-interview-questions), [Baeldung: Java Wrapper Classes](https://www.baeldung.com/java-wrapper-classes), [Java Interview Handbook (сообщество)](https://srisairevanth.github.io/java-interview-handbook/), [Java Core Interview Q&A (сообщество)](https://github.com/Hruday-Boppa/Core-Java-Interview-Questions-List/blob/main/README.md). Доступ к некоторым страницам/формулировкам интервью-вопросов неполный; проверенными первоисточниками нормативных утверждений служат JLS/API, а не чужие ответы.

## CORE-TYPES — типы, значения и переменные

**Уже раскрыто:** различие примитивов и ссылок; две переменные указывают на один объект; восемь примитивов; `null`; объявленный тип переменной и фактический класс объекта; значения по умолчанию для полей; definite assignment для локальных переменных; `final` не делает объект неизменяемым; короткие ссылки на дальнейшее чтение.

| Приоритет | Не раскрыто или раскрыто лишь названием | Что читатель должен суметь объяснить / воспроизвести | Граница материала |
|---|---|---|---|
| P0 | **Точные диапазоны примитивов** и размеры, signed `byte/short/int/long`, беззнаковый `char`, разные правила для `boolean` | Почему `byte` максимум 127; что будет при `int` overflow; почему `char` не «Unicode-символ целиком» | Здесь таблица + короткий пример; подробные вычисления — CORE-NUMBERS |
| P0 | **Литералы и суффиксы** `L`, `F`, числовые системы, подчёркивания, литерал `null`, типы целых/вещественных литералов | Почему `long x = 2147483648;` не компилируется без `L`; что не так с `float x = 1.5;` | Здесь либо чёткая ссылка на будущую CORE-SYNTAX/CORE-OPERATORS с достаточным минимумом |
| P0 | **Область видимости и время жизни переменных**, поля vs локальные, параметры, `static` vs экземпляр | Где доступна локальная переменная; что компилятор запрещает прочитать; у каких полей есть default values | Здесь минимум; детали — CORE-SYNTAX и CORE-CLASSES |
| P0 | **`var`** как вывод локального типа, не динамическая типизация; невозможность `var x = null` | Почему `var x = 67;` фиксирует тип и не разрешает позже `x = "text"` | Здесь — явный пример + ограничение; развитие — CORE-SYNTAX |
| P1 | **`==` для примитивов vs ссылок**, `equals` — метод с контрактом, `Objects.equals` | Почему `String` и `int` сравниваются по-разному; как избежать NPE | Часть здесь, глубокий контракт — CORE-EQUALITY |
| P1 | **Понятие массива как ссылочного объекта** и значение элемента / базовый тип | Почему `int[]` — ссылочный тип, а `int` — примитив | Здесь 2–3 предложения; подробности — CORE-ARRAYS |
| P1 | **`final` переменной, поля, метода и класса** — разные семантики; blank final | Почему `final List` не делает коллекцию неизменяемой; что значит `final class` | Здесь минимум; CORE-CLASSES / CORE-IMMUTABLE |
| P2 | **Поля, размещение и GC**: некорректно приравнивать «примитив = стек, объект = куча» | Не выдавать внутренности HotSpot за гарантии языка | Сохранить «хвост» JVM-MEMORY |

**Критерий исправления P0:** после статьи читатель отвечает на вопросы про диапазоны, объявления/литералы, `var`, область видимости и значения по умолчанию, а не только на «чем ссылка отличается от примитива».

## CORE-CONVERSIONS — преобразования типов

**Уже раскрыто:** widening/narrowing на примерах; потеря точности `long → double`; продвижение `byte + byte → int`; boxing/unboxing и NPE; диапазон `Integer` -128..127 и негарантированность идентичности вне него; String Pool; один случай перегрузки `long` vs `Integer`; некоторые опасные преобразования.

| Приоритет | Не раскрыто или раскрыто лишь названием | Проверяемый вопрос | Граница материала |
|---|---|---|---|
| P0 | **Различие контекстов преобразования**: assignment, invocation, casting, numeric promotion | Почему `byte b = 67;` разрешено, а `takeByte(67)` не вызывает `takeByte(byte)` автоматически? | Здесь обязательно, JLS §5.2–5.6 |
| P0 | **Преобразование константных выражений** (compile-time narrowing) | Почему `byte b = 127;` допустимо, а `byte b = 128;` нет? Что меняется, если вместо литерала переменная `int`? | Здесь, несколько строк и контрастный пример |
| P0 | **Смешанное сравнение wrapper/primitive** и автоматическая распаковка `==` | Почему `Integer a = 1000; int b = 1000; a == b` — true, хотя `Integer == Integer` непредсказуемо по ссылкам? Когда возникнет NPE? | Здесь: обязательный вопрос рядом с Integer Cache |
| P0 | **Перегрузки, `null` и неоднозначность**; приоритет widening / boxing / varargs | Почему `m(String)` и `m(Integer)` дают неоднозначный `m(null)`? Почему `m(long)` выигрывает у `m(Integer)`? | Здесь — по крайней мере два контрпримера; CORE-CLASSES для общей механики перегрузки |
| P0 | **Промежуточный тип арифметики и переполнение до присваивания** | Почему `long result = 1000 * 1000 * 1000 * 1000;` уже переполнен до записи в `long`; как меняет `1000L`? | Здесь + CORE-NUMBERS |
| P1 | **Приведения ссылок, upcast/downcast, `instanceof`**, интерфейсы и `ClassCastException` | Почему компилятор разрешает downcast, но ошибка возникает при выполнении? | Здесь минимум, глубже — CORE-INHERITANCE / CORE-PATTERNS |
| P1 | **Тонкости `?:` с примитивами и обёртками**, `null`, numeric promotion | Какие ветви условного выражения вызывают unboxing и NPE? | Хвост CORE-OPERATORS либо расширение этой статьи |
| P1 | **`Integer.valueOf` vs `new Integer` (устаревшее использование), cache ≠ неизменяемость** | Почему нельзя делать догадки по `==`? | Здесь контекст без излишнего описания реализации кэша |
| P1 | **Особые значения float/double**: NaN, ±Infinity, `-0.0`, narrowing | Что происходит с `NaN == NaN`? Почему `(int) Double.NaN` не падает? | CORE-NUMBERS, в этой статье — явное направление |
| P2 | **Подробное overload resolution, generic inference, bridge methods, heap pollution** | Какая фаза применимости и где нужны unchecked conversions? | CORE-ERASURE / CORE-GENERICS / JVM-BYTECODE |
| P2 | **String Pool как самостоятельная тема** | `intern()`, compile-time vs runtime конкатенация, текстовые блоки, `StringBuilder` | CORE-STRINGS; здесь достаточно короткого предупреждения |

**Критерий исправления P0:** читатель может **не только воспроизвести кэш `Integer`**, но и объяснить, почему одинаковые на вид присваивания и вызовы методов компилируются по-разному, а `==` в смешанных типах меняет смысл.

## CORE-PARAMS — передача аргументов

**Уже раскрыто:** pass-by-value, отличие копирования примитива и ссылки, изменение общего объекта vs переназначение параметра, роль `final`, возврат нового значения, отдельный запускаемый пример, ссылки на многопоточность.

| Приоритет | Не раскрыто или раскрыто лишь названием | Проверяемый вопрос | Граница материала |
|---|---|---|---|
| P0 | **Передача массивов**, изменение элемента и переназначение параметра массива | Почему `change(arr)` меняет `arr[0]`, а `arr = new int[...]` внутри метода не меняет переменную вызывающего? | Здесь явный контрастный код |
| P0 | **Ссылки на неизменяемые объекты** (`String`, boxed `Integer`) и «изменение» через присваивание | Почему `s += "x"` или `n++` внутри метода не изменяет `String`/`Integer` вызывающего? | Здесь код + CORE-STRINGS/CORE-IMMUTABLE |
| P0 | **Что именно получает метод при `null`**, вызов метода и переназначение параметра | Почему `change(null)` может работать или дать NPE в зависимости от действия? | Здесь |
| P1 | **`varargs`**, массив за `T...` и передача явного массива | Что происходит при `foo(1,2)` и `foo(new int[]{1,2})`; где есть риск изменения массива? | Здесь понятный минимум, CORE-CLASSES для перегрузок |
| P1 | **Параметры, `final`, эффективно финальные и захват лямбдой** | Может ли лямбда изменить локальную переменную вызывающего метода? | CORE-FUNCTIONS, здесь «хвост» |
| P1 | **Перегрузка выбирается по типу выражения до вызова**, а не по фактическому классу объекта | Почему ссылка `Object` на `String` выберет `m(Object)` вместо `m(String)`? | CORE-CONVERSIONS / CORE-INHERITANCE; минимум рядом с описанием вызова |
| P2 | **Рекурсия, кадры вызова, `this`, stack vs heap** | Почему у каждого вызова свои локальные параметры; что гарантировано JVM? | JVM-MEMORY / CORE-CLASSES |

**Критерий исправления P0:** читатель умеет предсказать вывод для примитива, изменяемого объекта, массива, `String`, boxed `Integer`, `null` и переназначения локального параметра.

## Поперечные проблемы всей тройки

1. **Нет опубликованного заранее списка обязательных вопросов для каждой статьи.** Поэтому работа завершалась после нескольких правильных примеров, а обнаруженные пользователем темы добавлялись реактивно.
2. **«Упоминание» не тождественно «раскрытию».** Например, у `CORE-CONVERSIONS` есть фраза о фазах перегрузки, но нет случая неоднозначности `m(null)` или разных контекстов преобразования.
3. **Недостаточно тестов на отрицательные случаи компиляции.** Вопросы собеседований нередко проверяют, *почему Java отклоняет программу*, а не только её вывод. Для этого полезны короткие невыполняемые фрагменты с явной пометкой «ошибка компиляции», не включаемые в собираемые исходники.
4. **Слабая проверка границ ожиданий читателя.** Если заголовок обещает «типы» или «преобразования», читатель вправе ожидать диапазоны/литералы/переполнение или контексты преобразования. Нужен явный договор: что статья раскрывает полностью, а что только обозначает с точным назначением следующего материала.
5. **Пример в CI не гарантирует полноту.** Он проверяет один выбранный сценарий; не проверяет, что забыты отсутствующие в примере конструкции или что формулировка всех гарантий корректна.
6. **Интервью-источники иногда неточны.** Формулировка «128 всегда false» и универсальная фраза «примитив на стеке» не являются нормативными. Факт присутствия вопроса в подборке не даёт права повторять ответ без JLS/API.

## Процесс публикации будущей статьи: две последовательные проверки

**Research gate — ДО написания текста:** существует план с точной областью, перечнем ожидаемых вопросов (основные/дополнительные), первоисточниками, контрпримерами, связями на существующие статьи и упоминаниями будущих; назначено, где ответ будет полным. Если P0-неопределённости остались, текст не объявлять готовым.

**Coverage gate — ПОСЛЕ написания:** для каждого обязательного вопроса в плане указан раздел готовой статьи, где ответ есть в тексте и (при необходимости) коде; ссылки работают; для утверждений с ограничениями указана версия, а для непройденных проверок прямо написано «не проверено». Независимо пройтись по тематическому перечню вопросов **после** написания текста и зафиксировать новые пробелы.

Для уже опубликованных материалов применять тот же процесс ретроспективно; исправлять в следующих PR по P0, не считать старый `Implemented` равным `Interview-ready`.
