# Правила сопровождения базы знаний Java Backend

**Назначение:** самостоятельная база знаний, а не LMS. Читатель скачивает репозиторий, открывает Markdown, изучает короткий код или большой пример, по желанию решает задачу, запускает её тесты и возвращается к теории. Помощь автора, преподавателя или ИИ не предполагается.

## Источники истины
- [README.md](README.md) — вход для читателя и проверенные команды запуска.
- [docs/CURRICULUM.md](docs/CURRICULUM.md) — состав и классификация тем; не список готовых статей.
- [docs/COVERAGE.md](docs/COVERAGE.md) — факт наличия/проверки материалов, открытые пробелы.
- [docs/SOURCE_REGISTRY.md](docs/SOURCE_REGISTRY.md) — повторно используемые нормативные, объясняющие и интервью-источники по разделам курса, версии и правила доверия.
- [docs/ROADMAP.md](docs/ROADMAP.md) — **необязательные** варианты первого и следующих проходов.

## Содержание и редактура
1. Писать по-русски, сохранять точные названия Java API и устоявшиеся термины; в условных числовых примерах можно использовать 67.
2. Сначала ясное **определение и назначение**, затем модель/устройство, логика работы, конкретный пример, существенные ограничения и альтернативы. Раскрывать только подходящие теме части; без «простыней», общих фраз, механических повторов и искусственного ограничения длины.
3. **Проверять естественность русского языка:** не переводить английскую документацию пословно; точно называть действующее лицо (поток, объект, метод) и его действие. Перед схемой объяснять, кто участвует и что означают стрелки; в каждом кодовом примере показывать, какой объект общий и кем вызывается метод. Если предложение допускает вопрос «кто это делает?» или смешивает вызов метода с потоком, переписать его. Термины определять в тексте или ссылаться на существующую статью. Различать гарантии JLS/JVMS, контракт Java API и особенности конкретной реализации; версию фиксировать при зависимости от неё. Не придумывать результаты тестов, benchmark или свойства, которых спецификация не гарантирует.
4. Когда подписанная схема яснее последовательности абзацев, использовать Mermaid или переносимую иллюстрацию. **Для схем с обозначенными состояниями использовать общую палитру из четырёх смысловых цветов**, описанную ниже. Цвет — дополнительный сигнал: смысл каждого блока должен быть ясен из текста и без цвета.
5. Основная идея должна быть видна сразу. Необязательные детали допускается выносить в `> [!note]-` для Obsidian (GitHub может не сворачивать блок) или в отдельную **содержательно самостоятельную** статью. Не требовать трёх слоёв Middle/Middle+/Senior для каждой статьи; не завышать уровень обычных API. Материал допускает многократное прохождение.
6. Короткий код, поясняющий механизм, держать непосредственно в статье. Большой связный пример из нескольких методов/классов или самостоятельную задачу — в Java-файлах. Не создавать файлы/тесты по формальному признаку.
7. Для каждой фактически используемой существенной теоретической зависимости дать работающую **локальную ссылку Obsidian**; новые связи добавлять в ранее опубликованные статьи при следующих итерациях. Не ссылаться на несуществующие файлы как на готовые. Если отдельной статьи нет, изложить минимально нужное прямо здесь и отметить пробел в COVERAGE.
8. Для вынесенного Java-кода указать в комментарии краткие **пути от корня репозитория** ко всем непосредственно необходимым теориям; для README задания — действующие локальные ссылки на материалы внутри репозитория. Не перечислять всю транзитивную энциклопедию. Проверять пути и ссылки **в Obsidian vault, открытом из корня клонированного репозитория**, после перемещения файлов. GitHub не является средой навигации по материалам.

## Цветовая палитра схем

Палитра применяется **по смыслу элемента**, а не механически ко всем блокам. Если в диаграмме нет ожидания или освобождения, соответствующие цвета не нужны. Для алгоритмов и структур данных сначала определить, какие события в этой схеме соответствуют четырём ролям; если соответствия нет — не навязывать его.

| Роль | Цвет блока | Граница | Цвет текста | Имя Mermaid-класса |
|---|---|---|---|---|
| Исходное состояние / условия | `#e2e8f0` | `#64748b` | `#1e293b` | `initial` |
| Успешная работа / активное выполнение | `#dcfce7` | `#15803d` | `#14532d` | `active` |
| Ожидание / ограничение | `#fef3c7` | `#b45309` | `#78350f` | `waiting` |
| Освобождение ресурса / снятие ограничения | `#dbeafe` | `#2563eb` | `#1e3a8a` | `release` |

Внутри Mermaid-блока использовать стандартные `classDef` и `class`, без глобального CSS и плагинов. Пример применения — [Semaphore](knowledge/03-concurrency/semaphore.md). Из-за особенностей встроенного рендерера IntelliJ/Obsidian оформление может различаться; не заявлять о визуальной проверке до открытия в целевой IDE.

**Никогда не полагаться только на цвет**: давать содержательные подписи блокам, объяснять обозначения и смысл стрелок непосредственно в статье. Не заливать крупные блоки ярким цветом ради украшения, не вводить пятый цвет без содержательной причины и отдельного решения.

**Компактность важнее размера картинки:** в обычном окне Markdown Preview читатель по возможности должен охватывать схему целиком. Для вертикальных Mermaid flowchart с короткими узлами сначала уменьшать расстояния между уровнями (`rankSpacing`) и размер шрифта, при необходимости корректировать ширину переноса (`wrappingWidth`) и переносы строк в подписях. Успешно проверенный в IntelliJ пилот: внутри блока `mermaid` использовать конфигурацию `flowchart: { rankSpacing: 12, nodeSpacing: 15, wrappingWidth: 400 }` и `font-size:13px` в классах. Это **пример**, а не обязательные размеры для всех схем; параметры рендерера могут отличаться по версиям. Если даже после настройки схема слишком громоздка или представляет лишь линейный список значений — использовать таблицу либо связный текст. Не делать текст настолько мелким, чтобы он перестал читаться.

## Исследование полноты ДО написания статьи (обязательно)

**План статьи — не черновик готового текста.** Начинать с [реестра источников](docs/SOURCE_REGISTRY.md), не повторять широкий поиск с нуля для каждой темы; если в нём нет необходимых первичных источников или вопросы явно не покрыты, делать адресный поиск и обновлять реестр. Перед созданием или существенным расширением учебной статьи сначала составить краткую рабочую карту вопросов и ожидаемых ответов. Сверить с JLS / JVMS / официальным Java API целевой версии, релевантной документацией и **несколькими независимыми подборками интервью-вопросов** (официальные и неофициальные источники не смешивать по авторитетности). Проверить не только популярные вопросы, но и «что напечатает код / почему не компилируется / при каких условиях ответ другой». Если интернет недоступен, зафиксировать ограничение и не объявлять обзор интервью полным.

Минимальный план до текста должен содержать:

1. **Название, обещание и границы:** какие вопросы читатель вправе ожидать от статьи, что раскрывается здесь, что требует отдельного материала.
2. **Матрицу вопросов:** основные P0, важные P1, специальные P2, исходный источник каждого спорного требования; ключевой механизм и граничный контрпример; где будет дан ответ. Частота в неофициальных подборках — подсказка, а не доказательство полноты.
3. **Связи:** реально существующие статьи с локальными Markdown-ссылками и будущие темы как обычные ID без несуществующих ссылок. Указывать направление дальнейшего изучения.
4. **Примеры:** короткие кодовые фрагменты, специально подобранные контрпримеры (в том числе **ошибки компиляции**) и обоснование отдельного запускаемого примера/упражнения, только если это действительно полезно.
5. **Отличие гарантий от реализации:** JLS/API vs HotSpot vs результат единичного запуска; версию Java, предполагаемые условия и неустановленные факты.

**Перед публикацией** сверить готовую статью с каждым вопросом плана: P0 должен иметь достаточное собственное объяснение и проверяемый пример, P1 — понятное объяснение либо явный содержательный переход к реально существующей статье, P2 — точный «хвост». Для отсутствующей целевой статьи дать минимально необходимое объяснение на месте и обозначить пробел в COVERAGE. Проверить вопросы *снова* по независимым внешним источникам: начальный план может быть неполным.

Писать «реализована» можно о фактически существующем файле, но **это не означает «покрывает тему для интервью»**. Непроверенную полноту и непокрытые P0 отмечать в COVERAGE. Кодовая CI проверяет поведение примеров, но не полноту текста. Образец ретроспективного аудита — [проверка первых трёх статей Java Core](docs/JAVA_CORE_COVERAGE_AUDIT_2026-11-19.md).

## Код, тесты, автономность
- Базовая Java — 21; существующая основная сборка — Gradle, пока отдельно не принят иной вариант. JUnit Jupiter для тестов; Mockito для внешних зависимостей **по необходимости**, не для подмены проверяемой синхронизации.
- Пример должен быть корректным и понятным. Для многопоточности учитывать interruption, исключения, освобождение ресурсов, недетерминированность; `Thread.sleep` не использовать как основной способ координации в тестах.
- **Упражнение запускается отдельно** от остальных заданий. Техническая реализация (подпроект, source set или другой способ) выбирается после проверки, не является догмой. Неразрешённые ученические заготовки не должны делать красной основную CI-сборку эталонов.
- В README задачи указать условия, контракт, расположение заготовки, команду запуска именно её тестов, назначение тестов и ссылки на необходимую теорию. Рабочие примеры и эталоны должны иметь проверенную инструкцию запуска.
- Минимальный сценарий приёмки — чистый клон + документированные внешние предпосылки (JDK, инструменты, возможная первая загрузка зависимостей). Обязательная помощь ИИ, секретные настройки и авторские файлы исключены. Офлайн-сборку обещать только после проверки.

## Git и контроль качества
- Изменения — в отдельной ветке и PR; **роль 00 — Project Coordinator вправе самостоятельно решать об объединении PR в `main`, без отдельного одобрения владельца**. Это постоянное делегирование полномочия, но не отмена исследования, проверок, независимого ревью и устранения блокирующих замечаний согласно применимым требованиям. Не force-push общие ветки.
- Проверять *фактическую* базу, существование файлов и актуальность ссылок перед редактированием. Изменения каталогов/сборки допустимы: важна сохранённая автономность и работающие пути, а не неизменная структура.
- Для каждого PR: кратко объяснить содержание и причины, какие ссылки/предыдущие статьи затронуты, какие команды **реально** запускались и результат, что осталось непроверенным. Обновить COVERAGE для затронутых тем и, если нужно, рекомендательный ROADMAP.
- При ревью проверить: точность определений, необходимую глубину без лишнего текста, читаемость диаграмм, ссылки на существующие цели, самостоятельный запуск задания, отсутствие скрытых зависимостей и честность заявленных гарантий тестов.
- Не требовать полной реализации каталога до публикации полезной статьи. При появлении новых понятий **повторно просматривать связанные старые статьи и примеры**, добавляя ссылки/исправления через Git.

## Формат передачи сообщений между чатами (только транспорт)

Для передачи конкретного задания другой роли создать **новый обычный комментарий** в GitHub Issue/PR (conversation), начав его отдельной строкой **`Кому: NN`** (`00`–`06`, один адресат на комментарий). После заголовка — полный свободный текст: ссылки, критерии, HEAD SHA, результаты проверок и замечания остаются в том объёме, который требуется содержанием работы. Дополнительный JSON, `backend-handoff`, `event_id`, `requires` или копия поручения **не нужны**. Диспетчер переносит **только URL** комментария; его GitHub ID служит ключом от повторов. Если следующего реального действия нет, искусственное поручение не создавать.

**Это изменение только формата передачи**: оно не отменяет проверку реального состояния GitHub, независимые review, G0–G6, полномочия 00, требования к содержанию, тестам и документации. Полная краткая инструкция и PowerShell-команды — в [COMMENT_DELIVERY.md](docs/COMMENT_DELIVERY.md). Автоматическая отправка в чаты не предполагается.
