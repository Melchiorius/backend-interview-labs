# Правила работы с репозиторием

## Назначение

Репозиторий предназначен для **систематизированной базы знаний Java Backend** с возможностью подготовки к собеседованиям на разной глубине, а не для управления индивидуальной траекторией обучения. Материалы должны помогать понимать устройство платформы и аргументированно обсуждать инженерные решения, а не только воспроизводить определения.

## Язык и стиль

- Основной язык обсуждений и документации — русский.
- Имена API, классов, методов, параметров JVM и общепринятые термины не переводить искусственно.
- Объяснять причинно-следственные связи. Не подменять объяснение перечнем терминов.
- Использовать конкретные примеры. Для условных числовых примеров предпочитать число 67.
- Не упрощать техническую точность ради эффектной формулировки.

## Требования к техническим утверждениям

- Разделять гарантии Java Language Specification, JVM Specification, Java API и детали конкретной реализации.
- Указывать версию Java, если поведение зависит от версии.
- Не выдавать типичное поведение HotSpot или OpenJDK за обязательную гарантию языка.
- Для спорных и меняющихся деталей проверять первичную документацию.
- Если утверждение не подтверждено, явно обозначать неопределённость.
- Не придумывать результаты benchmark, тестов или экспериментов.

## Требования к примерам кода

- Базовая версия — Java 21.
- Код должен быть компилируемым и иметь понятный способ запуска.
- Для нетривиальных гарантий добавлять тесты или воспроизводимый эксперимент.
- Не использовать Thread.sleep как средство синхронизации тестов, если задача не состоит именно в демонстрации временного поведения.
- Для многопоточных примеров объяснять, что именно гарантируется, а что остаётся недетерминированным.
- Не скрывать ошибки обработки исключений, отмены, прерывания и освобождения ресурсов.
- Не добавлять библиотеки без обоснованной необходимости.

## Формат материала и UX без ассистента

- Репозиторий обязан быть самодостаточным: читатель открывает Markdown, изучает код, меняет заготовку, запускает отдельные тесты и возвращается к объяснению.
- Писать **коротко, точно, предметно**. Определения терминов, устройство типов данных и алгоритмов, логика API и фреймворков, гарантии и конкретные примеры обязательны там, где применимы. Не писать длинные эссе и вводные рассуждения.
- **Схема вместо нескольких абзацев**, когда это улучшает понимание. Схема должна быть точной, подписанной и переносимой между GitHub и Obsidian.
- Средний объём не является целью: не размывать статью и не опускать важную информацию ради краткости.
- Слои Middle/Middle+/Senior факультативны, выбор глубины и последовательности принадлежит читателю.
- Использовать [простую методику самостоятельного чтения](docs/STUDY_METHOD.md) и [шаблон краткой статьи](docs/TOPIC_TEMPLATE.md); не навязывать пользователю экзамен или регистрацию.

## Работа с Git

- Не работать непосредственно в main, если задача предполагает изменение файлов.
- Создавать отдельную ветку на логическую задачу.
- Делать небольшие, содержательные коммиты.
- Перед PR запускать релевантные тесты и указывать фактический результат.
- В PR описывать цель, ключевые изменения, проверку и известные ограничения.
- Не выполнять merge без прямого разрешения владельца.
- Не переписывать историю общей ветки и не применять force push без отдельного согласования.

## Границы

- Не превращать лабораторию в набор случайных задач.
- Не добавлять Spring Boot, базы данных, брокеры и Docker только ради технологического списка.
- Не смешивать спецификацию платформы, детали реализации и собственные предположения.
- Не считать успешную компиляцию доказательством корректности многопоточного поведения.

## Обязательная навигация по курсу и статусам

Перед созданием урока, задания или рекомендацией изменить инфраструктуру:
1. Прочитать [архитектуру курса](docs/COURSE_ARCHITECTURE.md), [каталог](docs/CURRICULUM.md), [реестр покрытия](docs/COVERAGE.md), [стандарт заданий и тестирования](docs/EXERCISE_AND_TESTING_STANDARD.md) и [правила решений](docs/DECISION_AND_WORKFLOW.md).
2. Проверить актуальный main, существующие файлы и статус задания; план в документах не доказывает наличие реализации.
3. Определить зависимости/пробелы; не терять темы, которые не возникали в последних интервью (Semaphore, CountDownLatch, Mockito и т. д.).
4. Использовать Divide → Understand → Merge при организации материала; обеспечить самостоятельные слои Middle/Middle+/Senior без завышения уровней. Путь, темп и повторные проходы определяет читатель.
5. Для каждого PR с материалами обновить COVERAGE.md (состояние и глубина контента, не оценка человека) и необходимые ссылки, приводить только реально запущенные проверки.
6. Тесты на основе JUnit Jupiter; Mockito — для подходящих зависимостей; будущие упражнения запускать независимо через Gradle/IDE, не ломая main незавершёнными заготовками.
7. Работать в feature-ветке, не выполнять merge без разрешения владельца.

**Принцип рациональности:** оптимизировать совокупные затраты на весь жизненный цикл, инвестировать в архитектурные границы и фундаментальное понимание, но не реализовывать неподтверждённые сценарии заранее. При повторных неудачах пересматривать стратегию; различать гипотезы и факты, рассматривать безопасное восстановление известного исправного состояния. Подробности: [DECISION_AND_WORKFLOW.md](docs/DECISION_AND_WORKFLOW.md).

## Самодостаточность без преподавателя или ИИ

Критерий приёмки: пользователь с чистым клоном, JDK и IDE (или командной строкой) может самостоятельно найти тему, понять термины и принцип, открыть пример, изменить упражнение, запустить его тесты, интерпретировать результат и вернуться к соответствующему объяснению. **Автор, чат и подключённый ИИ не являются частью обязательной инфраструктуры.** Не оставлять «спросите преподавателя» вместо необходимого объяснения. Не требовать постоянного интернета для чтения локальных статей, примеров и запуска уже полученных зависимостей; первоначальная загрузка зависимостей может требовать сети — это указать явно.

Проверка публикации: пройти пользовательский сценарий из чистого клона, проверить пути и команды, диагностичность ошибок, наличие точного задания и объяснения границ того, что способны доказать тесты. При неопределённости не заявлять о проверке до фактического воспроизведения.

## Обязательные содержательные ссылки

- Если статья опирается на понятия из другой статьи, дать рядом с первым существенным использованием **реальную относительную ссылку** на определение, а не просто упомянуть название. Для комплексного материала перечислить все необходимые самостоятельные темы (без транзитивного дублирования всей энциклопедии).
- Каждый пример, заготовка и эталон Java содержит **короткий комментарий у класса или в начале файла**, перечисляющий все **непосредственно необходимые** теоретические темы и их пути **от корня репозитория** (`knowledge/...`). Если используется несколько механизмов, дать ссылки на каждый. Комментарий не заменяет объяснение логики кода.
- Рядом в `README.md` задачи размещать **кликабельные Markdown-ссылки** на те же статьи и обратно из теории — на код/упражнение. Пути в Java-комментариях могут быть обычным текстом (не гарантируется кликабельность в IDE); читатель должен легко найти файл по пути.
- Не создавать ссылок на отсутствующие файлы как на существующие. Если тема ещё не написана — фиксировать пробел в `COVERAGE.md`, а в опубликованном примере давать минимальное объяснение либо ссылку на уже существующую статью. Проверять все ссылки при PR и на чистом клоне.

## Эволюционная структура и подача глубины

- **Развивать постепенно:** по мере появления новых материалов возвращаться к старым статьям и Java-комментариям, добавлять ссылки и уточнения. Git и PR обеспечивают историю правок; не ждать полной готовности всего каталога для публикации полезной статьи.
- **Не дробить на микростатьи:** статья посвящена осмысленному блоку понятий; нюансы можно размещать в коротких факультативных Obsidian-блоках `> [!note]-` после основного объяснения. Большую самостоятельную подтему оформлять как отдельную связанную статью.
- **Не выносить код механически:** короткие демонстрации — прямо в Markdown; самостоятельные Java-файлы и тестовые задания — для крупных связных примеров и практических задач.
- **Roadmap — рекомендация по нескольким проходам**, а не обязательная последовательность и не показатель личного прогресса.
- **Не переусложнять инфраструктуру заранее:** при изменении потребностей можно перестроить каталоги и сборку, сохраняя проверяемую навигацию и запуск заданий.
- **Оформление:** видимый основной текст должен содержать всё необходимое для понимания; в callouts прятать только факультативную глубину. Цветные акценты применять умеренно, с резервным текстовым различением для GitHub и безцветного отображения.
