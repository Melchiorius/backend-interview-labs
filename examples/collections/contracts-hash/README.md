Предпосылки: [equals/hashCode](../../../knowledge/01-java-core/equality.md), [Generics](../../../knowledge/01-java-core/generics.md), [Неизменяемость](../../../knowledge/01-java-core/immutability.md).

## Что запускается

[ContractsHashProbe.java](src/ContractsHashProbe.java) — самостоятельная программа без входных данных и внешних зависимостей. Она создаёт небольшие коллекции в памяти, сравнивает результаты операций с ожидаемыми значениями и печатает 71 строку ([эталон](expected.stdout)). При несовпадении проверка бросает AssertionError независимо от флага -ea. Метки CC01…CC29 и CH01…CH28 — номера наблюдений в программе, **не** идентификаторы строк исследовательской матрицы. Это не набор из 71 JUnit-теста и не полноценная проверка всей теории.

## Запуск

Нужны OpenJDK 21 (javac и java из одного JDK), Bash, diff, grep, mktemp и стандартные Unix-утилиты. Из корня локальной копии репозитория:

```bash
bash examples/collections/contracts-hash/verify.sh
```

Или из каталога примера: `./verify.sh`. Проверочный скрипт компилирует только корректный исходный файл с помощью `javac --release 21 -encoding UTF-8 -Xlint:all`, запускает программу с временным путём к классам, полностью сравнивает стандартный вывод через `diff -u`, затем отдельно компилирует [N01](negative/N01.java) и [N02](negative/N02.java). Временные файлы удаляются при выходе; код завершения 0 означает успех всех проверок. При успехе печатаются диагностики негативных случаев, их exit=1 и итоговая строка PASS. Не компилируйте весь каталог одним вызовом javac: отрицательные исходники специально некорректны.

Для запуска только корректного примера из его каталога:

```bash
java src/ContractsHashProbe.java
```

## Почему изменяемый ключ перестаёт находиться

В CH11–CH15 HashMap создаётся с initial capacity 16, вставляется единственный ключ id=1, других вставок и resize нет. Для конкретной реализации OpenJDK 21 spread(h)=h ^ (h >>> 16); для 1 и 67 spread равен исходному hash. При длине таблицы 16 индекс (16-1) & hash меняется с 1 на 3. Узел хранит hash вставки, поэтому новый поиск не находит старую запись, хотя size остаётся 1. В этом примере восстановление id=1 возвращает возможность поиска. Это объяснение по [закреплённому исходнику OpenJDK 21](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java), а не универсальная гарантия Map: изменение ключа, влияющее на equals, пока ключ хранится в карте, оставляет поведение неопределённым контрактом. Не рассчитывайте на восстановление ключа в прикладном коде.

## Дополнения итогового аудита B1/B2

B1: CountingKey не реализует Comparable, все ключи имеют hashCode=67, equals сравнивает неизменяемый id за постоянную стоимость. Обычный runner проверяет только size, успешный поиск по равному ключу и отсутствие нового ключа. Отдельно из каталога примера:

```bash
java src/ContractsHashProbe.java --observe-collisions
```

Этот режим печатает число вызовов equals на отсутствующем query для n=16,32,67,128; счётчик не участвует в равенстве. Это наблюдение реализации, не эталон stdout и не benchmark. В [закреплённом HashMap.java OpenJDK 21](https://github.com/openjdk/jdk21/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java) TreeNode.find при равном hash и отсутствии пригодного сравнения может искать обе ветви; число посещений может быть O(m) для m ключей в bin. Счётчик не доказывает наличие дерева и не фиксирует его форму. Точные counts зависят от реализации. Независимое наблюдение, включая N5 (нарушенный протокол итератора, отсутствие CME не гарантируется), описано в [итоговом аудите](../../../docs/audits/COLLECTIONS_FINAL_COVERAGE_2026-11-24.md). N5 не добавлен к обязательному выводу.

B2: обычный LinkedHashMap сохраняет insertion order после get(a); access-order map переносит a в конец. В небольшой однопоточной LRU-модели removeEldestEntry возвращает size()>2, после get(a) и put(c) удаляется b, ключи [a,c]. Это ограничение числа отображений, не памяти/TTL/потокобезопасности. LinkedHashSet повторным add(1) не меняет порядок, но Java 21 addLast(1) перемещает существующий элемент в конец; порядок [67,2,1]. Явное позиционирование карты и обратное представление уже показаны CC27–29. См. [LinkedHashMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/LinkedHashMap.html), [LinkedHashSet](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/LinkedHashSet.html).

## Отрицательная компиляция и границы проверки

N01 (CC-01): Map не является Collection. N02 (CC-10): List<String> не является List<Object>. Каждый файл компилируется отдельно с --release 21 -XDrawDiagnostics; проверяется exit=1 и категория compiler.misc.inconvertible.types для javac 21, не полная строка сообщения. Другой компилятор или версия диагностик могут потребовать адаптации скрипта. Это ошибки компиляции, в отличие от ожидаемых исключений при выполнении.

Пример не закрепляет порядок HashMap/HashSet, не измеряет время/память, не исследует приватные бакеты и не доказывает потокобезопасность или атомарность compute/merge. Capacity, load factor, resize, tree bins, сложность (CH-05/06/07), конкурентность (CH-09) и остальные вопросы раскрываются в теории. Не переносите детали OpenJDK на все реализации Map.
