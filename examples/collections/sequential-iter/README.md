# Последовательные коллекции и итераторы: практические проверки Java 21

Теория: [последовательные коллекции](../../../knowledge/02-collections/sequential.md) и [итераторы](../../../knowledge/02-collections/iteration.md).
Предпосылки: [контракты коллекций](../../../knowledge/02-collections/contracts.md), [хеш-коллекции](../../../knowledge/02-collections/hash-collections.md), [массивы](../../../knowledge/01-java-core/arrays.md), [обобщённые типы](../../../knowledge/01-java-core/generics.md).
Основание: [исследовательский план C2](../../../docs/plans/COL-SEQUENTIAL-ITER.md).

## Что запускается

[SequentialIteratorProbe.java](src/SequentialIteratorProbe.java) — самостоятельная программа без входных данных и внешних библиотек. Вспомогательный метод `check` сравнивает ожидаемое значение с фактическим; при расхождении возникает `AssertionError` независимо от флага `-ea`. Метод `throwsType` проверяет тип ожидаемого исключения. Программа печатает 52 строки; весь вывод сравнивается с [эталонным файлом](expected.stdout). Это **52 наблюдения одного исполняемого примера, а не 52 теста JUnit** и не исчерпывающая проверка плана.

При чтении таблицы ниже полезно различать исключения: `NoSuchElementException` — запрошен отсутствующий элемент; `IllegalStateException` — операция вызвана в неподходящем состоянии итератора; `UnsupportedOperationException` — реализация не поддерживает изменение; `ConcurrentModificationException` — итератор обнаружил несовместимую модификацию, но такое обнаружение гарантировано не для каждого случая.

## Воспроизведение

Потребуются OpenJDK 21 (`javac` и `java` из одного JDK), Bash, `diff`, `grep`, `mktemp` и стандартные Unix-утилиты. Из корня репозитория:

```bash
bash examples/collections/sequential-iter/verify.sh
```

Из каталога примера можно вызвать `./verify.sh`; для запуска только корректной программы — `java src/SequentialIteratorProbe.java`. Скрипт компилирует её с `javac --release 21 -Xlint:all`, запускает JVM и полностью сверяет стандартный вывод командой `diff -u`. **Затем он действительно вызывает `javac` отдельно для N01 и N02**, проверяя, что каждая компиляция завершается ожидаемой ошибкой и выдаёт нужную диагностическую категорию. Эти файлы **намеренно не проходят компиляцию**, поэтому их нельзя включать в общую успешную сборку. Временные файлы удаляются при завершении скрипта; код выхода 0 означает успешную проверку всех условий.

## Разбор

| Сценарий | Строки плана | Механизм и граница |
|---|---|---|
| Размер, вставка, массив | CS-01/03/12 | `ensureCapacity(67)` у `ArrayList` резервирует вместимость, но не увеличивает `size()`. Вставка по индексу сдвигает позиции элементов; длина исходного массива не меняется. Внутренняя вместимость и время операций не измеряются. |
| R01 `subList` | CS-08, CI-14 | `set` через представление диапазона меняет исходный `ArrayList`; неструктурная замена `parent.set` внутри диапазона видна через представление. `clear` через представление удаляет соответствующие элементы из исходного списка. Внешнее структурное изменение исходного списка в обход представления не проверяется: после него поведение представления не определено контрактом. |
| R02 `Arrays.asList` | CS-09/14 | `set` в списке фиксированного размера заменяет элемент исходного массива, а запись в массив отражается в списке. `add` запрещён, потому что меняет размер. `new ArrayList<>(fixed)` создаёт независимую изменяемую структуру, но не копирует глубоко сами элементы. |
| R06 `Deque` | CS-05/06/07 | На пустом `ArrayDeque` `poll/peek` возвращают `null`, а `remove/element` бросают `NoSuchElementException`. Добавление `null` запрещено. Операции с концами показывают извлечение в порядке добавления (FIFO) и в обратном порядке (LIFO); нельзя переносить эту политику на все реализации `Queue`. |
| R03 и R08 `Iterator` | CI-01/02/04/08/09 | `hasNext` не извлекает элемент. `remove` до `next` и повторно без нового `next` вызывают `IllegalStateException` у итератора `ArrayList`; допустимое удаление позволяет продолжить обход. `forEachRemaining` обрабатывает оставшиеся элементы, а `next` после исчерпания бросает `NoSuchElementException`. Итератор `List.of` не поддерживает `remove` и бросает `UnsupportedOperationException`. |
| R04 `ListIterator` | CI-03/10, CS-04 | У `LinkedList` курсор сначала стоит перед первым элементом (`nextIndex=0`, `previousIndex=-1`). После `next()` и `add(67)` список становится `[1,67,2]`, курсор стоит после 67. До нового `next/previous` операции `set/remove` недопустимы. Затем `previous()` возвращает 67, `set(68)` заменяет его, `remove()` удаляет; следующий `next()` возвращает 2. |
| Расширенный `for` | CI-06 | По массиву компилятор выполняет индексный обход, а для `Iterable` использует `Iterator`. В примере суммы одинаковы, но механизмы различаются по JLS. |
| R05 снимок | CI-07/13 | Итератор `CopyOnWriteArrayList` создан до `add/set` и поэтому обходит прежнюю последовательность `[1,2]`; текущий список уже `[68,2,67]`. Вызов `iterator.remove` запрещён. Снимок фиксирует ссылки на элементы массива, а не глубокое состояние объектов. |
| R07 fail-fast | CI-04/05/08/12 | В этом запуске OpenJDK 21 после создания итератора `ArrayList` вызывающий код добавляет элемент через сам список, затем вызывает `next()`. Наблюдается `ConcurrentModificationException`. Это **конкретное наблюдение реализации** с обнаружением по возможности (best effort), не гарантия для всех изменений, реализаций или многопоточных гонок. |

## Сценарии ожидаемой ошибки компиляции

- [N01](negative/N01.java), CI-06: `HashMap` не реализует `Iterable`; расширенный `for` принимает массив или `Iterable`. Для карты можно обходить `entrySet()`.
- [N02](negative/N02.java), CS-05: у `ArrayDeque` нет индексного `get(int)`; элементы получают через методы `Deque`.

В отчёте 03 на `javac` 21.0.12.1 обе компиляции завершились с кодом 1. Диагностические категории: `compiler.err.foreach.not.applicable.to.type` и `compiler.err.cant.resolve.location.args` (метод `get`, аргумент `int`). Скрипт проверяет код выхода и категорию, а не полный текст ошибки; другая версия компилятора может выдавать другую диагностику.

## Границы

Итераторы представлений `ConcurrentHashMap` обладают **слабой согласованностью (weakly consistent)**: они могут увидеть часть обновлений, не обещают фиксированного снимка и не используют модель fail-fast с `ConcurrentModificationException` при конкурентном изменении. Это разбор API, а не тест гонки. Ни обход по снимку, ни слабая согласованность сами по себе не обеспечивают атомарность многошаговой операции; `ConcurrentModificationException` не является механизмом синхронизации.

Нормативные источники Java SE 21: [Iterator](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Iterator.html), [ArrayList](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/ArrayList.html), [CopyOnWriteArrayList](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/CopyOnWriteArrayList.html), [ConcurrentHashMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html). Пример не измеряет время выполнения, количество выделений памяти, работу сборщика мусора, рост вместимости или размещение объектов; не использует рефлексию и не заменяет проверки всей матрицы CS/CI.
